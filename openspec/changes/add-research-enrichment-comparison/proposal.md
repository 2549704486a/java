## Why

当前项目的客群规则、活动机制和奖品资料主要来自本地设计与演示数据，能够支撑流程验证，但不足以代表真实行业素材。需要建立一个可重复执行的公网研究建库流程，把公开资料整理为带来源、可核验、可人工晋级的候选资产，并用统一任务比较项目单 Agent、项目多 Agent、Codex 直接执行和 Codex 显式委派的实际效果，而不是先假定多 Agent 更优。

已确认事实：当前正式 RAG 只接收项目内受控来源；本地客群规模和活动效果包含 Fixture/Simulated 数据；项目尚无多 Agent 代码。当前假设是，并行研究与独立审核能提升多类资料覆盖率并减少无依据结论。替代解释是，提升可能只来自更多模型调用、更强模型或不同搜索能力，而不是角色拆分本身，因此必须保留同模型、同工具的项目单 Agent 对照。当前待验证问题是本地公网搜索与正文提取在现有网络中的可用性，以及多 Agent 的质量收益能否覆盖额外成本和延迟。

## Goals

- 用同一研究简报、来源规则、输出模型和评分口径完成四种执行方式的可复查对照。
- 形成奖品候选、活动机制和客群规则模板三类带证据的候选资料，而不是继续凭空补业务事实。
- 将来源发现、事实提取、冲突审核和最终导出分开，保留每条结论的来源与处理轨迹。
- 通过实测质量、延迟、模型用量和人工复核成本决定是否保留项目多 Agent 工作流。

## Non-Goals

- 不从公网生成或推断真实用户记录、客群人数、库存、内部采购成本、预算、转化率和活动收益。
- 不让研究 Agent 写 MySQL、修改活动状态、发布活动或直接激活正式 RAG 文档。
- 不建设通用 Supervisor 平台、长期自治爬虫、定时任务、研究 UI 或任意网站采集框架。
- 不把 Codex 的内部实现当作可观测事实；只区分本次执行是否显式使用委派工具。
- 不以一次胜负证明架构优劣，也不为了课程覆盖强行保留多 Agent。

## What Changes

- 新增可版本化的研究简报、来源证据、候选资料和运行报告契约，明确 `PUBLIC_RESEARCH`、`FIXTURE` 与项目实时事实的边界。
- 新增一个按需运行的公网研究入口，支持项目单 Agent 与项目多 Agent 两种模式；两种模式共享搜索/读取工具、模型配置、输出 Schema 和确定性质量门禁。
- 多 Agent 模式采用受限的混合工作流：规划 Agent 生成结构化任务，多个只读研究 Agent 并行取证，审核 Agent 检查支持关系与冲突，确定性代码负责校验和导出。
- 保存 Codex 直接执行与显式委派执行所使用的相同简报和结构化结果，生成四臂盲化比较报告，单独呈现内容质量与运行成本。
- 提供显式人工批准清单与确定性导出步骤；只有人工批准且证据门禁通过的记录才能生成待纳入项目的 Markdown/JSON 草稿，正式 RAG 清单和业务数据库仍需后续明确变更。
- 记录一次最小公网检索 Spike；若当前环境无法稳定搜索或读取页面，则停止端到端结论，只保留失败证据和显式 URL 输入模式，不用 Fixture 冒充联网成功。

## Capabilities

### New Capabilities

- `public-research-enrichment`: 定义公网资料发现、证据留痕、单/多 Agent 研究、候选治理与人工晋级边界。
- `research-enrichment-evaluation`: 定义四种执行方式使用统一输入、盲化评分、成本记录和结论判定的行为。

### Modified Capabilities

无。现有正式 RAG、运营活动和兑换能力的外部行为不在本次变更中修改。

## Impact

- `agent-service`：新增独立的研究建库模块、命令行入口、配置、结构化运行轨迹和定向测试；复用现有 LangChain、模型配置及 Pydantic，不接入用户/运营在线对话。
- `agent-service/research-data`：新增研究简报、少量来源摘要、候选结果、批准清单和对照报告；不保存网页全文、密钥或用户数据。
- 依赖与网络：需要一个经过 Spike 验证的公网搜索入口和受限 HTTP 页面读取；新增依赖必须限于该模块并支持失败显式化。
- `docs/agent-design` 与课程路线图：记录数据模型实例、真实运行结果、多 Agent 是否保留及课程覆盖进度。
- 当前未提交的 Java MCP 和 `agent-service/devtools/` 改动不属于本变更，不修改也不纳入提交。
