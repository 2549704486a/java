## Purpose

为公网资料建库提供一套能区分模型、工具和协作架构影响的对照方法，用统一输入和盲化评分判断项目多 Agent 是否带来足以保留的实际收益。

## ADDED Requirements

### Requirement: 使用冻结简报执行四臂对照
正式比较 SHALL 包含 `PROJECT_SINGLE`、`PROJECT_MULTI`、`CODEX_DIRECT` 和 `CODEX_DELEGATED` 四种执行臂，并使用同一组冻结研究简报、同一资产输出契约和同一来源政策。`CODEX_DIRECT` 只表示本次可见执行未显式调用子 Agent，`CODEX_DELEGATED` 只表示本次可见执行显式使用了委派能力，系统 MUST NOT 据此推断 Codex 服务内部实现。

#### Scenario: 启动正式比较
- **WHEN** 操作者启动一轮正式比较
- **THEN** 四种执行臂分别读取内容相同且版本一致的冻结简报
- **THEN** 每个执行臂写入隔离的运行目录，不读取其他执行臂的候选结果

#### Scenario: 某执行臂缺席
- **WHEN** 任一执行臂没有结果或没有满足统一输出契约
- **THEN** 报告将该执行臂标记为未完成
- **THEN** 报告不得把剩余执行臂的结果描述为完整四臂结论

### Requirement: 分开解释架构比较与实际效果比较
比较报告 SHALL 把 `PROJECT_SINGLE` 对 `PROJECT_MULTI` 作为同模型、同工具条件下的协作架构比较；把项目执行臂对 Codex 执行臂作为包含模型、搜索能力和运行时差异的实际效果比较。报告 MUST NOT 将跨系统差异单独归因于多 Agent。

#### Scenario: 项目多 Agent 优于 Codex 直接执行
- **WHEN** `PROJECT_MULTI` 在内容评分上高于 `CODEX_DIRECT`
- **THEN** 报告可以说明本轮项目流程产出更好
- **THEN** 报告同时说明该差异不能排除模型、搜索工具和运行环境的影响

#### Scenario: 比较项目内部两种模式
- **WHEN** `PROJECT_SINGLE` 与 `PROJECT_MULTI` 使用相同配置完成同一简报
- **THEN** 报告可以把两者差异作为角色拆分候选收益证据
- **THEN** 报告仍需同时展示调用量、延迟和失败情况

### Requirement: 输出在人工评分前盲化
系统 SHALL 在人工评分前为各执行臂生成不暴露执行方式的展示副本，并单独保存可恢复的标签映射。评分者 SHALL 只依据候选内容、来源和失败信息评分，不依据 Agent 数量、运行日志或执行臂名称评分。

#### Scenario: 生成盲评材料
- **WHEN** 所有可用执行臂完成结果归一化
- **THEN** 系统生成只包含匿名标签、候选内容和来源证据的评分材料
- **THEN** 执行方式与匿名标签的映射不出现在评分材料中

#### Scenario: 评分完成后揭盲
- **WHEN** 评分记录已经完成并锁定
- **THEN** 系统使用保存的映射生成按真实执行臂归属的比较报告
- **THEN** 原始评分值保持不变

### Requirement: 同时执行确定性检查与人工质量评分
每个执行臂 SHALL 接受相同的确定性检查，至少统计 Schema 通过率、目标数量完成度、有效来源数、可追溯结论比例、证据支持候选数、冲突显式率、无依据结论数和重复候选数。人工评分 SHALL 至少覆盖项目相关性、事实支持程度、适配建议可用性和冲突处理质量，并保留评分说明。

#### Scenario: 候选数量多但证据不足
- **WHEN** 某执行臂达到目标数量但包含无依据结论
- **THEN** 数量完成度可以为满值
- **THEN** 证据支持指标和人工事实评分分别反映该缺陷，不以数量掩盖质量问题

#### Scenario: 候选少但全部可用
- **WHEN** 某执行臂未达到目标数量但现有候选均有可靠来源且适配建议清晰
- **THEN** 报告分别呈现数量缺口和候选质量
- **THEN** 报告不得只用单一总分隐藏两者差异

### Requirement: 如实记录运行成本和缺失数据
每个执行臂 SHALL 记录可获得的端到端耗时、模型调用次数、Tool 调用次数、输入 Token、输出 Token、失败阶段和重试次数。运行环境未提供的成本字段 SHALL 为未知，MUST NOT 记为零或由其他执行臂推算。

#### Scenario: 项目执行臂提供完整模型用量
- **WHEN** 模型返回每次调用的可靠 Token 数据
- **THEN** 报告展示该执行臂的累计输入和输出 Token
- **THEN** 多 Agent 的规划、研究与审核调用全部计入

#### Scenario: Codex 执行臂没有精确 Token 数据
- **WHEN** 当前 Codex 运行环境未暴露精确 Token 或价格
- **THEN** 相应字段显示未知并注明可观测边界
- **THEN** 报告不把未知值当作零成本优势

### Requirement: 使用预先声明的规则形成保留建议
正式报告 SHALL 先给出各维度原始结果，再依据预先声明的规则输出 `KEEP_MULTI_AGENT`、`KEEP_SINGLE_AGENT` 或 `INCONCLUSIVE` 建议。项目多 Agent 只有在无新增门禁失败、至少三份冻结简报中赢得两份人工质量评分，并且总计增加至少两条可人工批准候选时，才可建议保留；否则 SHALL 建议保留单 Agent或标记证据不足。

#### Scenario: 多 Agent 质量提升且门禁稳定
- **WHEN** `PROJECT_MULTI` 满足全部保留条件
- **THEN** 报告建议 `KEEP_MULTI_AGENT`
- **THEN** 报告同时展示其延迟和模型调用成本，由人工决定是否接受代价

#### Scenario: 多 Agent 只增加调用量
- **WHEN** `PROJECT_MULTI` 没有增加可批准候选或没有赢得至少两份简报评分
- **THEN** 报告不得因实现了多个角色而建议保留
- **THEN** 报告建议 `KEEP_SINGLE_AGENT` 或在数据缺失时标记 `INCONCLUSIVE`

### Requirement: 试运行与正式比较必须分离
系统 SHALL 先使用一份小型简报完成联网 Spike 和流程试运行。试运行结果 SHALL 标记为 `PILOT`，不能进入正式胜负统计；只有冻结简报、执行配置和评分规则后产生的结果才能标记为 `OFFICIAL`。

#### Scenario: 根据试运行修改提示词
- **WHEN** 团队根据 Spike 结果调整研究提示词、来源规则或输出字段
- **THEN** 旧结果继续保留 `PILOT` 标识
- **THEN** 四个正式执行臂使用调整后冻结的同一版本重新运行

#### Scenario: 正式运行后发现评分规则缺陷
- **WHEN** 正式结果产生后需要修改评分规则或保留阈值
- **THEN** 原报告保持原规则下的结果
- **THEN** 新规则使用新的实验版本重新出具报告，不回写原始评分
