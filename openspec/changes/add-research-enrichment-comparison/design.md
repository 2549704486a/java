## Context

参见 [proposal.md](./proposal.md) 的问题与范围，以及两份能力规格。当前项目已经有 Pydantic 数据契约、LangChain `create_agent`、模型用量与 Tool 轨迹、受控 RAG 目录和来源引用，但没有公网研究模块，也没有多 Agent 运行代码。正式 RAG 要求项目内受控来源且只保存稳定知识，运营规划中的客群规模、奖品库存、成本和历史指标来自业务事实快照，因此公网研究结果不能直接复用现有 `KnowledgeCatalog` 或 `CampaignPlanningSnapshot`。

课程第八讲把研究报告列为多 Agent 的典型场景，同时明确简单任务不应拆分、角色之间应传递结构化状态并限制循环。当前 LangChain 官方文档也把 Subagents 用于职责隔离和上下文隔离，把 Custom workflow 用于“确定性步骤 + Agent 步骤”的混合流程。本设计采用后者，不搭建自由对话式 Agent 团队。

## Goals / Non-Goals

**Goals:**

- 用一个与在线用户 Agent、运营 Agent 隔离的按需命令完成研究，不改变现有 Web 请求生命周期。
- 让单 Agent 与多 Agent 共享模型、Tool、来源预算、Schema 和门禁，使项目内部比较具有解释力。
- 让每条公网结论都能回到一段实际读取到的来源证据，并允许明确表达冲突和缺失。
- 保留足够的运行数据复盘角色拆分是否有价值，但不保存网页全文和模型完整思维过程。
- 研究产物即使最终不保留多 Agent，也能作为候选资料继续人工使用。

**Non-Goals:**

- 不把“抓到网页”当成“事实正确”，也不让审核 Agent 代替人工批准。
- 不扩展现有运营 Harness、MCP Server、RAG 在线检索或 Agent 数据看板。
- 不支持登录态页面、JavaScript 渲染、PDF/Office 文档解析、图片 OCR 和大规模站点爬取。
- 不在第一版做 LLM Judge、向量去重、知识图谱、自动定时更新或研究任务 UI。

## Decisions

### 1. 新增独立研究子系统，不把公网数据塞进现有业务模型

代码集中在 `agent-service/app/research/`，只从命令行启动：

```text
app/research/
├── models.py       # 简报、来源、候选、运行与评分契约
├── web.py          # 受限搜索和页面读取
├── agents.py       # 单 Agent、规划 Agent、研究 Agent、审核 Agent
├── workflow.py     # 固定运行顺序与并行汇合
├── gates.py        # 确定性证据和边界校验
├── evaluation.py   # 归一化、盲化和比较报告
├── export.py       # 人工批准后的草稿导出
└── cli.py          # spike、run、blind、evaluate、export
```

研究文件放在 `agent-service/research-data/`：

```text
research-data/
├── briefs/                    # 冻结简报和评分规则
├── runs/<experiment>/<arm>/   # 各执行臂隔离结果
├── approvals/                 # 人工批准的候选 ID
└── reports/                   # 盲评材料与最终报告
```

只提交简报、短来源证据、结构化候选、评分和最终报告；网页全文、临时抓取内容、完整消息历史和密钥不进入 Git。现有 `knowledge/manifest.json` 与业务表不是该目录的下游自动目标。

备选方案是直接扩展 `KnowledgeMetadata`，允许外部 URL 并把研究结果建入 Chroma。它会把“外部候选”与“已审核业务知识”混成一个状态，也无法承载奖品候选和客群模板，拒绝采用。保持现状只靠人工浏览最快，但过程不可复用、来源和遗漏难以统一比较，作为 `CODEX_DIRECT` 对照保留而不是目标架构。

### 2. 使用一套原文证据优先的数据模型

研究模型保持宽泛语义，不能为了填业务表而猜字段。核心实例：

```json
{
  "candidate_id": "award-smart-band-001",
  "brief_id": "award-candidates-v1",
  "asset_type": "AWARD_CANDIDATE",
  "name": "某品牌智能手环候选",
  "summary": "适合作为中档数码奖品的公开商品候选",
  "project_fit": "可用于补充数码类奖品池；采购成本、兑换积分和库存仍需内部确认",
  "data_origin": "PUBLIC_RESEARCH",
  "claims": [
    {
      "text": "公开页面列出的核心规格为……",
      "source_ids": ["source-001"],
      "support_status": "SUPPORTED",
      "review_note": "页面正文直接支持"
    }
  ]
}
```

来源证据实例：

```json
{
  "source_id": "source-001",
  "url": "https://example.com/product",
  "title": "商品官方页面",
  "publisher": "示例品牌",
  "published_at": null,
  "retrieved_at": "2026-09-04T10:30:00+08:00",
  "discovered_by": "AGENT_SEARCH",
  "excerpt": "能够直接支持本条结论的短摘录",
  "read_status": "READABLE"
}
```

客群研究只输出可计算规则模板及其业务解释，例如“最近 30 天未登录且历史有兑换行为”，不会输出人数；奖品研究只输出公开商品信息和价格口径，不会填写 `award_id`、`required_points`、`unit_cost_cents` 或库存；活动研究只输出外部机制与适配建议，不会生成本项目效果数据。

候选 ID 使用可读 slug 与运行内序号，不依赖内容摘要。正式运行目录不可覆盖；重复执行必须使用新运行 ID，从而保留原始证据和评分。

### 3. 项目多 Agent 使用受限混合流水线

```text
ResearchBrief
      |
      v
Planning Agent --ResearchPlan--> deterministic coordinator
                                      |
                         +------------+------------+
                         |            |            |
                         v            v            v
                    Researcher A Researcher B Researcher C
                         |            |            |
                         +------ structured drafts-+
                                      |
                                      v
                                Evidence Reviewer
                                      |
                                      v
                              deterministic gates
                                      |
                                      v
                                CandidateBundle
```

- **规划 Agent** 只看研究简报和项目字段边界，输出有限数量的检索子任务，不接触业务写 Tool。
- **研究 Agent** 各自拥有独立上下文，只能调用公网搜索与页面读取；同一 Agent 模板按子任务多实例运行，可并行处理互不依赖的来源方向。
- **审核 Agent** 接收候选草稿和已读取来源，可按来源 ID重新读取公开页面，逐条标记支持、不完整、冲突或无依据；它不能增加新的业务事实。
- **确定性协调器** 负责扇出、汇合、超时、调用预算和一次有限修订，不让模型自由决定流程是否结束。
- **确定性门禁** 最终决定候选能否进入可批准集合，审核 Agent 的“通过”不能覆盖门禁。

第一版每份简报最多 3 个并行研究子任务，每个子任务使用相同的搜索结果数和页面读取数上限；审核后最多把明确的证据缺口退回原研究 Agent 一次。这里的限制是产品运行安全边界，不是开发过程的时间限制。

不选择“主管 Agent 把其他 Agent 当 Tool 并自由循环”的纯 Supervisor 方案，因为本任务顺序已知，自由路由会增加成本和难以解释的重复调用。也不选择 Peer 辩论，因为来源支持关系不是靠讨论投票决定的。固定工作流仍属于多 Agent：多个模型执行单元拥有不同职责、工具和隔离上下文，但流程控制权留在代码中。

### 4. 单 Agent 基线复用相同外围能力

`PROJECT_SINGLE` 使用一个 Agent 完成检索计划、页面读取、事实提取和候选整理；它与多 Agent 使用相同简报、模型参数、搜索/读取 Tool、调用预算上限和输出 Schema。确定性门禁发现结构问题时允许同一 Agent 修订一次，不增加独立审核角色。

这组比较回答“在当前模型和搜索工具不变时，独立规划/研究/审核上下文是否有收益”。Codex 两个执行臂则回答“实际使用哪种建库方式产出更好”，不能用于单独证明多 Agent 架构因果关系。

备选方案是只比较项目多 Agent 与 Codex 直接执行。它实现更快，但模型、搜索工具和运行时三项同时变化，即使结果不同也无法知道原因，因此拒绝采用。

### 5. 公网访问先做 Spike，再确定唯一实现

首选实现使用一个轻量搜索库取得标题、摘要和 URL，再由现有 `httpx` 独立读取正文；搜索摘要只帮助发现页面，不作为最终证据。Spike 只验证以下能力：

1. 中文和英文查询能返回可访问的公开结果。
2. 至少一个官方产品页、一个公开活动规则页和一个公开客群方法页能取得正文。
3. 超时、拒绝访问、无正文和跳转失败能被区分。

页面读取只允许 HTTP(S)，每次请求和每次跳转都校验目标为公网地址，限制跳转次数、响应大小、文本内容类型和超时时间；拒绝本机、私有、链路本地、保留地址及带 URL 凭据的目标。只抽取标题、正文文本和支持结论的短摘录，不保存 HTML 全文。外部正文使用明确的不可信数据边界传给模型，且研究 Agent 没有文件、Shell、业务 API 或密钥读取 Tool，因此页面中的提示注入无法获得额外能力。

如果无密钥搜索在当前网络不稳定，第一版不会继续增加多个搜索 Adapter。流程降级为简报显式提供 URL，由相同读取、提取和审核链路运行，并把自动发现标为未验证。付费搜索 API或搜索 MCP 只有在本次证据显示搜索是稳定瓶颈后再单独立项。

### 6. 结构化输出与运行轨迹是 Agent 之间的唯一接口

各角色使用 Pydantic Schema 作为最终输出，不通过大段自由文本互传。供应商不支持原生结构化输出时，使用 LangChain 的 Tool strategy；解析失败属于模型阶段失败，不用正则修补成看似有效的数据。

每个阶段记录：角色、开始/结束时间、终态、模型调用次数、Tool 调用次数、可获得的 Token、输入简报或任务 ID、输出候选 ID和错误类别。轨迹不保存模型隐藏推理、网页全文、访问令牌或完整业务数据。项目现有通用 Agent 看板不接收这些离线运行，避免把实验调用混入线上指标。

### 7. 门禁、人工批准和正式知识库保持三层状态

```text
模型候选 -> EVIDENCE_GATE_PASSED -> HUMAN_APPROVED -> IMPORT_DRAFT
               |                         |                  |
          机器可检查完整性          人工判断业务价值      仍未激活/未写库
```

门禁逐条检查来源是否实际读取、引用 ID是否存在、结论状态、重复候选、数量边界和禁止业务字段。`PARTIALLY_SUPPORTED`、`CONFLICTING`、`UNSUPPORTED` 均可保留供复盘，但不能进入批准清单候选。

人工批准文件只记录实验 ID、批准人标识、批准时间和候选 ID。导出器再次加载原运行结果并复验门禁，不信任批准文件携带的候选正文。导出结果是 Markdown/JSON 草稿；若后续要加入现有 RAG，仍需按 `KnowledgeCatalog` 规则补项目内来源、状态、版本和实时边界，并通过单独变更激活。奖品或客群模板若要成为业务配置，也必须走 Java 后端的数据建模、权限和审核流程。

### 8. 四臂实验使用三份冻结简报和两层评价

正式实验冻结三份简报：

| 简报 | 目标 | 明确不产出 |
| --- | --- | --- |
| 奖品候选 | 研究 5 个适合积分兑换的公开商品候选 | 库存、内部成本、兑换积分 |
| 活动机制 | 研究 5 个有公开依据的积分/会员活动机制 | 本项目转化率、收益和发布草案 |
| 客群模板 | 研究 5 个能由内部事件数据计算的客群规则模板 | 真实人数、个人数据和预测效果 |

第一层由代码统计契约完整性和证据指标；第二层生成匿名 `A/B/C/D` 材料，由人工按项目相关性、事实支持、适配可用性和冲突处理分别评分并写理由。匿名标签顺序由实验配置生成，映射单独保存，评分锁定后再揭盲。

最终报告分两段：

1. `PROJECT_SINGLE` 对 `PROJECT_MULTI`：协作架构比较。
2. 项目方案对 `CODEX_DIRECT`、`CODEX_DELEGATED`：实际产出比较，明确存在模型与工具差异。

只有多 Agent 无新增门禁失败、三份简报至少赢两份，且总计比项目单 Agent 多两条可人工批准候选，报告才建议保留。这个规则只决定工程建议，不自动删除代码或批准内容；延迟和 Token 作为代价完整展示。若未达标，实施阶段在最终合并前移除多 Agent 运行入口，保留研究数据、单 Agent 工具和失败结论。

### 9. 本次不引入高级 RAG 或通用设计模式框架

这次解决的是“离线资料从哪里来、是否可信”，不是“在线检索怎么召回”。候选未获人工批准前不建向量索引，因此混合检索、重排、复杂 Query Rewrite 和分库分索引不进入本变更。等真实新增文档进入受控目录并使现有冻结检索集出现稳定失败，再按现有路线图单独 A/B。

代码只保留自然形成的边界：结构化模型、受限公网客户端、工作流、门禁和评估器。不会创建通用 `BaseAgent`、角色注册中心、消息总线、Capability 平台或为未来业务预留空 Adapter。

## Risks / Trade-offs

- [搜索结果随时间和地区变化，四臂无法获得完全相同的网页集合] -> 项目内部两臂共享同一搜索实现和预算；所有来源带获取时间；跨 Codex 的结果只解释为实际效果，必要时再用同一 URL 集做补充实验。
- [无密钥搜索或目标网站可能限流、拒绝访问] -> 先做小型 Spike，失败时显式结束或使用简报提供 URL，不以本地数据冒充联网结果。
- [审核 Agent 仍可能错误判断证据支持] -> 审核结论只是一层标注；确定性门禁检查引用完整性，最终晋级依赖人工批准。
- [多 Agent 增加模型调用、延迟和调试成本] -> 限制角色、并行任务和一次修订；与单 Agent 同任务对照，未达到预设收益就移除多 Agent 入口。
- [公开价格会变化，商品页可能下架] -> 保存获取时间和价格口径，只把它当候选研究事实；采购成本和实际活动预算始终由内部数据确认。
- [短摘录可能不足以表达复杂上下文] -> 允许一条结论引用多个来源和多个短摘录；无法完整支持时标记部分支持，不扩大保存网页正文。
- [盲评仍可能从文风猜出执行方式] -> 统一结构化渲染和字段顺序，人工评分以结论与证据为主；报告保留这一残余偏差。
- [研究代码与现有未提交 MCP 改动并行存在] -> 本变更只触碰 `app/research`、`research-data`、对应测试和文档；提交前按路径暂存并检查 diff，不纳入 MCP 文件。

## Migration Plan

1. 完成公网搜索与三个页面类型的 Spike；若失败，先记录失败并转显式 URL 模式，不继续宣称端到端自动研究可用。
2. 落地研究数据模型、公网安全边界、门禁和 CLI，再完成项目单 Agent 基线。
3. 在相同外围能力上增加规划、并行研究与审核 Agent，先跑一份 `PILOT` 简报并冻结正式配置。
4. 分别生成 Codex 直接、Codex 显式委派、项目单 Agent 和项目多 Agent 的三份正式结果，完成盲评、揭盲与比较报告。
5. 根据预设规则决定保留多 Agent、保留单 Agent或标记证据不足；清理未被证据支持的候选实现。
6. 人工批准少量候选并验证草稿导出，更新设计文档、路线图和任务日记。正式 RAG 或业务数据导入另开变更。

回滚只需停止使用研究 CLI并移除独立研究模块及候选目录，不需要迁移数据库、回滚 Web API或重建现有 Chroma 索引。已经人工批准的研究报告可作为文档证据保留，但不能因此继续保留未证明有价值的多 Agent 运行代码。

## Open Questions

- 当前网络下哪些官方商品页对无浏览器 HTTP 客户端可读，将由第一项 Spike 给出事实，不改变显式 URL 降级方案。
- Codex 当前界面是否暴露精确 Token 与价格，将在运行报告中按“已知/未知”记录，不影响内容评分。
