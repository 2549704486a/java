## Context

参见 [proposal.md](proposal.md) 的问题与事实依据。当前 `/health` 同时承担存活信号和诊断快照，却会经由 `stats()` 扫描 Redis 或聚合查询 MySQL；`start-local.ps1` 只等待 TCP 端口。Java 服务已经引入 Actuator，Agent 的外部事实访问统一经过 Java API，但确认状态、长期记忆和本地知识索引仍由 Python 进程直接持有或连接。

## Goals / Non-Goals

**Goals:**

- 用两个稳定契约分别表达“进程活着”和“可以接收流量”。
- 探测实际启用的依赖，不因未启用的技术组件误报故障。
- 保持探针只读、短时、有界，并避免泄露配置和异常细节。
- 让本地启动流程复用服务自身的就绪判断，而不是另写一套判断逻辑。

**Non-Goals:**

- 不在本次设计中引入统一可观测平台、探针缓存、后台巡检线程或新的依赖注入框架。
- 不探测 Java 内部的 MySQL、Redis、RocketMQ、Canal 细节；这些由 Java Actuator 汇总。
- 不处理正在执行请求的停机排空，优雅停机作为后续独立变更。

## Decisions

### 1. 拆分存活与就绪，不继续复用一个含糊端点

采用以下契约：

- `GET /health`：存活检查，只返回服务标识和 `UP`，不调用任何外部依赖。
- `GET /ready`：就绪检查，聚合必需组件状态；全部正常返回 `200/UP`，否则返回 `503/DOWN`。

`/health` 不再返回缓存数量、模型名、Skill 列表和存储统计。这是有意的响应契约收敛，诊断信息后续应进入指标或受控诊断入口，而不应继续挂在公开存活探针上。

**备选方案 A：维持 TCP 端口检查和现有 `/health`。** 改动最小，但端口监听无法证明依赖可用，且现有健康检查成本会随数据增长，不能解决问题。

**备选方案 B：把所有依赖检查继续塞进 `/health`。** 表面上只有一个端点，但依赖故障会让编排系统误判进程死亡并反复重启，混淆 liveness 与 readiness，因此不采用。

### 2. 按运行配置生成必需组件矩阵

就绪组件和探针来源如下：

| 组件 | 生效条件 | 低成本探针 | 就绪影响 |
| --- | --- | --- | --- |
| Java 业务服务 | 始终 | `GET /actuator/health`，使用独立短超时且不做业务重试 | 必需 |
| 兑换确认内存存储 | 配置为 `memory` | 本地实例存在 | 必需，但无网络调用 |
| 兑换确认 Redis | 配置为 `redis` | `PING` | 必需 |
| 长期记忆内存存储 | 配置为 `memory` | 本地实例存在 | 必需，但无网络调用 |
| 长期记忆 Redis | 配置为 `redis` | `PING` | 必需 |
| 长期记忆 MySQL | 配置为 `mysql` | `SELECT 1` | 必需 |
| 本地知识索引 | `RAG_ENABLED=true` | 对已加载集合执行不触发 Embedding 的轻量元数据读取 | 必需 |

LLM 和 Embedding 服务不做主动网络探测。API Key 等必要配置已经在运行时创建阶段校验；真实供应商可用性只能在请求执行时获知，主动推理探针会增加费用、限流占用和误报来源。

Java Actuator 是 Java 服务自身依赖状态的事实来源。配置中显式暴露 `health` 端点，避免依赖框架默认值；Python 不重复直连 Java 所管理的 MySQL、Redis 或 MQ。

### 3. 探针由资源所有者提供，运行时只聚合结果

Java API 客户端、确认存储、长期记忆存储和知识检索对象各自提供轻量只读探针，因为它们持有真实连接并知道当前后端类型。运行时负责：

1. 依次调用当前配置对应的探针；
2. 捕获超时和异常并转换为稳定组件状态；
3. 汇总顶层 `UP/DOWN`；
4. 记录服务端告警日志，但不把原始异常返回给调用方。

不复用 `stats()` 作为探针：业务数量统计与连通性是不同问题，前者可能扫描数据且失败语义不稳定。

**备选方案：在 HTTP 路由中直接识别具体存储类型并访问底层客户端。** 文件更少，但会让路由了解 Redis、MySQL 和 Chroma 细节，后端切换时容易产生分支漂移，因此不采用。

### 4. 首版同步执行少量有界探针

首版不增加线程池、缓存或后台巡检。每个外部探针使用独立的短超时，整体只包含 Java、最多两个状态存储和一个本地索引读取。实现时记录各组件耗时，若未来部署平台的高频检查造成可测量压力，再单独引入短 TTL 缓存或并行探测。

这是对复杂度和最坏延迟的取舍：依赖连续超时时 `/ready` 可能比 `/health` 慢，但不会阻塞存活判定，也不会影响普通业务端点的契约。

### 5. 健康端点公开但最小化响应

两个端点保持无需登录，便于启动脚本和未来容器探针调用。响应只暴露稳定服务名、顶层状态、组件名、组件状态和非敏感错误类别；连接地址、用户名、令牌、模型密钥和异常堆栈只允许出现在经过脱敏的服务端日志中。

健康检查是只读操作，不涉及业务幂等键和审计表。失败状态通过结构化日志记录即可，不为每次成功探针写业务审计记录。

### 6. 本地启动脚本等待服务自己的事实信号

新增通用 HTTP 等待函数：

- Java 启动后等待 `http://127.0.0.1:8088/actuator/health` 返回成功状态；
- Agent 启动后等待其实际配置端口上的 `/ready` 返回成功状态；
- 轮询只在超时时输出明确错误，正常等待不刷屏。

TCP 检查仍可用于 Redis、RocketMQ、Canal 等没有统一 HTTP 运维端点的本地中间件，但不再作为 Java 和 Agent 已可服务的最终证据。

## Risks / Trade-offs

- **[兼容性]** `/health` 的诊断字段被移除，依赖旧响应的调用方会受影响。→ 当前仓库未发现该响应的消费者；实现前保留显式变更说明，并在需要时把诊断能力迁移到后续受控端点或指标。
- **[重复探测]** Java Actuator 和 Python 状态存储可能都访问同一台 MySQL/Redis。→ 两者验证的是不同进程的真实连接路径，使用 `PING`/`SELECT 1` 控制成本。
- **[级联超时]** 多个依赖同时故障时，同步探测会增加 `/ready` 延迟。→ 为每个探针设置短超时；若实测仍不可接受，再基于证据引入并行或缓存。
- **[模型服务盲区]** 就绪为 `UP` 时，外部模型供应商仍可能临时不可用。→ 明确这是有意边界；模型故障继续由请求级超时、错误语义和日志处理。
- **[Actuator 口径]** Java 健康状态受其 HealthIndicator 集合影响。→ Python 只信任 Java 的顶层状态，具体 Java 依赖治理留在 Java 服务内部。

## Migration Plan

1. 先实现各资源的轻量探针和运行时聚合，不改变启动脚本。
2. 增加 `/ready`，并将 `/health` 收敛为纯存活响应。
3. 使用定向检查验证存活不访问依赖、就绪成功和单依赖失败三类场景。
4. 显式配置 Java Actuator health 暴露，再把本地启动脚本切换到 HTTP 判定。
5. 若需回滚，先将启动脚本恢复为端口等待，再移除 `/ready`；业务接口和数据无需迁移。
