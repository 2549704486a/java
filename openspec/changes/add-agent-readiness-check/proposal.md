## Why

当前 Agent 的 `/health` 固定返回 `UP`，同时调用可能扫描 Redis 键或查询 MySQL 的业务统计；本地启动脚本则只判断端口是否监听。系统因此无法稳定地区分“进程已经启动”和“依赖已就绪、可以接收用户流量”，也可能让健康探针本身随业务数据增长而变重。

P5 已将健康检查列为下一阶段的可运维性基础。本次先建立清晰、低成本的存活与就绪契约，为后续本地部署固化和运行监控提供可靠入口。

## What Changes

- **BREAKING**：将 `/health` 收敛为进程内的低成本存活判断，不再返回缓存、Skill 和业务统计字段，也不访问外部依赖。
- 新增就绪检查，按当前配置验证 Agent 接流量所需的业务服务和状态存储，并返回可判定的组件状态。
- 就绪时返回成功；任一必需依赖不可用时返回 `503`，但不在响应中暴露连接凭据或内部异常堆栈。
- 本地启动脚本从“端口已监听”升级为“HTTP 就绪检查通过”后再报告 Agent 可用。
- 将现有缓存数量、Skill 列表和业务记录统计从健康判定中移出，避免把诊断信息误当成可用性证据。

## Goals And Non-Goals

**目标**

- 让启动脚本、人工排查和未来编排平台使用同一套存活/就绪语义。
- 使用有界、低成本的探针，明确指出未就绪的组件类别。
- 保持用户侧与运营侧业务接口、旧事务消息兑换链路不变。

**非目标**

- 本次不实现优雅停机、运行指标、容器化或 CI。
- 不通过真实 LLM/Embedding 请求探测外部模型服务，避免产生费用和额外流量。
- 不把一次健康检查扩展为完整业务流程回归，也不验证 RocketMQ、Canal 等由 Java 服务负责的内部依赖。

## Evidence And Open Questions

**已确认事实**

- `AgentRuntime.health()` 的顶层状态固定为 `UP`。
- 该方法会调用确认存储和长期记忆存储的 `stats()`；Redis 实现包含键扫描，MySQL 实现包含聚合查询。
- `start-local.ps1` 当前只等待 Agent 的 TCP 端口 `8090`。
- Java 服务已包含 Spring Boot Actuator，但当前 Agent 客户端没有独立健康探针。

**待设计阶段确定**

- Redis、MySQL 等状态存储应根据实际启用的后端动态成为必需组件，而不是固定探测所有中间件。
- RAG 本地索引应只检查运行时是否成功加载，还是需要额外的无模型调用探针。

## Capabilities

### New Capabilities

- `service-health-readiness`: 定义 Agent 服务的低成本存活检查、依赖感知的就绪检查及本地启动判定契约。

### Modified Capabilities

无。

## Impact

- Agent HTTP API 的健康检查响应语义，并新增就绪检查 API。
- `AgentRuntime`、Java 业务 API 客户端及已配置状态存储的轻量探针接口。
- `start-local.ps1` 对 Java 与 Agent 服务的启动完成判定。
- 不新增第三方运行时依赖，不修改 Java 业务接口和前端用户流程。
