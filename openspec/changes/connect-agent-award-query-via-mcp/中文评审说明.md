# Agent 奖品查询接入 MCP：中文评审说明

> 这份文档用于人工阅读和方案评审。OpenSpec 参与校验的英文原文仍在 `proposal.md`、`design.md`、`specs/agent-mcp-tool-consumption/spec.md` 和 `tasks.md` 中。
>
> 中文稿不是另一套设计。后续如果方案发生变化，中文稿与英文原文必须同步修改；两者出现冲突时，应先修正文档再继续开发。

## 1. 本次到底要改什么

本次不把整个 Java 后端改造成 MCP，也不把所有 Python 业务调用改走 MCP。

第一阶段只改变一个调用入口：**用户 Agent 暴露给大模型的 `get_award_detail` Tool**。

默认模式保持现状：

```text
大模型
  -> Python 本地 get_award_detail Tool
  -> BusinessApiClient
  -> Java REST 接口
```

显式开启 MCP 实验模式后：

```text
大模型
  -> 通过 MCP 发现的 get_award_detail Tool
  -> Java /mcp
  -> AgentQueryService.getAwardDetail
```

这样可以回答一个明确的问题：**现有 Agent 能否真正发现并调用 Java MCP Tool，而不是只证明 Java MCP Server 自己能运行。**

## 2. 哪些调用仍然走 REST

以下调用即使开启 MCP 实验模式也不改变：

- 积分规划内部查询奖品详情；
- 奖品推荐内部查询奖品详情；
- 长期目标与记忆处理内部查询奖品详情；
- 受控兑换准备和确认过程中的奖品查询；
- 除 `get_award_detail` 以外的其他 Agent Tool；
- 旧事务消息兑换链路、身份校验、幂等处理和订单处理。

不能在 `BusinessApiClient.get_award_detail()` 内部直接增加 REST/MCP 分支。这个方法被多个确定性业务服务复用，如果在这里切换，会让这些内部调用也悄悄改走 MCP，超出本次实验范围。

## 3. 需要满足的行为

### 3.1 默认关闭，显式开启

- 没有配置实验开关时，Agent 与现在完全一样，继续使用 REST。
- 默认启动不依赖 Java MCP Server 是否可用。
- 只有显式选择 MCP 模式时，才初始化 MCP Client 并发现远程 Tool。

### 3.2 只允许一个远程 Tool

- Agent 只接收名称为 `get_award_detail` 的远程 Tool。
- 即使 Java MCP Server 后续暴露了其他 Tool，也不能自动进入用户 Agent。
- 远程 Tool 只能接收一个必填的正整数参数 `award_id`。
- 如果远程 Tool 多出用户 ID、操作员 ID 或其他参数，视为契约漂移，拒绝启动实验模式。

### 3.3 MCP 失败时不能偷偷回退 REST

显式开启 MCP 模式后，如果出现以下情况，Agent 必须明确报告初始化失败：

- MCP 地址无法连接；
- 初始化或发现 Tool 超时；
- 找不到 `get_award_detail`；
- Tool 参数结构与预期不一致。

此时不能自动改用 REST。否则即使页面返回了正确答案，我们也无法证明这次请求到底有没有经过 MCP。

### 3.4 业务结果不能变

MCP 返回结果仍采用现有业务 Envelope：

```json
{
  "success": true,
  "code": "SUCCESS",
  "data": {
    "awardId": 6,
    "name": "小米手环"
  },
  "message": "查询成功",
  "retryable": false
}
```

奖品不存在属于正常的业务失败：

```json
{
  "success": false,
  "code": "AWARD_NOT_FOUND",
  "data": null,
  "message": "奖品不存在",
  "retryable": false
}
```

它不能被误判成 MCP 协议错误或网络错误。

### 3.5 调用过程必须可观察

轨迹中至少记录：

- Tool 名称 `get_award_detail`；
- `transport=mcp`；
- 耗时；
- 业务结果码；
- 当前请求的 request ID。

日志不记录完整奖品响应、访问凭证或其他不必要的业务数据。

## 4. 为什么先只迁移奖品查询

`get_award_detail` 只依赖 `award_id`，不需要相信大模型传入的用户身份，也不会修改业务数据，适合作为第一条真实 Agent MCP 链路。

其他能力风险不同：

| 能力 | 暂不迁移的原因 |
| --- | --- |
| 查询用户积分 | 必须解决可信用户身份如何透传 |
| 查询兑换资格 | 与用户身份、限购和实时业务状态有关 |
| 查询用户订单 | 涉及数据隔离和越权风险 |
| 执行兑换 | 属于写操作，还涉及确认、幂等和事务消息 |
| 运营能力 | 需要操作员身份、权限和审计 |

后续可以逐个评估这些能力，但不能因为“Java 已经有 MCP Server”就一次性全部暴露给模型。

## 5. 开发前为什么要先做兼容性验证

当前 Agent 使用同步的 `agent.invoke()`。官方 LangChain MCP Adapter 通常异步发现和调用远程 Tool。

开发前先做一个隔离验证：

1. 使用当前 Python 和 LangChain 版本连接 Java `/mcp`；
2. 发现 `get_award_detail`；
3. 把远程 Tool 放入当前 Agent；
4. 使用现有 `agent.invoke()` 完成一次真实调用；
5. 检查是否出现事件循环、异步 Tool 不支持同步调用或资源无法释放的问题。

实验已经证明官方远程 Tool 只能异步执行。经人工确认，本次允许把**受影响的用户 Agent 路径**改成异步：`run_agent`、用户 `AgentRuntime.answer`、`/v1/chat` 和 CLI Agent 入口使用异步等待。运营 Agent、确定性 Python Service 和 Java REST 基线不改；也不允许在 Tool 内偷偷启动后台事件循环或逐次调用 `asyncio.run()`。

## 6. 最终如何验收

至少完成以下验证：

1. 默认配置下不启动 MCP Client，原 REST Tool 正常工作。
2. MCP 模式只向模型注册一个远程 `get_award_detail`。
3. MCP 地址不可用或 Tool 契约错误时，服务明确失败且不回退 REST。
4. 查询存在和不存在的奖品时，MCP 与 REST 的业务字段含义一致。
5. 积分规划、推荐、长期记忆和受控兑换内部仍通过 REST 查询。
6. 一次真实用户提问只产生一次远程 Tool 调用，并在轨迹中看到 `transport=mcp`。
7. 该次直接 Tool 调用没有访问 Java 的奖品详情 REST 接口。

## 7. 如何回滚

MCP 是默认关闭的实验能力。回滚时只需将 Agent 侧奖品查询传输方式改回 `rest`，不涉及数据库迁移，也不改变 Java 原有 REST 接口和旧兑换链路。

## 8. 兼容性验证结果（2026-08-31）

隔离环境使用以下版本：

```text
Python 3.11
langchain 1.3.15
langchain-mcp-adapters 0.3.2
mcp 1.29.1
```

Adapter 要求 MCP SDK 版本小于 `2.0`，因此项目虚拟环境里原有但未写入依赖清单的 `mcp 2.0.0` 不能直接作为正式依赖。

在 18088 端口单独启动启用 MCP 的 Java 实例后，验证得到：

1. Adapter 可以通过 Streamable HTTP 发现 `get_award_detail`；
2. `award_id` 输入 Schema 与 Java 定义一致；
3. 异步执行 `tool.ainvoke({"award_id": 6})` 可以取得业务 Envelope；
4. 远程 Tool 只有异步执行函数，没有同步执行函数；
5. 直接调用 `tool.invoke()` 失败；
6. 使用 Fake Model 驱动与当前项目相同的 `agent.invoke()` 也失败，错误为：

```text
NotImplementedError: StructuredTool does not support sync invocation.
```

因此，当前同步 Agent 不能直接消费官方 Adapter 返回的 MCP Tool。兼容性实验阶段没有修改生产依赖、配置、Tool 装配或 AgentRuntime。随后用户明确同意继续，并批准仅将受影响的用户 Agent 执行路径改为异步；不采用隐藏的事件循环桥接来伪装同步兼容。

## 9. 人工批准后的异步边界

本次异步化不是把整个项目改成异步框架，只涉及下面四个连续环节：

```text
FastAPI /v1/chat 或 CLI Agent 入口
  -> await AgentRuntime.answer()
  -> await run_agent()
  -> await agent.ainvoke()
  -> await 远程 get_award_detail Tool
```

同一 `user_id + session_id` 的请求仍然串行执行，但会使用适合异步代码的锁；异常和取消时必须释放锁。兑换确认等已有同步确定性逻辑会放到工作线程执行，业务代码本身不改。运营 Agent 不在这条路径内，仍按现状同步执行。
