## Why

当前用户 Agent 和运营 Agent 已能记录请求耗时与 Tool 轨迹，但这些数据主要停留在结构化日志中；离线评测结果又保存在独立 JSON 中。运营人员无法在界面中连续回答“Agent 是否可用、哪里慢、调用了哪些 Tool、失败集中在哪一步”，并且容易把接口完成率误解为回答正确率。

已确认事实：线上请求日志与离线评测数据属于不同数据源和不同口径；现有运营入口已经具备独立身份认证与权限检查；项目尚无可按时间窗口查询的 Agent 运行观测事实源。合理假设是，一个口径明确、可下钻到请求轨迹的只读看板能降低人工翻日志的成本，但它本身不能证明回答正确或带来业务收益。

## Goals

- 在现有运营工作台展示用户 Agent 与运营 Agent 的真实运行数据。
- 提供请求完成情况、端到端耗时、Token 用量和 Tool 调用情况，并支持按请求 ID 查看最小化轨迹。
- 明确区分运行完成、Tool 业务结果和回答质量，避免用技术成功率代替业务或语义正确率。
- 以最少的数据结构完成可持久化、可授权、可限时查询的第一版闭环。

## Non-Goals

- 不展示或持久化用户提问、模型回答、Tool 完整参数与返回正文。
- 不把离线评测成绩、活动收益漏斗或模拟数据合并为线上 Agent 成功率。
- 不在本次引入通用监控平台、任意 SQL 分析、在线 LLM Judge 或新的 Agent/MCP 抽象。
- 不修改 Agent 的 Prompt、Tool 选择、兑换链路和活动业务规则，也不回填历史日志。

## What Changes

- 新增最小化 Agent 请求观测记录和 Tool 调用观测记录，以 MySQL 作为看板运行数据的事实源。
- 用户 Agent 与运营 Agent 在请求结束时写入运行摘要；观测写入失败时保留原对话结果并记录告警，不反向破坏业务请求。
- 新增受 `agent:observe` 权限保护的运营只读接口，提供固定时间窗口汇总、最近请求列表和单次请求轨迹。
- 在现有 `/operator` 工作台增加 Agent 运行数据区域，展示请求数、完成率、平均/P95 端到端耗时、Token 与 Tool 指标，并对指标口径和缺失数据作可见说明。
- 默认只保留 30 天观测摘要；查询设置最大时间窗口与分页上限，避免看板查询拖累 Agent 服务。

## Capabilities

### New Capabilities

- `agent-runtime-observability`: 规定 Agent 运行观测的采集边界、指标语义、运营权限、查询接口和看板行为。

### Modified Capabilities

无。

## Impact

- `agent-service`：请求级观测上下文、持久化仓储、用户/运营请求接入、运营只读 API、配置和定向测试。
- `web-ui`：运营工作台的数据类型、API 客户端及 Agent 运行数据区域。
- MySQL：新增两张仅存运行摘要的观测表，不修改既有业务表和 Java 业务服务。
- 权限配置：新增 `agent:observe`，不复用活动管理权限。
- 运维行为：新数据仅从功能启用后开始产生；旧日志不解析、不回填。
