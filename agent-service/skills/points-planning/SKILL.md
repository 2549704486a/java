# 积分规划 Skill

## 何时使用

- 用户询问“为了兑换这个奖品应该完成哪些任务”。
- 用户询问“怎样攒够兑换这个奖品的积分”。
- 用户询问“帮我规划之前保存的目标”或“规划我的手环目标”。

用户只是查询当前积分、任务列表、奖品列表、能否兑换或还差多少积分时，直接使用对应基础 Tool，不触发本 Skill。

## 输入

- 当前登录用户 ID：由运行时绑定，不能由模型修改。
- 明确奖品规划：`award_id`，以及用户明确表达的排除或允许任务名称。
- 已保存目标规划：可选 `goal_query`，用于多个目标之间的定位。

## 执行步骤

1. 用户给出明确奖品 ID 时，调用 `plan_points_for_award`。用户的“不要分享”“只做签到”等约束直接传入任务名称参数，不要先查任务再自行过滤。
2. 用户只给出奖品名称时，先调用 `list_awards` 解析奖品；只有唯一匹配后才调用 `plan_points_for_award`，多个候选时让用户选择。
3. 用户要求规划已保存目标时，调用 `plan_points_for_saved_goal`，不要提前调用记忆、奖品或积分工具。
4. 上述两个规划 Tool 内部已经由确定性 Service 完成资格、奖品、任务查询和任务组合，不得在前后重复调用对应基础 Tool。
5. 根据返回状态回答：已满足资格时说明可以前往兑换；非积分原因阻断时复述真实原因；任务可覆盖缺口时列出任务；仍不足时明确剩余缺口。
6. 用户给出期限时在回答中保留期限；业务数据没有任务周期时，不承诺一定能在期限前完成。

## 错误与重试

- Tool 层只对 GET 超时、连接失败、`408/429/5xx` 做有限退避重试。
- 参数错误、权限错误、业务原因和响应格式错误不重试。
- 规划 Service 不叠加网络重试；任一必要查询失败即返回 `QUERY_FAILED`。
- 不把失败压缩成模糊的“请求失败”，保留稳定错误码和 `retryable` 语义。

## 安全边界

- 只调用 `/agent/query/**` 只读接口。
- 不调用 `/userAward/exchange`、`/task/finish`、`/task/reward`。
- 不直连 MySQL、Redis、RocketMQ。
- 不修改积分、库存、任务、订单或消息状态。
- 不根据模型常识补写动态业务事实。

## 输出

`plan_points_for_award` 输出 `PointsPlan`；`plan_points_for_saved_goal` 额外返回目标解析状态。最终回答应转成用户语言，不展示内部状态名。
