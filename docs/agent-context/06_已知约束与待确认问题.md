# 已知约束与待确认问题

> 这里不根据历史压测猜问题，只记录当前源码能够直接观察到的事实。修改业务前先确认这些点，避免把旧缺陷带进 Agent 工具。

## 1. 业务约束

- 幂等键和事务回查都以 `userId + awardId` 为核心，当前模型默认一个用户对一个奖品最多成功兑换一次。
- 如果未来允许同一用户购买多份，必须引入订单 ID 或活动批次维度，不能只改限购校验。
- 入口库存和积分是缓存镜像，只用于快速拒绝；Agent 不能把入口校验成功解释为兑换成功。
- 写接口目前是 GET，但 Agent 工具层应使用明确的写操作语义，并增加确认和审计。

## 2. 直接从代码发现的问题

| 问题 | 源码证据 | 可能影响 |
| --- | --- | --- |
| 用户奖品状态 SQL 缺少空格 | `UserAwardMapper.updateStatus` 将两个字符串直接拼接为 `...updateTime=#{updateTime}where...` | 运行时可能生成非法 SQL，影响消费成功和死信置失败 |
| 超卖分支缺少订单 ID | `ConsumerServiceImpl.update2` 构造的 `UserAward` 没有设置 `id`，但 Mapper 按 `id` 更新 | `isOverSell != 0` 时可能更新 0 行并回滚 |
| 积分缓存键不一致 | 业务和预热使用 `user:currency:{id}`，Canal 使用 `user_currency:{id}` | 数据库变更后业务读取的积分缓存可能未被刷新 |
| Caffeine 不接受 Canal 主动失效 | 价格、结束时间、超卖标记和用户积分存在本地 TTL | 配置变更后可能在 TTL 内读取旧值，数据库条件更新仍负责最终保护 |
| Redis 锁释放不是原子比较删除 | 本地事务先 GET/直接 DEL 或直接删除创建锁 | 锁过期并被其他线程重获时存在误删风险 |
| 事务回查不含订单 ID | `selectUnhandleOrder(userId, awardId, 0)` | 多订单模型下可能用另一条待处理记录决定当前半消息状态 |
| 批量消息只处理第一条 | `TransactionConsumer.consumeMessage` 在 `for` 循环内部直接 return | 如果未来把消费批量调大，后续消息可能未被当前回调处理 |
| INSERT binlog 不更新缓存 | `RDSBinlog.handleInsert` 为空 | 新建奖品或记录依赖预热、回源或后续 UPDATE |
| 定时任务和 Canal 都会写库存镜像 | `DataSyncService` 每 60 秒把 Redis 总库存写回 `award_config`，Canal 又同步回 Redis | 需要明确总库存的唯一事实源和避免双向同步环 |
| 源文件存在乱码 | 多处日志、注释和用户提示字符串编码异常 | 可维护性差，部分用户响应不可读 |
| Spring Boot 版本存在混用 | 父工程为 3.2.3，`spring-boot-starter` 又显式声明 3.3.2 | 依赖解析和运行行为可能不一致 |

## 3. 开始 Agent 开发前应先确认

1. 首个 Agent 是面向用户、运营，还是开发运维人员。
2. Agent 第一阶段是否只读；如果允许兑换或领奖，确认机制是什么。
3. 是否继续坚持“一名用户一个奖品只能兑换一次”。
4. Agent 查询结果是否允许最终一致，还是必须回源数据库。
5. 是否先修复上表中的状态更新 SQL、超卖分支和积分缓存键。
6. Agent 与 Java 服务通过 HTTP、MCP 还是独立适配层连接。

## 4. 不要在上下文不足时推断

- 不推断线上部署拓扑、实例规格和网络地址。
- 不推断当前 QPS、延迟或容量。
- 不推断 RocketMQ Broker 的延迟级别时长。
- 不推断某张表的线上数据与初始化 SQL 完全一致。
- 不根据历史新链路讨论 Redis 预扣或补偿。
