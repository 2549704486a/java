# Agent 接入边界

> 这一页不预先决定要开发哪一种 Agent，而是给后续方案划安全边界：哪些能力适合先做，哪些操作必须受控，什么时候才需要引入更复杂的课程技术。

> 第 1、5 节保留的是项目早期候选方向和第一阶段方案，用于理解取舍，不代表当前完成状态。当前产品能力以根目录 `PRODUCT.md` 和路线图为准。

## 1. 候选业务方向

### 积分规划与奖品兑换顾问

- 围绕用户的目标奖品查询积分、任务和奖品信息。
- 计算积分缺口，生成可执行的积分获取方案。
- 解释为什么当前不能兑换；普通订单列表和结果轮询继续由页面承担。
- 第一阶段保持只读，稳定后再评审受控兑换。

### 运营配置助手

- 查询奖品、任务和活动配置。
- 检查配置完整性并生成修改建议。
- 真正修改库存、价格、结束时间时必须转为审批式工具。

### 异常诊断助手

- 按订单 ID、用户 ID、奖品 ID 汇总数据库和缓存状态。
- 解释状态停在哪一阶段，并提供证据链接。
- 默认只诊断，不自动修复数据。

## 2. 工具分级

| 等级 | 示例 | 默认策略 |
| --- | --- | --- |
| 只读 | 查积分、查奖品、查任务、查兑换状态 | 可直接调用，但要校验身份和数据范围 |
| 低风险写 | 创建诊断工单、保存用户偏好 | 明确告知结果，提供幂等键 |
| 高风险写 | 发起兑换、领取积分、改配置 | 二次确认、权限校验、幂等、审计、失败补偿 |
| 禁止直接暴露 | 任意 SQL、任意 Redis 命令、修改消息状态 | 只能封装为固定业务工具或人工处理 |

## 3. 推荐工具契约

工具应返回稳定结构，而不是把 Mapper 或异常原样暴露给模型：

```json
{
  "success": true,
  "code": "EXCHANGE_PROCESSING",
  "data": {
    "orderId": 123,
    "status": "PROCESSING"
  },
  "message": "兑换已受理，请稍后查询",
  "retryable": true
}
```

每个写工具至少包含：

- 调用人和权限范围
- 业务参数 Schema
- 客户端请求 ID 或幂等键
- 是否需要确认
- 超时和重试边界
- 审计记录
- 可向用户展示的结果，不泄露内部堆栈和密钥

## 4. 课程技术的引入条件

- Function Calling：所有项目工具的基础，优先引入。
- Skill：当工具需要触发规则、固定流程和权限说明时引入。
- RAG：只有当 Agent 需要基于业务规则、FAQ 或操作手册回答时引入。
- Memory：只有明确要保存用户偏好或跨轮任务状态时引入，不能保存密码和敏感业务数据。
- LangGraph：出现分支、审核、重试、人工介入等确定性流程后引入。
- MCP：需要多个 Agent 客户端复用同一套项目工具时引入。
- 多 Agent：单 Agent 职责已经无法清晰约束时再引入，不作为默认方案。

## 5. 建议的第一阶段

先实现一个只读“积分规划与奖品兑换顾问”：

1. 工具提供用户积分、奖品配置、可用任务和兑换资格查询。
2. 不直接调用 `/exchange`、`/task/finish`、`/task/reward`。
3. 使用第二节约束回答格式，第三节定义工具 Schema，第十节定义积分规划 Skill。
4. 建立金标用例，验证工具选择、积分计算、越权拒绝和异常兜底。
5. 只读链路稳定后，再单独评审是否开放兑换或领奖。

## 6. 受控兑换评审结论

受控兑换现已按下列边界落地；这些约束仍是后续修改不可绕过的产品不变量：

1. 使用“准备兑换 -> 服务端生成一次性凭证 -> 用户明确确认 -> 原子消费凭证 -> 调用旧链路”的确定性状态机。
2. 对话 Memory 只帮助理解语言，不作为高风险写操作的授权依据。
3. 同一凭证最多触发一次 Java 写调用；用户、会话、奖品和有效期都必须由服务端校验。
4. POST 超时或连接中断属于提交结果未知，不自动重试，也不宣称兑换失败。
5. Agent 只返回处理中、明确拒绝或提交结果未知；当前旧接口无法区分本次刚受理和此前已在处理，最终结果仍由订单页面承担。
