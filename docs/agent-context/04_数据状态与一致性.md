# 数据、缓存与一致性

> 这一页解释同一份业务状态为什么会同时出现在 MySQL、Redis 和 Caffeine，以及每一层到底能不能作为最终判断依据。

## 1. MySQL 核心表

| 表 | 职责 | 关键约束 |
| --- | --- | --- |
| `award_config` | 奖品配置和总库存 | `awardId` 主键 |
| `award_inventory_split` | 普通奖品的库存分片 | `(splitId, awardId)` 联合主键，库存非负 |
| `user_currency` | 用户积分 | `userId` 唯一，积分非负 |
| `user_award` | 预分配记录和兑换状态 | `id` 主键，`(userId, awardId, status)` 普通索引 |
| `idempotent_table` | 消费成功的业务幂等 | `idempotent_key` 唯一 |
| `agent_exchange_request` | Agent 兑换 HTTP 请求级幂等和响应快照 | `idempotency_key` 唯一，请求指纹防止同键异参 |
| `task_config` | 任务规则 | `taskId` 主键 |
| `finish_task_record` | 用户完成和领取任务记录 | `(userId, taskId)` 唯一 |
| `add_currency_record` | 积分增加流水 | `requestId` 唯一 |

幂等键当前固定为 `userId:{userId}-awardId:{awardId}`，语义是“一个用户对一个奖品最多成功兑换一次”。

## 2. Redis 状态

| 键 | 类型 | 作用 | 数据来源 |
| --- | --- | --- | --- |
| `user_award:status:{userId}:{awardId}` | String | 兑换状态 | 本地事务、消费者、Canal |
| `award_config:inventory:{awardId}` | String | 总库存镜像，供入口快速拒绝 | 预热、Canal、定时同步 |
| `award_inventory_split:{awardId}` | Hash | 各库存分片镜像 | 预热、Canal |
| `award_config:price:{awardId}` | String | 奖品价格 | 预热、回源、Canal |
| `award_config:endTime:{awardId}` | String | 活动结束时间 | 预热、回源、Canal |
| `award_config:isOverSell:{awardId}` | String | 是否允许超卖 | 预热、回源、Canal |
| `user:currency:{userId}` | String | 用户积分镜像 | 预热、业务回源 |
| `createOrder:award:{awardId}:user:{userId}` | String | 本地事务创建锁 | 事务回调 |
| `inventoryLock:award:{awardId}:split:{hashKey}` | String | 消费分片锁 | 消费者 |
| `icr:{awardId}:{date}` | String | 分布式自增 ID 序列 | `RedisDao.nextId` |

Redis 库存只能做准入和分片选择，不能替代 MySQL 条件更新。消费者真正成功的必要条件是数据库事务提交。

## 3. Caffeine 本地缓存

| 缓存 | TTL | 说明 |
| --- | --- | --- |
| 奖品价格 | 5 分钟 | 本地读优化 |
| 活动结束时间 | 5 分钟 | 本地读优化 |
| 是否允许超卖 | 5 分钟 | 消费侧读优化 |
| 用户积分 | 1 分钟 | 入口快速拒绝，数据库仍会再次条件扣减 |
| 已兑换幂等键 | 24 小时 | 只缓存数据库已存在的正向结果 |

当前没有本地库存缓存，避免每个应用进程持有过时库存。

## 4. 缓存预热

`CacheWarmer` 在启动后按配置：

1. 从 MySQL 读取有效库存分片并写入 Redis Hash。
2. 把奖品价格、超卖标记、总库存和结束时间写入 Redis。
3. 把价格和结束时间写入 Caffeine。
4. 可选地批量预热用户积分到 Redis 和 Caffeine。

预热是冷启动初始化，不是持续一致性机制。

## 5. Canal 同步

Canal 客户端订阅 binlog，当前处理：

- `user_award` UPDATE 和 DELETE：更新或删除 Redis 兑换状态。
- `user_currency` UPDATE：更新 Redis 积分镜像。
- `award_config` UPDATE：更新库存、价格、结束时间、超卖标记。
- `award_inventory_split` UPDATE：更新分片 Hash，并根据前后值差量维护总库存镜像。

INSERT 事件当前没有缓存处理逻辑，因此新建数据主要依赖预热或业务回源。

## 6. 一致性结论

- 兑换受理一致性：RocketMQ 半消息和 `user_award(status=0)` 绑定。
- Agent 请求幂等性：Java 在调用旧链路前持久化 `Idempotency-Key`，重复请求重放响应而不再次发送消息。
- 消费幂等性：数据库唯一键承担最终保护。
- 库存正确性：`UPDATE ... inventory > 0` 防止分片扣成负数。
- 积分正确性：`UPDATE ... currency >= price` 防止积分扣成负数。
- Redis 一致性：通过业务写入、预热和 Canal 最终同步，不是强一致。
- 查询一致性：优先 Redis，未命中回源数据库，因此可能短暂看到处理中或旧值。
