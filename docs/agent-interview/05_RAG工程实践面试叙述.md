# RAG 工程实践面试叙述

> 这份材料把当前项目已经落地的 RAG 能力整理成可直接口述的面试答案。主线不是罗列 Embedding、向量库和 Top-K，而是说明为什么引入 RAG、知识与实时数据如何分工、怎样控制无依据回答，以及如何用评测证明检索和生成链路确实有效。

## 1. 项目总述

### 面试官：请介绍一下你在项目中实现的 RAG

> 我在积分规划与兑换 Agent 中实现了一套面向稳定业务规则的 RAG。它主要回答“任务完成后积分是否自动到账”“处理中是否等于兑换成功”“为什么兑换前需要二次确认”这类规则解释问题。
>
> 实现上，我没有把整个项目文件直接塞进向量库，而是先整理了 3 篇受控知识文档，明确知识版本、适用范围和源码依据。离线阶段先校验文档，再按 Markdown 标题和段落递归切分，使用 Embedding 模型生成向量并写入本地 Chroma；在线阶段由 Agent 调用只读检索 Tool，过滤低相关结果，把命中的原文和引用交给模型生成答案。
>
> 工程重点有三个：第一，RAG 只解释稳定规则，用户积分、库存和资格等实时事实仍然查询 Java Tool；第二，没有可靠命中时明确拒答，不允许模型凭记忆补业务规则；第三，检索和 Agent 分层评测，同时校验 Tool 路由、知识命中、引用、用户语言和无关问题拒答。

这段适合作为开场。面试官继续追问时，再从知识边界、索引、检索、引用和评测展开。

## 2. RAG、业务 Tool 与写操作的边界

### 面试官：哪些问题走 RAG，哪些问题走业务接口？

> 我按“事实是否会随用户和时间变化”划分数据来源。积分获得方式、任务状态含义和兑换规则相对稳定，适合放进 RAG；当前积分、库存、奖品价格、活动时间和兑换资格随时可能变化，必须调用 Java 查询 Tool；真正提交兑换则继续走服务端受控确认状态机。
>
> 例如用户问“处理中是否等于兑换成功”，Agent 应检索兑换规则并解释处理中只代表请求已进入异步流程，最终结果要查看订单。用户问“我现在有多少积分”，则只调用实时积分 Tool，不能从知识文档或历史对话中回答。若一个问题同时包含规则与实时事实，就分别调用 RAG 和业务 Tool，再组合答案。

### 可能追问

- 为什么不能把库存放入向量库：检索准确不等于数据新鲜，旧库存会形成事实错误。
- RAG 是否能替代数据库：不能，RAG 擅长从非结构化知识中找解释，不承担强一致实时查询。
- 为什么兑换写操作不做成 RAG：检索只能提供上下文，不能承担授权、幂等和状态流转。
- 判断边界的简单方法：先问“这条事实一分钟后是否可能变化”，会变化就优先走实时 Tool。

### 事实边界

当前 RAG 只覆盖积分、任务、兑换规则和 Agent 能力说明，不包含订单结果查询，也不参与旧事务消息链路的写入。

## 3. 知识源治理

### 面试官：你为什么不直接把项目文档全部向量化？

> RAG 的上限首先取决于知识原料，而不是向量库。项目目录中同时存在源码、开发记录、历史方案、压测材料和实时数据描述，如果全部导入，模型可能检索到过期甚至相互冲突的内容。
>
> 因此我先建立受控知识目录，只保留 3 类稳定知识：积分与任务规则、兑换规则与状态、Agent 使用边界。每篇 Markdown 都带有稳定知识 ID、文档版本、状态、主题、事实范围和项目内来源。只有状态为 active、来源存在且固定章节完整的文档才能进入索引。
>
> 文档加载前还会执行确定性校验，包括清单结构、重复知识 ID、目录越界、来源文件缺失和必需章节缺失。内容发生变化时提升文档版本和目录版本，由 Git 保存修改历史，再重新构建索引。

### 可能追问

- 为什么知识文档还要引用源码：便于复查规则依据，文档与实现冲突时能够回到权威来源。
- 为什么不直接让模型阅读源码：源码适合确认实现，但不一定适合面向用户解释，也会引入大量无关上下文。
- 文档版本有什么用：能够知道某个 Chunk 来自哪版知识，并支持更新后重新验证。
- 校验通过是否代表 RAG 正确：不代表，只说明知识原料满足治理契约；检索和回答仍需单独评测。

### 事实边界

当前知识库规模是 3 篇文档，不是企业级大知识库。它验证的是一套可治理、可追踪的工程流程，不能包装成大规模知识平台。

## 4. 文档切分与向量索引

### 面试官：你的文档是怎么切分和建索引的？

> 我采用两阶段切分。第一步先按 Markdown 标题拆出语义章节，避免规则标题和正文分离；第二步只对过长章节递归切分，依次尝试段落、换行、句号、分号、逗号和空格，最后才按字符截断。
>
> 当前参数是 `chunk_size=400`、`chunk_overlap=60`，3 篇文档生成 12 个 Chunk。重叠用于保留跨切片语义，但不会无限增大，否则会带来重复召回、Embedding 成本和上下文浪费。每个 Chunk 都保留知识 ID、文档版本、目录版本、标题层级、来源路径和适用主题，后续检索结果可以追踪回原文。
>
> 向量化使用阿里云 `text-embedding-v4`，索引存储使用本地持久化 Chroma。建库时先写临时集合，全部向量化成功后再替换正式集合；如果外部 Embedding 调用失败，旧正式集合仍可继续使用，避免一次失败构建破坏现有检索能力。

### 可能追问

- 为什么不是固定长度直接切：固定长度可能把标题、条件和结论拆开，命中片段缺少完整语义。
- overlap 越大越好吗：不是，过大会增加重复内容和检索噪声。
- 为什么选择 Chroma：当前知识量小且本地单实例，Chroma 部署简单、支持持久化，足以验证完整链路。
- 为什么不直接上 Elasticsearch 或专用向量数据库：当前没有规模、过滤或高可用需求支撑额外基础设施。
- Embedding 与聊天模型有什么区别：Embedding 把文本映射为便于计算相似度的向量，聊天模型负责理解工具结果并组织答案。

### 事实边界

当前索引是本地派生产物，可以通过受控文档重复构建，不提交到 Git。尚未实现启动时自动比较知识目录版本与索引版本的新鲜度门禁。

## 5. 在线检索与低相关拒答

### 面试官：一次 RAG 查询的完整流程是什么？

> 用户提出稳定规则问题后，Agent 选择 `search_business_knowledge`。检索服务把问题向量化，从 Chroma 取回 `limit * 2` 个候选，再按相关度阈值过滤、按 Chunk ID 去重，最终最多返回 `limit` 个片段。Tool 结果包含原文、相关度、文档身份、版本、来源路径和用户可读引用，模型只能依据这些片段回答。
>
> 当前阈值是 `0.35`。在最新 18 条检索用例中，相关问题最高分最低为 `0.4367`、平均为 `0.5877`、最高为 `0.7195`；无关问题最高分不超过 `0.0540`，所以当前数据上正负样本有明显间隔。这个阈值不是经验拍脑袋得出的，也不是普适值，知识和模型变化后需要重新校准。
>
> 如果所有候选都低于阈值，Tool 返回“没有可靠相关知识”。这里检索动作本身成功，但知识库没有答案；Agent 必须明确能力边界，不能根据模型常识补全项目规则。

### 可能追问

- 为什么先取 `limit * 2`：为阈值过滤和去重预留候选，避免处理后结果数量不足。
- Top-K 越大越好吗：不是，过多低价值片段会稀释证据并增加上下文长度。
- 相关度代表正确率吗：不代表，它只表示当前向量空间下的语义接近程度，还要结合知识身份和评测判断。
- 为什么无关问题不直接交给模型：对项目业务规则而言，没有受控证据就不应生成确定性结论。

### 事实边界

`0.35` 只对当前 Embedding 模型、3 篇知识文档和现有评测集有效。扩充知识库后必须重新观察正负样本分布。

## 6. 来源引用与防止无依据回答

### 面试官：如何确保答案真的来自检索结果？

> 检索 Tool 为每个片段返回形如 `[奖品兑换规则与状态 / 规则说明]` 的引用，同时保留来源路径和知识版本。System Prompt 要求稳定规则必须先检索，并根据命中原文回答。
>
> 但引用不能只依赖 Prompt。第一次 Agent 评测中有一条用例回答内容正确、知识也已进入上下文，却遗漏了引用，因此我在统一回答出口增加了确定性兜底：只读取本轮真实的知识检索 Tool 消息；模型已经引用时保持不变，完全漏引时只补排名第一的真实来源；没有调用 RAG、检索失败或无匹配时绝不追加引用。
>
> 这层逻辑不重写模型答案，也不会自己猜来源。它只解决“证据已经获得但展示遗漏”的问题，避免把后处理器变成第二个回答生成器。

### 可能追问

- 有引用是否一定没有幻觉：不一定，还要检查回答是否被命中片段支持，这属于事实一致性评测。
- 为什么不把 Top3 来源全部追加：用户通常只需要最直接依据，堆积引用会影响可读性。
- 模型编造一个引用怎么办：最终兜底只信任本轮 Tool 真实返回的来源，不从自然语言猜测来源。
- 实时 Tool 结果需要知识引用吗：不需要，实时积分和库存不是知识文档，不能伪装成 RAG 引用。

### 事实边界

当前引用能够追踪到受控 Markdown 和项目内依据，但还没有做面向终端用户的可点击引用详情页。

## 7. 面向用户的表达治理

### 面试官：检索正确后，为什么还要治理回答表达？

> 初版知识文档直接使用了后端状态和内部字段。模型忠实引用时，会把这些实现术语原样暴露给普通用户；另外，模型还可能在相邻句子后重复同一个来源。这说明检索命中不等于用户答案合格。
>
> 我从三层治理。第一层修改知识源，用“处理中”“已经兑换过”“已完成待领取”等业务语言作为主表达；第二层在 Prompt 中要求默认翻译内部状态、原因、字段和 Tool 名称，只有用户明确询问技术实现时才展开；第三层在评测中增加用户语言和引用简洁性指标，统一回答出口只做去重和漏引兜底。
>
> 例如“处理中是否等于兑换成功”的最终答案直接告诉用户：不等于，处理中只代表请求已进入异步流程，最终结果请查看订单。普通用户不需要先理解服务端状态码才能获得结论。

### 可能追问

- 为什么不只改 Prompt：模型会受知识原文影响，原料本身面向用户更稳定。
- 为什么不在后处理中统一重写：确定性后处理不擅长理解复杂语义，重写可能改变业务含义。
- 技术用户询问状态码怎么办：用户明确要求实现细节时可以解释，默认展示仍使用业务语言。

### 事实边界

当前治理覆盖评测中声明的内部术语和重复引用，不代表已经穷举所有可能的表达问题。

## 8. RAG 评测体系

### 面试官：你如何证明 RAG 是有效的？

> 我把评测拆成检索层和 Agent 层，因为只看最终回答无法判断模型是根据证据答对，还是凭参数记忆碰巧答对。
>
> 检索层有 18 条用例，覆盖兑换规则、积分任务、Agent 边界和天气、编程、旅游等无关问题，记录返回码、Top1、Hit@3、相关度和引用结构。最新结果是 `18/18`，Top1、Hit@3、无关问题拒答率和引用结构有效率都是 `100%`。
>
> Agent 层有 7 条用例，覆盖 3 类稳定规则、3 类实时事实和 1 个领域外问题。它同时检查 Tool 选择、Tool 是否执行、期望知识是否命中、最终引用、用户语言、引用简洁性和必需内容。最新结果是 `7/7`，各项检查均为 `100%`。
>
> 此外还使用 3 个全新会话做真实 HTTP 验证，3 次都产生知识检索轨迹并返回一处有效引用。原始问题、回答、Tool 轨迹、检索结果和判定会保存到 JSON，失败时可以回看直接证据。

### 可能追问

- Top1 和 Hit@3 有什么区别：Top1 看第一条排序是否正确，Hit@3 看前三条是否给模型提供了正确证据。
- 为什么不能只看 Hit@3：它可能掩盖第一条结果长期排序错误。
- 为什么要加入无关问题：只测正样本无法证明系统会拒绝错误知识。
- 为什么 Agent 层还要检查 Tool：最终文字可能正确，但模型可能走错数据源或产生多余调用。
- 这些百分比能代表生产准确率吗：不能，只能代表当前冻结用例下的回归结果。

### 事实边界

当前用例规模较小，尚未覆盖大量错别字、口语省略、知识冲突、长问题和知识扩容后的排序变化。面试中应称为“当前工程回归结果”，不能称为线上准确率。

## 9. 一个完整的排查案例

### 面试官：RAG 开发中遇到过什么问题，怎么定位的？

> 一次真实 HTTP 冒烟中，中文规则问题没有触发 RAG，模型返回了英文澄清。开始时看起来像 Prompt 路由不稳定，但我没有直接改 Prompt，而是沿请求链排查。
>
> 首先看 Agent 的 Tool 轨迹，确认本轮没有执行知识检索；再检查服务端收到的请求，发现通过 Windows PowerShell 发送的中文 JSON 已经发生编码失真，模型实际没有收到原问题。随后改用 Python `httpx` 明确按 UTF-8 发送请求，并用 3 个全新会话复验，三次都执行了知识检索并返回有效引用。
>
> 这个案例说明 Agent 问题不能只看最终回答。请求编码、Prompt 路由、检索、Tool 执行和生成出口属于不同环节，应先用轨迹确定故障层，再修改对应组件，否则很容易用 Prompt 掩盖客户端问题。

### 可能追问

- 为什么使用全新会话复验：避免历史消息影响本轮路由判断。
- 如何证明不是向量检索故障：异常请求根本没有进入检索 Tool；修正编码后同一索引稳定命中。
- 为什么不直接增加 Prompt 强调：根因在请求体，改 Prompt 不能保证客户端传入正确问题。

## 10. 技术选型与克制

### 面试官：为什么没有使用混合检索、重排或更复杂的 RAG 链？

> 我根据问题和证据决定是否增加组件，而不是为了覆盖技术名词。当前只有 3 篇受控文档和 12 个 Chunk，正式评测中 Top1、Hit@3 和拒答率都达到当前验收标准，没有证据表明排序需要重排，也没有大量专有编号或关键词问题要求混合检索。
>
> 因此当前保留“Agent 选择只读检索 Tool”的简单结构，没有强行引入复杂链式编排、关键词检索或重排模型。后续只有在评测暴露明确问题时再升级：专有名词召回差时考虑混合检索，Top-K 有正确结果但排序不稳时考虑重排，复杂问题需要拆解时再考虑问题改写。

### 可能追问

- 技术越多是否效果越好：不一定，每增加一个组件都会带来延迟、成本、配置和评测复杂度。
- 什么时候升级向量数据库：当数据规模、并发、元数据过滤、高可用或运维需求超过本地 Chroma 能力时。
- 当前最值得补的能力：索引新鲜度门禁，以及知识扩容后的更大规模回归集。

### 事实边界

混合检索、重排和复杂链式编排属于后续候选方案，当前项目没有实现，面试时不能描述成已有能力。

## 11. 一条统一的工程主线

如果面试官没有指定细节，可以把全部实践收束成下面这段：

> 我实现 RAG 时先划清知识和实时事实的边界，只把稳定业务规则纳入受控知识库，动态积分、库存和资格继续走业务 Tool。离线阶段对知识来源、版本和结构做校验，再按标题和段落切分，生成带完整来源元数据的向量索引；在线阶段通过只读 Tool 检索，使用阈值和去重控制候选，没有可靠证据就拒答。生成阶段要求保留真实引用，并在统一出口对漏引和重复引用做有限兜底。最后把检索和 Agent 分层评测，用 Top1、Hit@3、无关问题拒答、Tool 路由、引用和用户语言等指标验证整条链路。对我来说，RAG 的工程价值不只是“让模型查文档”，而是让业务知识可治理、回答有依据、失败可拒绝、结果可回归。
