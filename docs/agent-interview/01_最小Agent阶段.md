# 最小 Agent 阶段

> 本阶段的重点不是堆叠 RAG、记忆或多 Agent，而是先证明模型能够在明确边界内调用真实业务能力，并让关键业务计算保持可验证。

## 1. 为什么没有把所有接口都包装成 Agent

兑换结果轮询、订单列表等流程用普通页面更直接。第一版只选择“目标奖品 -> 查询资格 -> 计算积分缺口 -> 组合任务方案”这个需要多步理解和编排的问题。

可以这样回答：

> 我先判断问题是否真的需要 Agent。固定流程继续用页面和普通接口，Agent 负责用户目标不明确、需要组合多个业务事实并生成个性化方案的部分，避免为了使用 Agent 而改造所有功能。

## 2. Tool 和 Skill 如何分层

- Tool 是最小查询动作，例如查询积分、任务、奖品和兑换资格。
- Skill 是带业务上下文的组合能力，负责停止条件、工具顺序和积分方案计算。
- 模型负责识别意图、选择能力和解释结果，不直接计算关键积分，也不访问数据库。

对应证据：`agent-service/app/tools.py`、`agent-service/app/services/points_planning.py`。

## 3. 如何保证动态事实可信

积分、库存、任务状态和兑换状态只能来自 Java `/agent/query/**` 接口。接口统一返回 `success`、稳定 `code`、结构化 `data`、`message` 和 `retryable`，Agent 根据机器码分支，不解析模糊文案。

异常或字段不完整时返回 `QUERY_FAILED`，不让模型补全数据。离线测试已经覆盖畸形业务响应。

## 4. 为什么第一版只读

兑换和领奖属于有副作用操作，需要认证上下文、明确确认、幂等和审计。第一版先关闭写工具，只验证查询和规划闭环，减少误调用风险。后续即使开放兑换，也只会接入原有事务消息旧链路，而不是让模型直连数据库或中间件。

## 5. 重试为什么不全部交给 Agent

Tool 层只对幂等 GET 的超时、连接失败和部分瞬时 HTTP 错误做有限退避重试。业务条件、参数错误和响应格式错误不重试；Skill 层也不重复叠加网络重试，避免形成重试放大。

## 6. 当前验证证据

- 6 个 Function Calling 工具成功生成参数 Schema。
- Agent 成功构建为 LangGraph `CompiledStateGraph`。
- Python 8 个离线测试通过。
- Java `AgentQueryServiceTest` 和 Maven 打包通过。
- Java 服务不可达时返回明确失败，不生成虚假积分方案。

当前尚未进行真实模型端到端评测，因此不能声称工具选择准确率或自然语言回答质量已经达到生产标准。
