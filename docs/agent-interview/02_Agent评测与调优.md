# Agent 评测与调优

> 只记录已经由代码和评测结果证明的工程过程，不把 15 条用例包装成生产级稳定性证明。

## 面试场景

**问题：你如何评测和调优这个 Agent？**

第一版运行成功后，我没有只检查最终回答，而是建立了 15 个固定业务场景和 2 个真实集成用例。Runner 同时记录模型的 Tool 调用、结构化参数、Fixture 后端路径、最终回答和 Token，避免回答碰巧正确却掩盖工具误调。

原始基线严格通过 5/15，但必要回答内容已经达到 15/15。分析轨迹发现主要问题不是 Skill 计算错误，而是模型过度调用基础 Tool：15 条用例共调用 33 次 Tool，并且在工具失败后继续查询其他信息。

我保持模型、Tool 和 Skill 不变，只在 System Prompt 中加入最小工具决策表、失败立即停止、越权请求零 Tool 拒绝和失败原因禁止猜测。最终固定场景达到 15/15，真实集成达到 2/2，Tool 调用降至 12 次。

人工复核还发现过“用户不存在就猜测登录异常”的软幻觉，以及关键词规则把“格式异常”误判为不包含“数据异常”的假阴性。因此最终保留原始结果，并通过正反例和离线重评分修正规则，而不是反复调用模型直到出现满意结果。

## 工程认识

- Agent 评测不能只看最终文字，还要检查 Tool、参数和业务执行路径。
- 回答正确不代表调用过程合理；过度调用会增加延迟、Token 和故障面。
- 自动评测也会犯错，关键词检查必须配合人工代表性复核。
- Prompt 调优应控制变量，并保留调优前后的原始证据。
- 当前结果只是最小基线，样本扩充、重复运行和更多安全用例仍是后续工作。
