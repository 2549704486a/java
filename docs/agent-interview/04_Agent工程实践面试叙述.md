# Agent 工程实践面试叙述

> 这份材料把当前已经实现的 Agent 能力整理成可直接口述的面试答案。主线不是罗列 LangChain、Pydantic、FastAPI，而是说明业务问题、设计取舍、代码落地和验证证据。本文不包含基础设施闭环排查。

## 1. 项目总述

### 面试官：请介绍一下你做的 Agent

> 我在原有积分激励和奖品兑换系统上开发了一个积分规划与兑换 Agent。它能够查询用户实时积分、任务和奖品，帮助用户计算积分缺口、规划任务组合、推荐当前可兑换奖品，并通过二次确认受控地接入原有 RocketMQ 事务消息兑换链路。
>
> 这个项目的重点不是简单接入大模型，而是处理模型能力和确定性业务之间的边界。我把自然语言理解和能力选择交给模型，把积分计算、资格判断、确认状态机和写操作控制放在确定性代码中。同时补充了数据契约、会话隔离、调用轨迹、固定评测集和前端确认页面，让它从一个命令行 Demo 逐步变成可验证的常驻服务。

这段适合作为开场，后续根据面试官追问展开下面的具体主题。

## 2. Agent 与普通业务功能的边界

### 面试官：为什么这里需要 Agent，而不是普通接口？

> 我没有把所有业务接口都包装成 Agent。订单列表、兑换结果查询和固定页面跳转都属于确定流程，普通接口更直接、更稳定。Agent 主要处理用户表达不完整、需要组合多个实时事实并给出个性化建议的场景，例如“我想换手环，还差多少积分，应该完成哪些任务”。
>
> 在这个请求中，模型适合识别用户目标、奖品名称和排除偏好；但是实时积分、库存和任务状态必须来自 Java 接口，任务组合也由确定性算法计算。这样既利用了模型理解自然语言的能力，又没有把关键业务事实和计算交给概率模型。

### 可能追问

- 为什么兑换结果查询不做成 Agent：流程固定，页面跳转或订单查询体验更直接。
- 哪些内容交给模型：意图识别、参数提取、能力选择和自然语言解释。
- 哪些内容不能交给模型：动态事实、积分计算、资格判断、授权和最终写入。

### 事实边界

当前项目不是“万能业务助手”，而是围绕积分规划、奖品推荐和受控兑换构建的垂直 Agent。

## 3. Tool 与 Skill 的分层

### 面试官：你的 Tool 和 Skill 是怎么设计的？

> 我把 Tool 定义为最小、可复用的业务动作，例如查询积分、任务、奖品和兑换资格。Skill 则是一项有完整业务目标的组合能力，例如积分规划 Skill 会依次检查兑换资格、判断阻断原因、查询可完成任务，再通过确定性算法选择任务组合。
>
> 模型不需要理解所有 Java 接口细节，只需要根据 Tool 描述和参数 Schema 选择能力。复杂业务顺序、停止条件和计算规则收敛在 Skill 代码中。这样可以减少模型重复调用基础 Tool，也让核心规则能够单元测试。
>
> Skill 的说明保存在 `SKILL.md` 中。我使用 YAML Front Matter 声明名称、描述、触发条件和版本，Markdown 正文记录执行步骤、错误处理和安全边界。运行时扫描并校验这些文件，计算 SHA-256，用于记录本次执行对应的 Skill 版本。

### 可能追问

- Tool 与普通函数的区别：Tool 具有模型可见的名称、描述和参数 Schema，可以被 Function Calling 选择。
- Skill 是否只是 Prompt：不是。当前 Skill 同时包含声明文件和确定性 Python 编排代码。
- 为什么不把全部步骤写进 System Prompt：Prompt 难以保证严格顺序和计算正确性，也不便单元测试和版本追踪。

### 事实边界

当前实现是单 Agent 加多个 Tool/Skill，不是多 Agent 协作系统。

## 4. 受控兑换项目故事

### 面试官：Agent 如何安全执行兑换？

> 兑换属于高风险写操作，我没有让模型在识别到“兑换”后直接调用写接口，而是设计了准备和确认两个回合。
>
> 第一回合，模型只能调用 `prepare_exchange`。Skill 会实时查询资格和奖品信息，在服务端创建一条带 TTL 的确认记录，记录用户、会话、奖品、积分摘要和一次性凭证。返回给模型和浏览器的只有奖品名称、当前积分、消耗积分、剩余积分和过期时间，真正的 `confirmationId` 会在进入模型上下文之前移除。
>
> 第二回合，用户点击确认按钮或明确回复“确认兑换”。如果当前会话存在待确认记录，`AgentRuntime` 会通过保守白名单识别确认意图，绕过模型，直接进入确定性确认流程。`ConfirmationStore` 在同一把锁内检查用户、会话、状态和有效期，并把状态从 `PREPARED` 原子更新为 `EXECUTING`。只有抢到执行权的请求才能调用 Java 写接口，所以重复确认或并发确认最多提交一次。
>
> Java 侧没有复制兑换逻辑，而是通过一个 Agent 适配接口复用原有 RocketMQ 事务消息链路。接口返回 `EXCHANGE_PROCESSING` 只表示已经受理，Agent 不会把它描述成最终成功。如果 POST 超时或断连，系统返回 `SUBMISSION_UNKNOWN`，要求用户先查询订单，不能自动重试非幂等写请求。

### 为什么从模型 Tool 改成服务端确定性确认

> 早期方案让模型拿着一次性凭证调用确认 Tool，但这会让凭证进入模型上下文，也依赖模型准确判断“确认”语义。后面我把确认动作收回运行时：模型负责生成摘要，服务端负责授权和执行。这体现了一个原则，模型可以参与高风险流程，但不应该成为最终的权限判定者。

### 可能追问

- 如何防止同一凭证重复使用：锁内完成状态检查和 `PREPARED -> EXECUTING` 更新。
- 如何防止跨用户或跨会话使用：确认记录同时绑定 `user_id` 与内部 `thread_id`。
- 为什么确认和准备不能同一轮完成：创建记录的请求 ID 与确认请求 ID 必须不同。
- 为什么 POST 不自动重试：超时无法判断服务端是否已经受理，重试可能产生重复写入。
- 页面为什么拿不到凭证：浏览器只需要展示摘要和发送明确确认，不需要持有服务端授权值。

### 事实边界

- 确认存储目前是单进程内存状态，服务重启会失效，多实例前需要迁移到 Redis 或数据库。
- `Idempotency-Key` 已随请求传给 Java，但 Java 目前只校验格式，尚未完成请求级持久化去重。
- 当前只复用旧事务消息链路，没有接入 Redis 预扣新链路。

## 5. Pydantic 数据契约

### 面试官：为什么 Agent 层还需要 Pydantic 校验？

> Java 返回 JSON 并不等于 Python 已经获得可信业务对象。Agent 后续会根据积分、资格原因码和任务状态做分支，如果字段缺失、类型错误或状态值超出约定，直接使用字典容易把异常数据继续传给模型。
>
> 因此我用 Pydantic 定义 Java 响应和 Tool 输入契约。`Field(alias=...)` 适配 Java 的驼峰字段，`Literal` 限制状态取值，`model_validate()` 把外部 JSON 转成经过校验的对象。校验失败时 Skill 返回稳定的格式异常，而不是让模型猜测缺失字段。输出时再通过 `model_dump()` 转成稳定结构。

### 可能追问

- Schema 和契约是否相同：Schema 是契约的结构化部分，完整契约还包括状态语义、错误码和行为约束。
- 为什么不能只用 `dict`：字典不能自动约束字段存在性、类型和枚举范围。
- Pydantic 是否保证业务正确：不能，它保证结构符合约定；业务资格仍由 Java 和 Skill 规则判断。

## 6. Agent 评测与 Prompt 调优

### 面试官：你如何判断 Agent 做得好不好？

> 我没有只看最终回答，而是建立固定 Fixture 用例和真实集成用例，同时检查模型选择的 Tool、结构化参数、代码实际执行轨迹、后端调用路径、必要回答内容和安全约束。
>
> 第一版固定场景严格通过率只有 5/15，但回答内容其实已经达到 15/15。轨迹显示主要问题是模型过度调用 Tool，以及工具失败后继续查询。我保持模型和业务代码不变，只调整 System Prompt 中的最小工具决策、失败立即停止和越权请求零 Tool 拒绝规则，回归后固定集达到 15/15，Tool 调用从 33 次降到 12 次。
>
> 后续扩展到 25 个场景后，当前完整回归是 23/25，安全检查是 25/25。剩余问题分别属于拒绝措辞评分和多调用一次资格查询。我保留失败结果，没有反复调用模型碰出满分。对于“格式异常”和“数据异常”这类关键词假阴性，则通过人工复核和离线重评分修正规则。

### 可能追问

- 为什么最终回答正确还要判失败：回答可能碰巧正确，但过程存在错误 Tool、参数或多余调用。
- 什么是 Fixture：提供可重复的模拟业务数据，让评测不受实时数据库变化影响。
- 为什么需要人工复核：自动关键词规则也会产生假阳性和假阴性。
- 如何避免 Prompt 针对特例膨胀：优先总结可泛化的决策规则，不把每条失败原句都塞进 System Prompt。

### 事实边界

25 个用例只能作为当前版本的工程回归集，不能包装成生产流量准确率。

## 7. Tool 调用链可观测性

### 面试官：Agent 回答错误或延迟高时怎么排查？

> 我为每个 HTTP 请求生成或透传 `X-Request-ID`，并把它带到 Agent 执行和 Java 请求。每个 Tool/Skill 都通过统一包装器记录结构化轨迹，包括执行顺序、精简参数、是否完成、业务结果码和耗时。
>
> 评测同时保存模型声明的 Tool Call、代码实际执行轨迹和 Fixture 后端调用路径。这样可以区分模型选错 Tool、Tool 本身执行失败、Skill 内部路径错误以及下游接口异常。总耗时也可以继续拆成模型、Skill 和 Java 请求，而不是看到 Agent 慢就直接归因于数据库。
>
> 轨迹遵循最小化原则，不保存 API Key、完整确认凭证、用户问题全文和完整业务响应，只保留定位问题需要的摘要。

### 可能追问

- 为什么模型 Tool Call 和执行轨迹要分开：模型声明调用不代表代码一定执行成功。
- Request ID 有什么价值：把入口日志、Agent 轨迹和下游 Java 日志关联成同一次请求。
- Trace 和普通日志的区别：Trace 是结构化、请求级的执行证据，普通日志可能只是零散事件文本。

## 8. 短期记忆与会话隔离

### 面试官：你的 Agent 如何支持多轮对话？

> 我使用 LangGraph 的 `InMemorySaver` 保存短期消息，并通过 `thread_id` 读取同一会话历史。内部 Thread ID 不是客户端直接传来的 Session ID，而是 `user:{user_id}:session:{session_id}`，因此不同用户即使使用相同 Session ID，也不会读取彼此的上下文。
>
> 为了避免同一会话并发请求造成消息顺序错乱，我给每个会话增加串行锁。为了避免会话持续增长占满内存，又增加了有界 LRU：超过容量后淘汰最久未使用且当前没有执行请求的会话，同时删除对应 Checkpoint。

### 可能追问

- 用户 ID、会话 ID、Thread ID 的区别：用户 ID 表示身份，Session ID 表示客户端会话，Thread ID 是运行时隔离记忆的内部主键。
- 为什么需要淘汰：进程内 Checkpointer 会随新会话持续增长。
- 是否支持长期记忆：目前不支持，只保存进程内短期会话。

### 事实边界

当前没有 Token 窗口、自动摘要和跨实例共享记忆，不能声称已经实现完整记忆治理。

## 9. Agent 服务化与前端落地

### 面试官：你如何把 Agent 从 Demo 变成可使用的服务？

> 第一版 Agent 是命令行程序，每次运行都要重新初始化模型客户端和执行图。后面我使用 FastAPI 将它改造成常驻服务，提供 `/health`、`/v1/chat` 和页面聚合接口。请求在进入运行时前由 Pydantic 校验，异常在服务端记录堆栈，对外返回稳定错误码和脱敏信息。
>
> 运行时复用 HTTPX 连接池，并按用户缓存绑定身份的 Agent 执行对象；缓存设置容量和 LRU，避免用户持续增加导致内存无界增长。前端使用 React 和 TypeScript 展示奖品、实时积分、Agent 对话和受控兑换确认卡片，生产构建由 FastAPI 同源托管，减少额外的跨域配置。

### 可能追问

- HTTP 连接池的作用：复用到 Java 服务的 TCP 连接，减少重复建连开销。
- 为什么 Agent 按用户缓存：Tool 的用户身份由运行时闭包绑定，避免模型自行填写其他用户 ID。
- 为什么还需要缓存上限：常驻服务不能让用户和会话对象无限增长。

### 事实边界

当前是本地单实例服务，尚未完成登录认证、网关身份注入、分布式会话和生产部署。

## 10. 一条统一的工程主线

如果面试官没有指定细节，可以把全部实践收束成下面这段：

> 我的实现思路是先划清模型和确定性业务的边界，再把 Java 能力封装成具有稳定 Schema 的 Tool，把多步规则收敛成可测试的 Skill。对于兑换这类写操作，增加服务端二次确认和状态机，不让模型直接掌握授权。运行后通过 Request ID 和 Tool Trace 获取过程证据，再用固定 Fixture、真实接口和安全用例做分层回归。最后通过 FastAPI、会话隔离、有界缓存和 React 页面完成服务化。这个过程中我更关注的不是调用了多少 Agent 框架 API，而是模型的不确定性如何被业务契约、确定性代码、评测和可观测性约束住。
