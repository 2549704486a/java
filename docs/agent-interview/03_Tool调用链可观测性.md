# Tool 调用链可观测性

## 面试场景

**问题：你如何排查 Agent 回答慢或工具调用错误？**

我没有只打印最终回答，而是为每次请求建立结构化 Tool 轨迹。FastAPI 的 `request_id` 会传入 Agent 执行层和下游 Java 请求头，`load_skill` 与每个业务 Tool 都统一记录调用参数、是否完成、业务结果码和自身耗时；完整业务响应和用户问题正文不进入轨迹。

评测时同时保留模型声明的 `tool_calls`、代码实际执行轨迹和 Fixture 后端路径。这样可以区分四类问题：模型没有加载 Skill、模型选错业务 Tool、Tool/Service 执行失败、下游接口路径错误。评测汇总还按 Tool 计算调用次数、失败数、平均和最大耗时。

真实验证中，一次奖品推荐 HTTP 请求总耗时约 4.99 秒，两次 Java 查询分别约 8.94 和 12.13 毫秒，`recommend_awards` 总耗时约 21.56 毫秒，说明该次延迟主要在模型调用，不在 Java 查询或业务 Skill。固定集接入轨迹后回归 `22/22`，证明采集逻辑没有改变原有路由行为。

## 工程认识

- 模型声明调用不等于代码实际执行，二者应分别留证。
- 总 RT 必须拆分模型、Tool 和后端耗时，不能直接把慢归因于大模型或数据库。
- 可观测性数据也要最小化，记录诊断所需摘要，而不是复制完整业务数据。
- `request_id` 的价值是把入口请求、Agent 轨迹和下游接口日志串成一条证据链。
