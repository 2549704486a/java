# 原文优先的长期记忆内核

> 本阶段解决的不是“如何记住更多”，而是“如何忠实、可控地保存用户已经说清楚的内容”。记忆不再要求先变成完整业务对象，业务参数只在真正执行操作时补充。

## 1. 原方案的问题

旧实现只有一个兑换目标对象和一份偏好列表，因此出现两个问题：

- “我喜欢小鸟”必须被解释成奖品分类，否则无法进入固定字段。
- “我明年想换一个手环”必须补充奖品 ID 和精确日期，否则无法保存目标。
- 偏好更新采用完整列表替换，需要模型先读取、合并再写回，可能误删没有被本轮提及的偏好。

这些限制来自内部数据结构，而不是用户语义。

## 2. 数据模型

每条长期信息独立保存为一个 `MemoryItem`：

```json
{
  "memoryId": "31d55277aa6f4f8c809e15dc68420f55",
  "userId": 10,
  "memoryType": "goal",
  "memoryKey": "goal:手环",
  "rawText": "我打算明年换一个手环",
  "normalizedData": {
    "subject": "手环",
    "timeExpression": "明年",
    "targetYear": 2027
  },
  "status": "ACTIVE",
  "validFrom": "2026-08-22T09:20:00Z",
  "validTo": null
}
```

其中 `rawText` 是事实来源，必须忠实保存；`normalizedData` 只是帮助检索、去重和冲突识别的可选投影。即使无法提取主题、年份或偏好方向，语义明确的原文仍可保存。

## 3. 写入决策

存储层按照记忆类型和主题生成可读的 `memoryKey`，再与同一用户的生效记忆比较：

| 动作 | 含义 | 示例 |
| --- | --- | --- |
| `ADD` | 没有同主题记忆，新增 | 第一次说“我喜欢小鸟” |
| `NOOP` | 内容没有实质变化 | 再次说“我喜欢小鸟” |
| `UPDATE` | 同主题补充或修改信息 | “明年换手环”改为“后年换手环” |
| `SUPERSEDE` | 新表达否定旧表达 | “喜欢小鸟”改为“不喜欢小鸟” |

冲突更新时旧记录保留为 `SUPERSEDED`，新记录成为唯一 `ACTIVE` 版本。用户明确要求遗忘时，删除对应范围内的内容。

## 4. 存储与兼容

- MySQL 表 `agent_long_term_memory` 是新的长期记忆事实来源。
- 唯一索引保证同一用户、同一主题最多只有一条生效记录。
- 旧的目标和偏好结构保留为兼容视图，能够映射时继续返回。
- Redis 后端暂时保留，便于旧环境和测试运行；下一阶段再降为缓存。
- `remember_user_memory` 接收原文和可选结构化字段；`save_redemption_goal` 继续服务已经明确绑定奖品和日期的目标。

## 5. 当前边界

本阶段只实现语义记忆的可靠写入，没有引入向量检索、后台记忆总结、情景记忆或知识图谱。当前记忆量较小，先使用用户、类型、状态和主题完成确定性查询；后续只有在评测证明召回不足时再增加语义检索。

## 6. 验证

关键测试覆盖：

- 宽泛偏好保留原文。
- 不完整目标无需奖品 ID 和精确日期即可保存。
- 重复表达返回 `NOOP`。
- 相反偏好返回 `SUPERSEDE`，最终只有新记忆生效。
- 真实 MySQL 中完成 `ADD -> SUPERSEDE` 和跨查询读取，临时测试数据已清理。
