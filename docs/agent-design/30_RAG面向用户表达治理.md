# RAG 面向用户表达治理

> 检索命中并不代表回答已经适合直接展示给用户。本阶段解决两个问题：知识文档中的内部实现术语泄漏到回答，以及同一来源在相邻句子中反复出现。

## 1. 问题与目标

初版知识文档直接使用后端状态码描述兑换和任务状态。模型忠实引用文档时，会把这些内部术语原样交给用户；与此同时，模型可能在每个要点后重复相同引用。两者都不是检索错误，而是知识表达、生成约束和评测标准没有区分“服务端事实”与“用户展示语言”。

本次治理目标是：

- 默认使用“处理中”“已经兑换过”“已完成待领取”等用户能理解的业务语言。
- 只有用户明确询问技术实现时，才解释内部字段、状态码或 Tool 名称。
- 同一来源在一个自然段或一组紧密相关的要点后引用一次。
- 不能只依赖 Prompt，要用自动化评测约束输出，并在统一回答出口做有限兜底。

## 2. 三层治理

### 2.1 知识源：先让原料面向用户

三篇受控知识文档统一升级版本。兑换状态和任务状态改用业务含义作为主表达，实时数据边界也不再向普通用户暴露 Tool 名称。这样即使模型复述检索片段，也不容易把内部实现细节带入最终回答。

### 2.2 Prompt：约束路由和表达

System Prompt 增加三类规则：

1. 稳定业务规则必须先调用知识检索，不得凭模型记忆直接回答，也不得把语义明确的问题改成澄清问题。
2. 默认把后端状态、原因、字段和 Tool 名称翻译为用户语言。
3. 同一知识来源不在相邻句子中重复引用。

Prompt 负责告诉模型“应该怎么做”，但不能把它当成唯一保证。

### 2.3 评测与回答出口：验证并有限纠偏

Agent 评测新增两项独立指标：

- `user_language`：回答不得出现用例声明的内部术语。
- `citation_concise`：每个知识来源的出现次数不得超过用例上限。

统一回答出口会去除完全相同的重复引用；当模型已经调用知识检索却完全漏引时，只补充排名第一的真实来源，不把 Top3 全部堆到回答末尾。这里不负责重写业务答案，避免后处理器变成第二套回答生成器。

## 3. 验证结果

| 验证层 | 结果 | 说明 |
| --- | --- | --- |
| 知识目录与切分 | `3` 篇文档、`12` 个 Chunk | 使用新目录版本重建真实 Embedding 索引 |
| 检索评测 | `24/24` | Hit@3、拒答和引用结构为 `100%`，Top1 为 `94.44%` |
| Agent 评测 | `11/11` | Tool 路由、知识命中、引用、用户语言、引用简洁性和关键结论忠实度均为 `100%` |
| 定向单元测试 | `14/14` | 覆盖引用兜底、重复引用、内部术语和知识目录契约 |
| 真实 HTTP | `3/3` | 三个全新会话都执行知识检索并返回一处有效引用 |

真实 HTTP 验证曾出现一次英文澄清。结合请求工具和轨迹复查后确认，是 Windows PowerShell 发送中文 JSON 时发生编码失真，服务端没有收到正确问题；改用 Python `httpx` 明确发送 UTF-8 后，连续三次均产生 `search_business_knowledge` 轨迹。因此它不是 RAG 运行时漏接或模型路由故障。

## 4. 工程结论

用户表达治理不能只改 Prompt。更稳定的顺序是：先净化知识原料，再约束模型输出，用评测持续检查，最后只在统一出口做不改变业务语义的有限兜底。若以后新增知识文档，应同时增加口语问法、内部术语禁用和引用次数用例，防止知识规模扩大后重新退化。
