# 奖品中心与 Agent 对话前端

> 这一阶段把 Agent 变成用户可操作的页面。页面既展示实时业务事实，也承载受控兑换对话，但浏览器始终不能绕过 Agent 的一次性确认机制直接调用旧写接口。

## 1. 用户流程

```text
进入页面
  -> 使用签名访问令牌验证身份
  -> 查看实时积分、奖品和兑换资格
  -> 点击奖品生成对应咨询问题
  -> Agent 查询实时事实并回答、规划任务或生成兑换确认
  -> 用户明确确认后受理旧事务消息兑换
```

页面包含两个核心区域：

- 奖品中心：展示积分、奖品库存、所需积分、资格状态和积分缺口。
- 兑换顾问：保留 `session_id` 延续同一会话，支持快捷问题和奖品上下文带入。

## 2. 接口设计

当前使用 `GET /v1/dashboard` 作为页面聚合接口，用户由 Bearer Token 提供：

```text
Browser
  -> FastAPI dashboard
      -> Java user points
      -> Java award list
  <- points + awards
```

FastAPI 负责校验 Java 信封和嵌套奖品 Schema，并统一错误语义；Java 仍然是动态业务事实的唯一来源。请求中的 `X-Request-ID` 会继续透传到 Java 服务。

没有让浏览器直接并发调用两个 Java 接口，原因是：

- 页面不需要理解 Java 的 `ToolEnvelope`。
- 聚合失败的状态码和提示可以统一。
- 后续身份认证接入后，用户身份可在服务端注入，而不是相信浏览器参数。

## 3. 部署方式

开发模式使用 Vite，`/v1` 和 `/health` 代理到 8090。生产模式先构建静态资源，再由 FastAPI 挂载 `web-ui/dist`：

```text
http://127.0.0.1:8090/        -> React 静态页面
http://127.0.0.1:8090/v1/**   -> Agent API
http://127.0.0.1:8090/docs    -> FastAPI 文档
```

这种同源方式减少一个常驻进程，也避免为了本地演示额外开放 CORS。`start-local.ps1` 会按文件修改时间判断是否需要重新构建前端。

## 4. 安全边界

奖品卡片不会直接调用 Java 写接口，而是向同一 Agent 会话发送“准备兑换”：

- `prepare_exchange` 只展示实时摘要并生成短期一次性凭证，不写业务数据。
- 用户明确确认后，`confirm_exchange` 原子消费凭证并最多提交一次旧链路。
- 重复、并发、跨用户、跨会话和过期确认都在 Java 调用前拒绝。
- POST 超时或响应异常标记为 `SUBMISSION_UNKNOWN`，不自动重试。

浏览器不再填写用户 ID，而是携带签名 JWT；FastAPI 验证后把可信身份绑定到查询、会话和兑换确认。

## 5. 验证结果

- React TypeScript 生产构建通过，共转换 1584 个模块。
- 构建产物约为 `161.75KB JS` 和 `16.92KB CSS`，gzip 后合计约 `57KB`。
- Agent 离线测试 `30/30` 通过，包含 dashboard 聚合契约测试。
- 本地真实冒烟通过：首页返回 `200`；用户 10 返回 `1680` 积分和 6 个实时奖品；请求 ID 正确回传。
- PowerShell 启动脚本完成语法检查，前端构建已纳入一键启动流程。

## 6. 已知限制

- 当前 JWT 签发命令仅用于本地演示，生产环境仍需接入正式登录系统。
- 确认存储已经迁移到 Redis；短期会话记忆仍保存在单个 Agent 进程中。
- Agent 回答按纯文本显示，暂未增加 Markdown 渲染。
- 为兼容 Node.js 18 使用 Vite 5；剩余 npm 审计项影响 Vite 开发服务器，生产页面由 FastAPI 静态托管。
