# 复杂规划评测与任务约束

> 这一阶段不预设“复杂问题就要上 Query Rewrite 或多 Agent”，而是先冻结真实约束问题，检查模型选了什么 Tool、参数是否完整、后端查了几次，以及答案是否忠实覆盖用户条件。评测证明，当前缺口不是模型不会规划，而是原 Tool 只能接收任务 ID，无法直接表达用户说出的任务名称。

## 1. 要验证的问题

核心问题来自以下用户表达：

> 我想在月底兑换 6 号奖品，但每天只能完成签到和浏览任务，请帮我规划。

这句话同时包含四类信息：

1. 目标奖品：`6 号奖品`。
2. 时间约束：`月底`。
3. 能力约束：只能做`签到`和`浏览`。
4. 任务目标：生成积分计划，而不是立即兑换。

评测不能只看最终文字“像不像正确答案”，还要检查约束是否真正进入 Tool 参数。否则当前数据碰巧选对任务，换一组奖励值就可能失败。

## 2. 冻结用例与隔离数据

`evals/complex_planning_cases.json` 包含 8 类案例：

| 用例 | 场景 | 关键检查 |
| --- | --- | --- |
| P01 | 已保存目标 + 排除分享 | 只调用一次目标规划 Skill，排除条件进入参数 |
| P02 | 单个已保存目标 | 直接生成实时计划，不重复读记忆或奖品列表 |
| P03 | 多个目标但未指定 | 返回候选，不访问实时业务接口 |
| P04 | 多目标中指定手表 | 正确选中手表，再查询实时数据 |
| P05 | 一个手环目标匹配两个奖品 | 返回两个奖品候选，不替用户猜测 |
| P06 | 目标时间已过 | 停止规划并提示更新目标 |
| P07 | 没有已保存目标 | 提示先建立目标，不访问业务接口 |
| P08 | 6 号奖品 + 月底 + 只做签到浏览 | 允许集合进入参数，并回应期限 |

每条 Fixture 自带独立的 `memory_seed`，不会读取开发机上的历史长期记忆。例如：

```json
{
  "memory_type": "goal",
  "raw_text": "我计划在 2099 年兑换 6 号手表",
  "normalized_data": {
    "subject": "手表",
    "awardId": 6,
    "targetYear": 2099
  }
}
```

评测 Runner 还增加了调用次数断言：

```json
{
  "expected_tool_counts": {
    "plan_points_for_saved_goal": 1
  },
  "expected_backend_counts": {
    "check_exchange_eligibility": 1,
    "get_award_detail": 1,
    "list_available_tasks": 1
  }
}
```

这样可以区分“答案正确”和“答案正确但走了冗余路径”。

## 3. 基线暴露了什么

### 3.1 排除任务需要一次额外查询

首轮 P01 的轨迹是：

```text
list_available_tasks
  -> plan_points_for_saved_goal(excluded_task_ids=[3])
      -> check_exchange_eligibility
      -> get_award_detail
      -> list_available_tasks
```

原 Tool 只接受 `excluded_task_ids`。模型必须先查任务列表，把“分享活动”翻译成 ID `3`；规划 Service 为了生成计划又查一次任务，造成任务接口重复调用。

直接数据：

| 指标 | P01 基线 |
| --- | ---: |
| Agent Tool 数 | 2 |
| 任务接口调用数 | 2 |
| 模型调用数 | 3 |
| 端到端耗时 | 8320.17ms |
| Token | 13370 |

### 3.2 结果可能只是碰巧正确

P08 基线只调用了：

```json
{
  "name": "plan_points_for_award",
  "args": {
    "award_id": 6
  }
}
```

回答最终推荐了签到和浏览，看起来满足要求，但“只能签到和浏览”没有进入参数。之所以没有推荐分享，仅仅因为当前最小任务组合恰好是签到加浏览。这个结果不能证明 Agent 真正处理了约束。

## 4. 修复方案

规划 Tool 同时支持 ID、排除名称和允许名称：

```python
PlanPointsInput(
    award_id=6,
    excluded_task_ids=[],
    excluded_task_names=[],
    allowed_task_names=["签到", "浏览"],
)
```

对应语义如下：

| 字段 | 使用场景 |
| --- | --- |
| `excluded_task_ids` | 调用方已经掌握准确任务 ID |
| `excluded_task_names` | 用户说“不做分享” |
| `allowed_task_names` | 用户说“只能做签到和浏览” |

Skill 在一次实时任务查询后规范化名称，并执行以下顺序：

1. 排除明确的任务 ID。
2. 排除命中 `excluded_task_names` 的任务。
3. 如果存在允许集合，只保留命中 `allowed_task_names` 的任务。
4. 在过滤后的任务中计算最小任务组合。

`签到`可以匹配`每日签到`，`浏览`可以匹配`浏览奖励`；匹配只服务于任务约束，不做开放式语义猜测。

用户提供期限时，Prompt 要求回答复述期限。由于现有任务数据没有每日次数和执行周期，Agent 只能判断当前任务奖励能否覆盖积分缺口，不能承诺一定在月底前完成。

## 5. 验证结果

修复后 P01 的轨迹缩短为：

```text
plan_points_for_saved_goal(excluded_task_names=["分享"])
  -> check_exchange_eligibility
  -> get_award_detail
  -> list_available_tasks
```

| 指标 | P01 基线 | P01 修复后 |
| --- | ---: | ---: |
| Agent Tool 数 | 2 | 1 |
| 任务接口调用数 | 2 | 1 |
| 模型调用数 | 3 | 2 |
| 端到端耗时 | 8320.17ms | 5030.90ms |
| Token | 13370 | 9164 |

这组耗时和 Token 只用于解释本次调用路径，单次样本不能当作稳定性能结论。可以确定的是调用层级和后端查询次数确实减少了。

验证结果：

- 任务约束、评测 Runner、目标规划和轨迹相关定向单元测试通过。
- P02 至 P07 在修改后的完整轮中为 `6/6`。
- 修正任务契约、期限表达和评分同义参数后，P01、P08 定向复验为 `2/2`。
- 没有执行项目全量回归，遵循“定向优先、里程碑全量”的回归约定。

## 6. 技术决策

当前证据不支持引入 Query Rewrite、LCEL 或多 Agent：

- 多目标、多奖品、过期目标和无目标都能由单 Agent 与确定性 Service 正确处理。
- 两个失败都能定位到明确的 Tool 契约和回答约束。
- 修改后不需要额外模型步骤，反而减少了一次 Tool 和一次模型往返。

因此 P3.4 的结论是：复杂规划先靠结构化 Tool 契约承接业务约束，把选择和计算留在确定性 Service；Skill 负责告诉模型何时调用以及怎样处理结果。只有后续运营策划出现稳定漏拆子任务时，再比较 Query Rewrite 或复杂编排。
