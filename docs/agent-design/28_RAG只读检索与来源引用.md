# RAG 只读检索与来源引用

> 本阶段解决“Agent 怎样安全地查询规则知识”。检索只负责返回可靠片段和出处，不替代实时业务 Tool，也不参与兑换写操作。

## 1. 调用链

```text
用户询问稳定规则
  -> Agent 选择 search_business_knowledge
  -> KnowledgeSearchService 查询本地 Chroma
  -> 过滤低相关和重复 Chunk
  -> 返回原文、相关度和 citation
  -> Agent 仅依据命中片段回答并保留引用
```

运行时只创建一个 `KnowledgeSearchService`，所有按用户缓存的 Agent 共享它，避免重复打开相同索引。服务停止时由 Runtime 统一释放自己创建的索引连接。

## 2. Tool 契约

输入：

```json
{
  "query": "兑换进入处理中是否代表成功",
  "limit": 3
}
```

可靠命中时返回 `KNOWLEDGE_FOUND`，每个 `match` 包含：

- `content`：可供模型回答的原文片段。
- `score`：本次检索的相关度，只用于过滤和诊断。
- `citation`：用户可读的 `[文档标题 / 章节]` 引用。
- `knowledgeId`、`knowledgeVersion`：知识身份和版本。
- `sourcePath`：受控知识文档的项目内相对路径。

没有候选达到阈值时返回：

```json
{
  "success": true,
  "code": "NO_RELEVANT_KNOWLEDGE",
  "data": {"matches": []},
  "message": "受控知识库中没有找到足够相关的可靠内容",
  "retryable": false
}
```

这里的 `success=true` 表示“检索动作正常完成”，不表示“知识库一定有答案”。Agent 必须明确无可靠答案，不能根据常识补全业务规则。

索引异常则返回 `KNOWLEDGE_SEARCH_FAILED`，不暴露数据库文件、内部异常和调用栈。

## 3. RAG 与 Tool 边界

| 问题 | 数据来源 |
| --- | --- |
| 积分如何获得、处理中是什么意思、为什么需要确认 | RAG |
| 当前积分、库存、价格、活动时间 | Java 查询 Tool |
| 当前是否符合兑换条件 | `check_exchange_eligibility` |
| 某次兑换最终是否成功 | 订单页面或订单查询能力 |
| 提交兑换 | 受控兑换状态机 |

如果一个问题同时包含规则和实时事实，应分别调用知识检索和必要的实时 Tool，不能使用文档中的示例或旧描述替代当前数据。

## 4. 低相关拒答

当前配置使用 `RAG_RELEVANCE_THRESHOLD=0.30`。它由扩充后的真实检索集重新校准：最低正样本为 `0.3446`，最高负样本为 `0.0540`。处理顺序是：

1. 检索 `limit * 2` 个候选。
2. 删除低于阈值的候选。
3. 按 `chunk_id` 去重。
4. 最多返回 `limit` 个片段。
5. 没有剩余片段时返回 `NO_RELEVANT_KNOWLEDGE`。

`0.30` 不是普适结论。不同 Embedding 模型和知识规模的分数分布可能不同，后续必须使用“应命中、易混淆、无答案”三类检索集重新校准阈值。

## 5. 按能力注入

`.env` 中 `RAG_ENABLED=false` 时：

- 不打开向量索引。
- 不向 Agent 注册 `search_business_knowledge`。
- System Prompt 不声明知识检索能力。
- 现有积分规划、奖品推荐和受控兑换不受影响。

完成建库后设置 `RAG_ENABLED=true`，Runtime 会在启动时检查正式集合。目录不存在或集合为空时直接启动失败，避免模型以为自己有知识库、实际却在无依据回答。

当前还会比较正式集合与受控知识目录中的目录版本、知识 ID 和单篇文档版本；旧索引、混合版本或缺少版本元数据时同样拒绝启动并要求重建。

Tool 轨迹只记录查询字符数和返回状态，不复制用户问题正文。回答所需的原文只存在于本次 Tool 结果和模型上下文中。

## 6. 建库失败保护

索引构建改为：

```text
清理上次临时集合
  -> 在临时集合完成向量化和写入
  -> 全部成功后删除旧正式集合
  -> 将临时集合切换为正式集合
```

外部向量化失败时，只清理临时集合，原正式集合继续可用。对应测试先建立可检索集合，再注入向量化异常，验证旧 Chunk 数量不变。

## 7. 当前验证与缺口

已验证：

- 可靠命中会过滤重复 Chunk 并生成引用。
- 低相关候选会返回结构化无答案。
- 底层异常会转换为稳定错误，不泄露内部细节。
- RAG 关闭时 Tool 和 Prompt 能力同时消失。
- Tool 调用进入统一轨迹，但查询正文不写入轨迹。
- 建库失败不会覆盖正式集合。
- 旧索引、混合文档版本和缺少版本元数据会被启动门禁拒绝。
- 全量 Python 测试共执行 `86` 个，`79` 个通过，`7` 个 Redis 集成测试按开关跳过。

当前已经使用阿里云 `text-embedding-v4` 完成真实联调：3 篇受控文档生成 `12` 个 Chunk，并成功写入本地 Chroma 正式集合。由于服务限制单批最多提交 `10` 条文本，建库客户端显式配置 `RAG_EMBEDDING_BATCH_SIZE=10`。

初次联调曾使用 `0.35` 阈值验证三类业务问题和一个无关问题；后续困难集暴露口语问题误拒答，当前阈值已按 `31_RAG索引新鲜度与答案忠实度.md` 重新校准为 `0.30`。距离换算结果会规范化到 `0~1`，避免明显无关结果产生负分告警，但不改变候选排序。

`search_business_knowledge` Tool 已使用真实索引调用成功，能够返回正文、相关度和来源引用；本机 `.env` 已启用 `RAG_ENABLED=true`。这次是小规模冒烟校准，足以证明接入链路可用，但还不能替代后续包含更多同义问法、干扰问题和引用正确性的正式检索评测。
