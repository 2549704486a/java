# 运营活动审核发布与效果回流

> 本阶段补齐智能运营 Agent 的业务闭环：大模型负责理解需求和生成草案，确定性服务负责持久化、审核状态迁移、发布和效果回流。这样既保留 Agent 处理模糊需求的价值，也不把高风险写操作交给模型自由决定。

## 1. 为什么需要这一步

上一阶段已经能生成活动草案，但草案只存在于一次 Tool 返回中，缺少三个关键能力：

1. 没有事实源，页面刷新后无法继续审核同一份草案。
2. 没有审核状态机，无法证明谁在什么时间批准了什么版本。
3. 没有效果回流，下一次活动规划仍只能依赖预置历史指标。

本阶段把一次性的“建议文本”升级为可追踪的业务对象，同时继续坚持：**LLM 生成建议，确定性代码执行状态变化。**

## 2. 完整调用链

### 2.1 生成并保存草案

```text
运营人员自然语言需求
  -> Operator Agent
  -> draft_campaign_plan Tool
  -> 确定性活动规划 Skill
  -> CampaignWorkflowService.createDraft
  -> campaign_plan_draft
  -> campaign_plan_audit(CREATE)
```

草案只有在规划结果为 `DRAFT_READY` 时才会保存。缺少历史指标、单位成本或约束冲突时，系统返回待补数据或冲突原因，不保存一份看似完整但不可执行的草案。

### 2.2 人工审核与确定性发布

```text
/operator 工作台
  -> FastAPI 校验运营令牌和细粒度权限
  -> Java CampaignWorkflowController
  -> CampaignWorkflowService
  -> 乐观版本检查 + 状态机校验
  -> 更新草案并写入审计记录
```

状态机如下：

```text
DRAFT
  -> PENDING_REVIEW
     -> APPROVED
        -> PUBLISHED
     -> REJECTED
```

只有 `APPROVED` 草案可以发布。发布事务同时完成：

- 将草案改为 `PUBLISHED`；
- 创建一条 `campaign_activity` 活动记录；
- 写入 `PUBLISH` 审计记录。

当前“发布”表示生成活动事实记录：尚未开始的活动为 `SCHEDULED`，已进入时间窗口的活动为 `ACTIVE`。它供后续活动执行器读取，不等于已经向用户发送通知，也没有虚构尚未实现的触达系统。

### 2.3 效果回流

```text
运营人员录入活动效果
  -> campaign_effect_metric
  -> campaign_metric_history
  -> 下一次 getCampaignPlanningSnapshot
  -> 下一份活动草案使用真实历史参与率
```

一份效果指标同时承担两个职责：

- `campaign_effect_metric` 保存“哪场活动、谁记录、何时测量”的活动级事实；
- `campaign_metric_history` 提供下一轮规划需要的客群历史指标。

这形成了“规划 -> 审核 -> 发布 -> 复盘 -> 再规划”的闭环，而不是每轮活动都从静态 Fixture 重新开始。

## 3. 数据模型实例

### 3.1 活动草案

```json
{
  "id": 1,
  "draftKey": "campaign-20260824-a1b2",
  "version": 2,
  "operatorId": "local-operator",
  "objective": "提升高积分用户活跃度",
  "targetSegmentKey": "POINTS_AT_LEAST_500",
  "budgetAmountCents": 100000,
  "pointsIssuanceCap": 5000,
  "status": "PENDING_REVIEW"
}
```

`plan_json` 保存 Agent 生成并经确定性校验后的完整任务、奖品、预算和风险快照；独立列保存审核和查询必须使用的稳定字段。

### 3.2 审计记录

```text
CREATE         null             -> DRAFT
SUBMIT_REVIEW  DRAFT            -> PENDING_REVIEW
APPROVE        PENDING_REVIEW   -> APPROVED
PUBLISH        APPROVED         -> PUBLISHED
```

每条记录都保存 `draft_id`、操作者、备注和时间，因此不是只看当前状态，而是可以还原完整变更过程。

### 3.3 已发布活动

```json
{
  "id": 1,
  "draftId": 1,
  "status": "SCHEDULED",
  "publishedBy": "local-operator",
  "budgetAmountCents": 100000,
  "pointsIssuanceCap": 5000
}
```

### 3.4 效果指标

```json
{
  "activityId": 1,
  "metricName": "participation_rate",
  "metricValue": 0.32,
  "sampleSize": 1200,
  "sourceRef": "e2e-campaign-report",
  "recordedBy": "local-operator"
}
```

参与率限制在 `0~1`，样本量必须大于 0，避免把百分数 `32` 或无样本指标写入下一轮规划事实。

## 4. 权限与一致性边界

| 权限 | 能力 |
| --- | --- |
| `campaign:read` | 读取规划快照、草案、活动和效果 |
| `campaign:draft` | 生成并保存草案、提交审核 |
| `campaign:review` | 批准或拒绝待审草案 |
| `campaign:publish` | 发布已批准草案 |
| `campaign:metric` | 记录活动效果 |

关键边界：

- 操作者身份从服务端验证后的令牌获得，浏览器和模型不能自行填写 `operator_id`。
- 草案使用 `version` 做乐观并发控制，旧页面不能覆盖别人刚完成的审核。
- 状态迁移由 Java 服务校验，LLM 不能跳过审核直接发布。
- Python Client 对状态写操作不做自动重放；网络结果不确定时先查询当前事实，避免重复发布。
- 本地闭环为了演示可以给同一运营账号全部权限；生产环境应给策划、审核、发布角色签发不同权限。

## 5. 真实闭环证据

本地通过真实 HTTP、Java 服务和 MySQL 完成了一次完整流程：

| 步骤 | 结果 |
| --- | --- |
| 创建草案 | `id=1, status=DRAFT, version=1` |
| 提交审核 | `status=PENDING_REVIEW, version=2` |
| 审核通过 | `status=APPROVED, version=3` |
| 发布活动 | `activity_id=1, status=SCHEDULED` |
| 回写效果 | `participation_rate=0.32, sample_size=1200` |
| 再次读取 | 草案 1 条、活动 1 条、活动指标 1 条 |

MySQL 审计表完整记录了 `CREATE -> SUBMIT_REVIEW -> APPROVE -> PUBLISH`。效果值也进入 `campaign_metric_history`，下一次规划快照可以读取到 `0.32 / 1200`，证明回流不是只写展示表。

里程碑回归结果：

- Python 全量单元测试 `175/175` 通过；默认跳过的 Redis 集成测试显式开启后 `9/9` 通过。
- Java Maven 全量测试 `28/28` 通过，包含 Spring 上下文真实启动和新增状态机测试 `4/4`。
- React/TypeScript 生产构建通过，共转换 `1587` 个模块。
- 最终只读冒烟确认 Agent 服务为 `UP`，运营身份具有 5 项权限，草案和活动事实均可读取。

## 6. 闭环测试发现的问题

这次真实启动、HTTP 验证和里程碑回归发现了四个仅靠局部单元测试不容易暴露的问题：

1. **Spring 多构造器选择失败**：生产构造器和测试构造器并存时未明确注入构造器，应用启动失败；通过显式标记生产构造器修复。
2. **MyBatis 下划线字段映射丢失**：数据库的 `target_segment_key` 等字段没有稳定映射到 Java 驼峰属性；查询 SQL 改为显式别名。
3. **Python 字段别名遗漏**：Java 返回 `historicalMetrics`，Python 模型没有声明对应别名，导致数据库已有指标仍被当成空列表；补齐模型别名并增加回归断言。
4. **冻结 Fixture 继承失效**：模型增加 Java 别名后，父快照使用驼峰键、子快照使用 Python 字段名，空指标覆盖没有生效；Fixture 合并统一使用内部字段名，避免评测结论受序列化形式影响。

这些问题说明闭环验收不能只验证每个模块各自通过，还要验证真实数据能跨越 MySQL、Java、Python 和前端边界。
