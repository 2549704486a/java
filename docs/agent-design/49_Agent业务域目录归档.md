# Agent 业务域目录归档

这一轮只调整代码的物理位置，不改变业务行为。原先知识检索、长期记忆、受控兑换和智能运营代码都平铺在 `app` 根目录，文件数量增加后，很难从目录判断职责，也容易让后续开发把不相关逻辑继续堆进同一个位置。

## 1. 调整目标

把已经形成稳定边界的代码放入对应业务域，同时保留 `config.py`、`models.py`、`api_client.py`、`trace.py` 等高复用基础模块在根目录。

本次不新增 Service、Capability 或 Adapter，不改变 Agent、Tool、Skill 的调用链，也不为多 Agent 预留空目录。

## 2. 目录映射

| 业务域 | 新目录 | 主要内容 |
| --- | --- | --- |
| 知识检索 | `app/knowledge/` | 知识目录、文档切分与索引、检索、查询归一化 |
| 长期记忆 | `app/memory/` | 记忆模型与存储、MySQL/Redis 实现、记忆召回 |
| 受控兑换 | `app/exchange/` | 兑换确认记录、Redis 确认记录实现 |
| 智能运营 | `app/operator/` | 运营 Agent、身份鉴权、意图识别、运营 Tool、活动数据 |

例如，知识索引现在统一通过业务域内的模块路径调用：

```text
app.knowledge.index
```

## 3. 保持不变的边界

- 类名、函数名、请求模型和返回模型保持不变。
- 用户 Agent、运营 Agent、Tool 与 Skill 的行为保持不变。
- 业务代码和测试代码统一更新导入路径，不保留旧模块兼容壳。
- 命令行入口同步改为新的模块路径，避免文档继续传播过期命令。

## 4. 为什么先做物理归档

目录归档解决的是“代码在哪里”的问题，不顺便重写业务逻辑。这样一旦测试失败，可以优先判断为导入或依赖方向问题，而不是同时排查行为变化。后续拆分 `web.py` 和 `tools.py` 时，也能直接依赖这些稳定业务域。

## 5. 验证方式

本阶段使用两层验证：

1. `compileall` 检查所有源码、测试和评测脚本能否正确解析新导入路径。
2. 完整 Python 单元测试检查目录移动没有改变原有行为。

验证结果：`compileall` 通过；Python 单元测试共执行 `181` 条，全部通过，另有 `9` 条依赖外部条件的测试按预期跳过。
