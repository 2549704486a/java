# 运营知识底座与受众隔离

> 运营活动草案已经能基于实时快照做确定性计算，但模型还不知道运营制度、历史案例和异常处理方法。本阶段先建立可治理的运营知识底座，并把用户知识与运营知识隔离；高级检索算法和知识冲突裁决留到冻结困难用例之后验证。

## 1. 为什么不能只增加 Markdown

知识扩容后，同一个索引同时包含用户兑换规则和运营内部手册。如果检索层只按相似度返回内容，普通用户可能召回运营预算制度、异常代码或历史指标。

因此本轮同时完成两件事：

1. 增加历史活动复盘、运营制度、奖品说明、异常手册和规则变更通知。
2. 给知识补充受众、生效区间和权威级别，并由服务端固定受众过滤。

模型只能填写查询，不能把 `audience` 改为 `operator` 绕过隔离。

## 2. 最小运营知识集

| 知识 ID | 类型 | 权威级别 | 作用 |
| --- | --- | --- | --- |
| `campaign-operation-policy` | 运营制度 | `official_policy` | 解释草案输入、事实来源和人工审核边界 |
| `campaign-award-guide` | 奖品说明 | `system_contract` | 区分兑换积分、单位成本、库存和计划数量 |
| `campaign-review-demo-202608` | 历史案例 | `historical_case` | 演示如何使用历史参与率，同时明确不是生产数据 |
| `campaign-exception-handbook` | 异常手册 | `operations_manual` | 解释缺数据、快照过期和约束冲突的处理方式 |

知识目录由 3 篇文档扩为 8 篇，切分结果由原用户知识扩展为 33 个 Chunk。

## 3. 元数据如何进入检索结果

### 3.1 文档元数据实例

```yaml
knowledge_id: campaign-rule-change-20260822
audience: [operator]
business_type: rule_change_notice
authority_level: official_policy
effective_from: 2026-08-22
source_refs:
  - agent-service/app/models.py
  - sql/migrations/20260822_add_award_unit_cost.sql
```

这些字段分别回答：这是什么知识、谁能看、何时有效、冲突时应把它当作什么级别的证据。

### 3.2 Chunk 元数据实例

```text
Document(
  page_content="自 2026-08-22 起，活动奖品预算统一使用人民币分……",
  metadata={
    "knowledge_id": "campaign-rule-change-20260822",
    "business_type": "rule_change_notice",
    "audience": "operator",
    "authority_level": "official_policy",
    "effective_from": "2026-08-22",
    "effective_until": "",
    "chunk_id": "campaign-rule-change-20260822:1.0.0:0001"
  }
)
```

切分器把治理字段复制到每个 Chunk。检索结果继续返回这些字段，后续才能按照权威级别和生效时间做冲突裁决，而不是只比较向量分数。

## 4. 受众隔离

```text
同一个 Chroma 索引
        |
        +-- 用户检索服务 allowed_audiences={end_user}
        |       -> 只返回兑换规则、积分规则和用户指南
        |
        +-- 运营检索服务 allowed_audiences={operator}
                -> 只返回运营制度、案例、手册和通知
```

当前在候选召回后执行服务端过滤。它先解决权限与上下文污染问题，但不等同于完整的多租户安全方案；知识规模扩大后，可以把受众条件下推到向量库过滤表达式，并保留服务端二次校验。

本地正式索引已重建为目录版本 `2026.08.22.2`。本轮只抽查三个代表性问题，没有执行完整 RAG 回归。

## 6. 当前边界与下一步

- `authority_level` 和生效区间已经进入索引，但尚未实现多文档冲突自动裁决。
- 历史活动复盘是明确标注的演示 Fixture，不是生产经营数据。
- 当前只证明新增运营知识可以被检索，不代表关键词检索、混合召回、重排或 Query Rewrite 已经有收益。
- 已冻结包含精确编号、语义相似案例、口语表达和知识冲突的 15 条运营 RAG 用例，纯向量检索基线见 `41_运营RAG纯向量检索基线.md`。下一步先完成运营检索入口、生效时间过滤和真正的多文档冲突治理；当前基线没有提供立即引入混合检索或重排的证据。
