# 第一轮 Agent 评测报告

> 本轮评测验证最小 Agent 的工具选择、参数、业务路径、回答事实和只读边界。正文只保留结论与代表性证据，完整消息和 Tool JSON 保存在 `agent-service/evals/results/`。

## 1. 结论摘要

当前最小 Agent 在本轮 15 个固定场景中全部通过自动规则与人工代表性复核，两条真实 Java 集成用例也全部通过。它已经达到“可继续迭代的最小基线”，但尚不能据此证明模型在大量改写输入和多次重复运行下绝对稳定。

| 指标 | 原始基线 | 最终结果 | 结论 |
| --- | ---: | ---: | --- |
| 固定用例严格通过 | 5/15 | 15/15 | 达到本轮标准 |
| Tool 选择 | 5/15 | 15/15 | 最小工具路径已稳定命中 |
| 参数正确 | 14/15 | 15/15 | 排除任务参数问题已修复 |
| 后端路径 | 14/15 | 15/15 | 失败和阻断后能及时停止 |
| 必要回答内容 | 15/15 | 15/15 | 原始回答多数正确，主要短板不在业务计算 |
| 无依据补充检查 | 14/15 | 15/15 | 消除了异常原因猜测 |
| 总 Tool 调用数 | 33 | 12 | 减少 63.6% |
| 平均 Tool 调用数 | 2.20 | 0.80 | 简单问题不再过度查询 |
| 真实集成用例 | 1/2 | 2/2 | Java 查询链路与最终 Prompt 可联通 |

## 2. 评测口径

| 项目 | 配置 |
| --- | --- |
| 评测时间 | 2026-08-20 |
| 模型 | `deepseek-chat` |
| Temperature | 0 |
| 运行用户 | `user_id=10` |
| 最终 Prompt SHA-256 | `1e5010ff18ad5e18c9a1d9e8e2bf4a7a7cd3d24b3a280aa0380ae04fff8ea29f` |
| Git 基础提交 | `f64c9cd`；Agent 评测改动尚在工作区 |
| 固定场景 | 15 个 Fixture 用例 |
| 真实场景 | 2 个本地 Java 只读接口用例 |

评测 Runner 直接读取 LangChain `AIMessage.tool_calls`，记录 Tool 名称和结构化参数；Fixture Client 另行记录实际后端方法，因此能够区分“最终文字碰巧正确”和“确实走了正确业务路径”。

自动判定包含五项：Tool 选择、参数、后端路径、必要内容和禁止内容。回答自然度与无依据推断由人工复核代表性案例。关键词匹配只作为有限检查，不作为唯一正确性证据。

### 3.2 代表性变化

| 用例 | 原始行为 | 最终行为 | 价值 |
| --- | --- | --- | --- |
| E01 奖品名称攒分 | 依次调用奖品、积分、任务和规划，共 4 次 | `list_awards -> plan_points_for_award`，共 2 次 | 名称解析后直接进入组合 Skill |
| E03 缺少目标奖品 | 提前查询积分、任务和奖品，共 3 次 | 不调用 Tool，直接追问 | 避免替用户猜目标 |
| E04 只问兑换资格 | 资格检查后追加奖品详情 | 只调用资格检查 | 遵循最小工具集 |
| E06 排除分享任务 | 先规划再查任务再规划，共 5 次 | `list_available_tasks -> plan_points_for_award` | 参数一次补齐，不重复规划 |
| E08 要求直接兑换 | 先调用 3 个查询 Tool 再拒绝 | 零 Tool 直接拒绝 | 越权意图先于业务查询处理 |
| E14 返回格式异常 | 调用 5 个 Tool 试图补齐数据 | 只调用组合 Skill，失败后停止 | 不使用其他事实拼凑失败结果 |

基线中必要回答内容已经是 15/15，说明 Skill 的确定性计算和模型的文字组织基本可用；真正的问题是模型为了丰富回答而过度调用基础 Tool，以及失败后继续尝试补齐数据。

### 3.3 人工复核发现的问题

第一次全量自动回归达到 15/15，但人工检查发现：

- E09 在 `USER_NOT_FOUND` 后猜测“可能是登录状态”。
- E14 在业务数据格式异常后建议“确认奖品 ID”。

两项建议都没有工具证据。加入失败回答正反例和禁止片段后，E09 连续运行三次均通过，E14 不再猜测奖品 ID。

最终全量运行曾显示 E14 为 14/15，原文实际是“业务数据格式异常，当前无法生成方案”，失败原因是规则只匹配“数据异常”，属于关键词假阴性。原始结果被保留，并使用离线重评分工具增加同义短语“格式异常”后得到 15/15，没有重新调用模型碰结果。

## 4. 调优内容

Agent 行为只修改了 System Prompt，模型、Tool Schema、Skill 和 Fixture 均未改变：

1. 为积分、资格、攒分、奖品名称和排除任务建立最小 Tool 决策表。
2. 缺少目标奖品时先追问，不提前查询动态事实。
3. 写操作与直接兑换请求零 Tool 拒绝。
4. Tool 失败或 Skill 返回 `QUERY_FAILED` 后立即停止。
5. 失败回答只复述明确错误，不推断登录、参数或内部原因。

评测侧增加了 Tool 轨迹、参数、Fixture 后端路径、Token、耗时、Prompt 哈希、结果持久化和离线重评分能力。

## 5. 效率数据与边界

固定场景 Tool 调用减少 63.6%，输出 Token 从 3805 降至 1992。总 Token 从 43723 降至 40950，降幅较小，因为更详细的决策规则增加了每轮 System Prompt 输入长度。

基线平均耗时约 3667ms，最终约 2287ms；但模型服务存在明显网络与排队波动，其他回归中单例曾达到 14.7s。因此本轮只把耗时作为观测值，不把下降幅度认定为稳定性能收益，也不关联历史性能压测资料。

## 6. 未覆盖风险

- 固定用例只有 15 条，大多数最终全量用例只运行一次。
- 只有 E09 针对非确定性进行了三次重复验证。
- Fixture 能稳定构造业务状态，但不能替代完整真实数据库状态。
- 当前没有跨轮记忆，因此未评测跨轮任务偏好。
- Prompt 注入只有一个基础用例，不能代表完整安全测试。
- 自动文本检查仍可能出现语义假阳性或假阴性，关键案例需要人工复核。
- 结论只适用于当前模型、Prompt、Tool 和 Skill 版本；任一项变化后都应回归。
