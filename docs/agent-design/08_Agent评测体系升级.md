# Agent 评测体系升级

> 这份文档不重复第一轮评测结果，而是说明现有评分体系还缺什么、为什么要补，以及后续按照什么顺序演进。简单地说，第一轮解决了“能不能稳定回归已知问题”，下一阶段要解决“换一种问法、重复运行或进入真实环境后是否仍然可靠”。

## 1. 当前基线与结论边界

当前评测已经具备一套可复现的最小闭环：固定用例驱动真实模型运行，记录最终回答、Tool 调用、参数、Fixture 后端路径、Token、耗时和完整消息轨迹，再使用确定性规则自动评分。

| 已有能力 | 价值 |
| --- | --- |
| Tool 选择与允许列表 | 发现漏调用和多余调用 |
| Tool 参数断言 | 验证奖品 ID、排除任务等结构化参数 |
| Fixture 后端路径 | 区分“文字碰巧正确”和“确实执行了正确业务流程” |
| 必要内容与禁止短语 | 检查关键事实、无依据推断和越权表达 |
| Prompt 哈希、轨迹与原始结果 | 支持版本追踪和问题复盘 |
| 离线重评分 | 修正评分器后重新批改原始答卷，不重新调用模型 |

当前结果只能证明：**现有固定场景在当前模型、Prompt、Tool 和评分口径下通过回归**。它不能证明对未见表达、多次运行和真实用户分布已经稳定泛化。

主要缺口：

1. 现有固定用例都参与过调优，只能作为回归集，不能再充当独立盲测集。
2. 回答内容主要依靠关键词判断，存在同义表达假阴性和关键词碰巧命中的假阳性。
3. 大部分用例只运行一次，无法量化模型的随机波动。
4. 当前评分以二值结果为主，没有区分安全越权、业务错误和表达瑕疵的严重程度。
5. 真实集成用例数量较少，尚未形成生产轨迹回流和长期质量监控。

## 2. 目标评测分层

成熟评测不是寻找一个万能评分器，而是让不同方法负责自己最擅长的部分。

| 层级 | 评测对象 | 推荐手段 | 在本项目中的例子 |
| --- | --- | --- | --- |
| 组件层 | 确定性代码 | 单元测试、Schema 校验 | Pydantic 校验、积分组合计算、HTTP 重试 |
| 硬约束层 | Tool 与安全边界 | 代码评分，作为硬门禁 | Tool 名称、参数、只读接口、禁止写操作 |
| 结果层 | 最终业务结果 | 确定性状态计算 | 推荐积分合计、剩余缺口、排除任务是否生效 |
| 轨迹层 | Agent 完整执行路径 | 规则匹配，必要时增加轨迹 Judge | 是否重复查询、失败后是否停止、路径是否合理 |
| 表达层 | 语义正确性与可用性 | LLM-as-a-Judge + 评分 Rubric | 是否真正回答问题、是否清晰、是否无依据推断 |
| 校准层 | 自动评分器本身 | 人工黄金标注与误判复核 | Judge 与人工判断的一致率、假阳性和假阴性 |
| 线上层 | 真实用户分布 | 轨迹抽样、异常检测、反馈回流 | 将真实失败问题加入离线回归集 |

硬约束不能交给 LLM Judge 代替。例如“是否调用写接口”和“积分合计是否正确”应由代码直接判定；只有语义等价、清晰度和相关性等难以枚举的内容才交给 Judge。

## 3. 数据集与实验规范

### 3.1 数据集分工

| 数据集 | 用途 | 是否允许用于调优 |
| --- | --- | --- |
| `development` | 快速定位和修复新问题 | 允许 |
| `regression` | 防止已修复问题再次出现；现有 15 个 Fixture 归入此处 | 允许查看，不应只追求字面命中 |
| `holdout` | 验证未见表达和泛化能力 | 禁止根据单例结果定向修改 Prompt |
| `live/backtest` | 来自真实接口或后续生产轨迹 | 仅脱敏后进入评测 |

盲测集需要覆盖同义改写、口语、省略信息、错误参数、越权请求、异常返回和多轮上下文。盲测结果只用于验收；若根据失败案例完成调优，该案例随后转入回归集，并补充新的未见案例。

### 3.2 重复运行与统计

关键用例至少重复运行 3 次，高风险安全用例建议运行 5 次。报告不再只写一次性的 `15/15`，还要记录：

- 每个用例的通过次数，如 `5/5`。
- 各检查维度通过率。
- 平均值及 P95 延迟、Token 和 Tool 调用数。
- 同一版本多次运行的波动与失败样本。

Temperature 为 0 只能降低随机性，不能替代重复试验。

### 3.3 版本与证据

每次实验至少保存以下元数据：

- Git 提交、模型名称与模型参数。
- System Prompt、Tool Schema、Skill 和用例集的版本或哈希。
- 评分器版本、运行时间、重试和递归上限。
- 原始回答、完整轨迹、Tool 参数、后端调用、Token、耗时与异常。

原始运行结果不可覆盖。评分规则修正后生成新的重评分文件，并记录源文件与评分器版本。

## 4. 评分器设计与 E14 反思

E14 原始回答是“业务数据格式异常，当前无法生成方案”，但旧规则只识别“数据异常”，因此出现关键词假阴性。正确处理方式是：

1. 保留原始 `14/15` 运行结果。
2. 确认 Tool、参数、后端路径和回答语义实际正确。
3. 在通用评分规则中补充合理同义表达，而不是针对用例 ID 特判。
4. 使用原回答和原轨迹离线重评分，生成新的 `15/15` 结果。
5. 不重新调用模型直到碰出评分器喜欢的措辞。

这件事说明评分器也需要测试。后续内容评分应逐步从单纯关键词升级为组合评分：

| 内容 | 评分方式 |
| --- | --- |
| 数字、原因码、状态、禁止操作 | 确定性规则 |
| 是否包含某类必要语义 | 同义短语组或结构化字段 |
| 是否清晰、相关、无依据推断 | 带 Rubric 的 LLM Judge |
| 自动评分是否可信 | 人工抽样复核和误判统计 |

不得因为某个用例失败就直接向 System Prompt 堆叠字面特例。只有高风险、可泛化、模型仅靠抽象规则仍反复出错的行为，才进入全局 Prompt；Skill 专属规则应沉淀到 Skill，确定性问题应由代码和 Schema 解决。

## 5. 分阶段升级计划

### 阶段一：夯实可重复基线

- 将现有 15 个 Fixture 明确标记为回归集。
- 增加用例集哈希、评分器版本和 Git 提交元数据。
- 优先把积分合计、剩余缺口、排除任务等检查改成结构化结果断言。
- 支持每个用例重复运行并输出稳定通过率、P95 延迟和 Tool 调用统计。

### 阶段二：验证泛化和语义质量

- 建立不参与调优的盲测集。
- 增加同义改写、异常、高风险和多轮场景。
- 引入只负责正确性、相关性、清晰度和无依据推断的 LLM Judge。
- 使用人工标注样本校准 Judge，并记录假阳性、假阴性和分歧案例。

### 阶段三：比较版本并形成线上闭环

- 对 Prompt、模型和 Skill 版本进行 Pairwise A/B 评测。
- 对存在多条合理路径的场景增加轨迹评测。
- 上线后抽样真实轨迹，将高风险、低分和人工投诉案例脱敏回流。
- 将回流案例纳入 development 或 regression，持续回归后再发布。

## 6. 下一阶段验收口径

以下口径在实施前固定，不能在看到结果后临时降低：

1. 现有回归集硬约束检查全部通过。
2. 新盲测集独立运行，结果与回归集分开报告。
3. 安全边界和写操作禁令必须每次运行全部通过。
4. 每个关键用例至少完成 3 次重复试验，并保留全部原始轨迹。
5. 自动 Judge 上线前必须与人工黄金标注对比，分歧案例经过复核。
6. 调优前后同时报告质量、Tool 调用、Token、延迟和失败类型，不能只汇报总通过率。
