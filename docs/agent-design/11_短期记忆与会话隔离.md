# 短期记忆与会话隔离

> 用户通常不会在每句话里重复完整上下文。他可能先说“我想兑换 6 号奖品”，下一句只说“不要分享任务，重新规划”。短期记忆让 Agent 理解省略的信息，但必须同时控制会话容量、并发顺序和用户隔离。

## 1. 课程概念如何落到项目

第七讲把短期记忆定义为单次会话内的对话上下文，并指出长对话需要滑动窗口或摘要等控制策略。项目当前由三层共同治理短期记忆：

```text
InMemorySaver + thread_id + 模型输入窗口
```

`create_agent(checkpointer=...)` 保存每轮消息；调用时通过配置指定：

```python
config={"configurable": {"thread_id": thread_id}}
```

相同 `thread_id` 读取同一段历史，不同 `thread_id` 相互隔离。

## 2. 会话标识为什么包含用户 ID

HTTP 调用方只看到 `session_id`，Runtime 内部生成：

```text
user:{user_id}:session:{session_id}
```

即使用户 10 和用户 11 都传入 `session-001`，最终也是两个不同的 thread：

```text
user:10:session:session-001
user:11:session:session-001
```

这避免了不同用户因为会话 ID 碰撞而读取彼此历史。首次请求不传 `session_id` 时，由服务生成随机值并在响应中返回。

## 3. 为什么需要会话 LRU

`InMemorySaver` 会保存消息检查点。如果只增加记忆、不设计遗忘，持续出现新会话就会让进程内存不断增长。

当前通过 `AGENT_SESSION_CACHE_SIZE` 限制会话数量：

- 每次访问将会话移动到 LRU 尾部。
- 超过容量后，删除最久未使用且当前没有请求执行的会话。
- 淘汰时调用 `checkpointer.delete_thread(thread_id)` 删除历史检查点。
- 同一会话的并发请求通过会话锁串行执行，避免消息顺序错乱。

Agent LRU 与会话 LRU 不是同一个概念：前者缓存按用户绑定的执行图，后者保存具体对话历史。

会话还有独立的空闲 TTL。超过 `AGENT_SESSION_TTL_SECONDS` 没有访问且当前没有请求执行的会话，会删除检查点并同步撤销该会话尚未使用的兑换确认凭证。LRU 解决“会话太多”，TTL 解决“会话虽然不多，但长期不释放”。

## 4. 模型输入窗口如何工作

Checkpointer 中可以保留完整会话状态，但不能把全部历史无限传给模型。每次模型调用前，`context_window` 中间件执行以下步骤：

```text
完整会话消息
  -> 按 HumanMessage 划分完整对话轮次
  -> 先取最近 AGENT_CONTEXT_MAX_TURNS 轮
  -> 从当前轮向前装入 AGENT_CONTEXT_MAX_TOKENS 预算
  -> 注入当前仍有效的待确认兑换摘要
  -> 只把选中的窗口发送给模型
```

按完整轮次裁剪是为了避免拆散以下序列：

```text
HumanMessage
  -> AIMessage(tool_call)
  -> ToolMessage
  -> AIMessage(最终回答)
```

如果只按消息条数从中间切断，模型可能只看到 `ToolMessage`，却看不到是谁调用了这个 Tool，导致消息协议不合法。

一次裁剪的数据模型示例：

```python
ContextWindowResult(
    estimated_tokens_before=8240,
    estimated_tokens_after=5630,
    messages_before=38,
    messages_after=22,
    turns_before=16,
    turns_after=9,
    pending_context_injected=True,
)
```

这里的 `estimated_tokens_*` 使用统一近似算法计算，用于裁剪决策；模型服务返回 `usage_metadata` 时，日志还会记录真实 `actual_input_tokens` 和 `actual_output_tokens`。日志只记录数量，不记录用户对话正文：

```text
agent_context_window thread_id=user:10:session:web-001 max_tokens=6000
estimated_before=8240 estimated_after=5630 messages_before=38 messages_after=22
turns_before=16 turns_after=9 trimmed_messages=16 pending_context=True
actual_input_tokens=5487 actual_output_tokens=126
```

待确认兑换不能只依赖旧聊天记录。中间件会根据当前 `thread_id` 查询确认存储，将仍有效的奖品摘要临时追加到 System Message；确认凭证本身不会进入模型上下文。即使准备兑换发生在较早轮次并已被窗口裁掉，明确确认和取消仍由 Runtime 的确定性路径处理。

配置如下：

```dotenv
AGENT_SESSION_CACHE_SIZE=1024
AGENT_SESSION_TTL_SECONDS=3600
AGENT_CONTEXT_MAX_TOKENS=6000
AGENT_CONTEXT_MAX_TURNS=12
```

## 5. 验证结果

真实 HTTP 验证：

1. `memory-demo-001` 第一轮指定目标为 6 号奖品。
2. 同一会话第二轮只问“我能兑换它吗”，Agent 正确查询 6 号奖品并回答可以兑换。
3. 新会话 `memory-demo-002` 直接问同一句话，Agent 要求重新提供奖品 ID。

自动化 Fixture 评测 `M01`：

| 轮次 | 用户输入 | Tool 调用 | 结果 |
| --- | --- | --- | --- |
| 1 | 我想兑换 6 号奖品，需要做哪些任务？ | `plan_points_for_award` | PASS |
| 2 | 不要推荐分享任务，请重新规划。 | `list_available_tasks`、`plan_points_for_award` | PASS |

第二轮的规划参数包含 `award_id=6` 和 `excluded_task_ids=[3]`，证明奖品 ID 来自会话上下文，而不是重新查询或猜测。

`P3.1` 新增定向测试覆盖：

- 丢弃最老轮次并保留最近完整轮次。
- 不拆散 Tool 调用与 Tool 返回。
- 当前问题即使单独超过预算也不会被删除。
- 待确认兑换从确认存储注入，不依赖可裁剪历史。
- 模型实际 token 元数据能够进入日志。
- 空闲 TTL 删除检查点，并同步撤销待确认兑换。

相关 Agent、Runtime 和上下文窗口定向测试共 `17/17` 通过。

## 6. 当前边界

- 只支持进程内短期记忆，服务重启后丢失。
- 多实例部署时，不同实例之间不共享会话。
- 当前已按轮次和估算 token 裁剪模型输入，但 Checkpointer 仍保存 TTL 内的完整历史。
- 估算 token 用于提前控制窗口，最终计费仍以模型服务返回的实际 token 为准。
- 尚未实现自动摘要和长期用户目标、偏好。
- 多实例部署时，需要将 Checkpointer 换成 Redis/PostgreSQL 等共享存储。

下一步进入长期记忆，但只保存用户明确确认的兑换目标和稳定偏好；实时积分、库存和订单仍必须通过 Tool 查询。
