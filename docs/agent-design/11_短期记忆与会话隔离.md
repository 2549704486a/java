# 短期记忆与会话隔离

> 用户通常不会在每句话里重复完整上下文。他可能先说“我想兑换 6 号奖品”，下一句只说“不要分享任务，重新规划”。短期记忆让 Agent 理解省略的信息，但必须同时控制会话容量、并发顺序和用户隔离。

## 1. 课程概念如何落到项目

第七讲把短期记忆定义为单次会话内的对话上下文，并指出长对话需要滑动窗口或摘要等控制策略。本阶段先实现最小可用版本：

```text
InMemorySaver + thread_id
```

`create_agent(checkpointer=...)` 保存每轮消息；调用时通过配置指定：

```python
config={"configurable": {"thread_id": thread_id}}
```

相同 `thread_id` 读取同一段历史，不同 `thread_id` 相互隔离。

## 2. 会话标识为什么包含用户 ID

HTTP 调用方只看到 `session_id`，Runtime 内部生成：

```text
user:{user_id}:session:{session_id}
```

即使用户 10 和用户 11 都传入 `session-001`，最终也是两个不同的 thread：

```text
user:10:session:session-001
user:11:session:session-001
```

这避免了不同用户因为会话 ID 碰撞而读取彼此历史。首次请求不传 `session_id` 时，由服务生成随机值并在响应中返回。

## 3. 为什么需要会话 LRU

`InMemorySaver` 会保存消息检查点。如果只增加记忆、不设计遗忘，持续出现新会话就会让进程内存不断增长。

当前通过 `AGENT_SESSION_CACHE_SIZE` 限制会话数量：

- 每次访问将会话移动到 LRU 尾部。
- 超过容量后，删除最久未使用且当前没有请求执行的会话。
- 淘汰时调用 `checkpointer.delete_thread(thread_id)` 删除历史检查点。
- 同一会话的并发请求通过会话锁串行执行，避免消息顺序错乱。

Agent LRU 与会话 LRU 不是同一个概念：前者缓存按用户绑定的执行图，后者保存具体对话历史。

## 4. 真实验证结果

真实 HTTP 验证：

1. `memory-demo-001` 第一轮指定目标为 6 号奖品。
2. 同一会话第二轮只问“我能兑换它吗”，Agent 正确查询 6 号奖品并回答可以兑换。
3. 新会话 `memory-demo-002` 直接问同一句话，Agent 要求重新提供奖品 ID。

自动化 Fixture 评测 `M01`：

| 轮次 | 用户输入 | Tool 调用 | 结果 |
| --- | --- | --- | --- |
| 1 | 我想兑换 6 号奖品，需要做哪些任务？ | `plan_points_for_award` | PASS |
| 2 | 不要推荐分享任务，请重新规划。 | `list_available_tasks`、`plan_points_for_award` | PASS |

第二轮的规划参数包含 `award_id=6` 和 `excluded_task_ids=[3]`，证明奖品 ID 来自会话上下文，而不是重新查询或猜测。

## 5. 当前边界

- 只支持进程内短期记忆，服务重启后丢失。
- 多实例部署时，不同实例之间不共享会话。
- 当前按会话数量限制内存，还没有按 Token 数裁剪长对话。
- 尚未实现滑动窗口、自动摘要和长期用户偏好。
- 生产环境需要将 Checkpointer 换成 Redis/PostgreSQL 等共享存储，并增加会话过期时间。

下一步若继续记忆方向，应先增加 Token 窗口或摘要，而不是直接把所有聊天内容永久保存。
