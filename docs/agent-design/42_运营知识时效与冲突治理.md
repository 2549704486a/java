# 运营知识时效与冲突治理

> 这一阶段解决的不是“能不能搜到文档”，而是“搜到的文档现在能不能用、有没有越权、和另一份规则冲突时该信谁”。这些判断由服务端完成，不能留给模型临场猜测。

## 1. 为什么需要治理层

运营知识会同时包含现行制度、旧制度、变更通知、操作手册和历史案例。只按向量相似度排序会产生三类风险：

1. 未生效或已过期的规则被引用。
2. 用户侧知识进入运营回答，或运营内部资料进入用户回答。
3. 旧制度比新通知更像用户问题，因相似度更高而排在前面。

因此检索链路调整为：

```text
Query
  -> 原文与标准化 Query 双路召回
  -> 相关度阈值
  -> 服务端受众过滤
  -> 运营业务范围过滤
  -> 生效时间过滤
  -> 替代关系与权威级别裁决
  -> TopK 与引用
```

## 2. 数据模型

### 2.1 知识元数据

旧预算制度示例：

```yaml
knowledge_id: campaign-budget-policy-legacy
audience: [operator]
business_type: campaign_policy
authority_level: official_policy
effective_from: 2026-08-01
policy_key: campaign_budget_semantics
```

新通知示例：

```yaml
knowledge_id: campaign-rule-change-20260822
audience: [operator]
business_type: rule_change_notice
authority_level: official_policy
effective_from: 2026-08-22
policy_key: campaign_budget_semantics
supersedes: [campaign-budget-policy-legacy]
```

`policy_key` 表示两份文档属于同一条规则链，`supersedes` 表示新通知明确替代旧制度。目录加载时会校验被替代文档必须存在，且两端的 `policy_key` 必须一致。

### 2.2 运营 Tool 入参

```json
{
  "query": "旧草案说积分就是预算，现在该按哪个口径？",
  "scope": "campaign_policy",
  "limit": 3
}
```

`scope` 不是任意字符串，而是服务端允许的枚举：

| scope | 允许的业务类型 |
| --- | --- |
| `campaign_policy` | 活动制度、规则变更通知 |
| `award_rules` | 奖品字段与选品规则 |
| `operations` | 异常处理手册 |
| `review_cases` | 历史活动复盘 |

向量检索负责语义相似，`scope` 负责业务边界。二者不能互相替代。

### 2.3 冲突裁决结果

```json
{
  "policyKey": "campaign_budget_semantics",
  "selectedKnowledgeId": "campaign-rule-change-20260822",
  "suppressedKnowledgeId": "campaign-budget-policy-legacy",
  "reason": "EXPLICIT_SUPERSEDES"
}
```

该结果让调用方知道旧制度不是“没搜到”，而是被新通知明确替代。若没有显式替代关系，则依次比较权威级别、生效日期和文档版本。

## 3. 权限与时效边界

- 用户 Agent 只持有 `end_user` 检索服务。
- 运营入口只持有 `operator` 检索服务，并要求独立运营 Token 和 `campaign:read` 权限。
- 模型和请求参数都不能修改服务实例的受众范围。
- `effective_from` 晚于当前日期、或 `effective_until` 早于当前日期的文档直接被过滤。
- 时效元数据无法解析时采用失败关闭，不把状态未知的制度交给模型。

## 4. 基线复验暴露的问题

旧版纯向量基线曾得到 `15/15`，但扩大治理所需候选池后，受众隔离用例 `OR13` 被运营奖品文档以 `0.4483` 误命中。原因是旧版只取 `2 × limit` 个候选，前面的用户知识被受众过滤后刚好没有剩余结果；它证明了受众隔离，却不能证明无关问题拒答稳定。

本轮进行了两项修正：

1. 将“受众隔离”和“无关问题拒答”拆成独立验收条件。
2. 运营用例按当前任务固定知识范围，再在范围内执行向量检索。

修正后 15 条运营检索重新通过。`OR13` 不再返回用户兑换知识，真正的无关问题 `OR14` 仍返回 `NO_RELEVANT_KNOWLEDGE`。

## 5. 验证结果

- 知识目录：`9` 篇文档、`37` 个 Chunk，目录版本 `2026.08.22.3`。
- 运营检索集：`15/15`。
- Top1、Hit@3、负样本拒答率、引用结构有效率：均为 `100%`。
- 真实冲突用例 `OR11`：新通知 Top1 分数 `0.7276`，旧制度被记录为 `EXPLICIT_SUPERSEDES`。
- 代码定向测试：目录、索引、检索、运营 Tool/API、Runner 和 Runtime 共 `61/61`。

本轮没有调用对话模型，也没有执行项目全量回归。

## 6. 当前结论

当前失败来自业务范围和知识治理缺失，不是“向量能力不够”。因此暂不加入关键词检索、重排或复杂 Query Rewrite。后续知识规模扩大并出现可重复的召回或排序失败时，再使用同一冻结集做单变量消融。
