# RAG 检索与引用评测

> 本轮不只检查“回答看起来是否正确”，而是把知识检索和 Agent 决策拆开评测：先确认正确知识能否被找到，再确认 Agent 是否选对 Tool、使用正确证据并把来源展示给用户。

## 1. 为什么分成两层

如果只看最终回答，模型可能凭参数记忆答对，也可能检索到了错误文档但碰巧写出正确文字。两层评测分别回答：

| 层级 | 直接证据 | 主要问题 |
| --- | --- | --- |
| 检索层 | 返回码、Top1、Hit@3、分数、引用结构 | 正确知识是否进入上下文，无关问题是否被拒绝 |
| Agent 层 | Tool 轨迹、检索结果、最终回答 | 是否区分稳定规则与实时事实，是否真正引用了检索证据 |

实时积分、库存、任务、奖品和资格仍由业务 Tool 查询，RAG 只回答稳定规则。这一边界也被纳入 Agent 用例，而不是只写在 Prompt 中。

## 2. 数据集与通过口径

检索集共 `24` 条：在原有兑换规则、积分任务规则、Agent 能力边界和无关问题基础上，增加错别字、口语和冲突陈述。Agent 集共 `11` 条，覆盖三类稳定规则、三类实时业务事实、一个领域外问题，以及四条困难表达。

关键指标：

- `Top1 Accuracy`：第一条结果是否来自期望知识文档，用于观察排序质量。
- `Hit@3`：前三条结果中是否包含期望知识文档，代表 Agent 是否获得了正确证据。
- `Negative Rejection Rate`：无关问题是否返回 `NO_RELEVANT_KNOWLEDGE`。
- `Citation Valid Rate`：命中结果是否带有可读引用和可追踪来源。
- Agent Tool 选择率：稳定规则是否走 RAG，实时事实是否走对应业务 Tool。
- Agent 引用正确率：最终回答是否包含期望知识文档的真实引用，而非任意引用。

检索用例以“返回码正确、Hit@3 命中、引用结构有效”为通过条件；Top1 单独记录，避免因为第一条排序波动而误判整个 RAG 不可用，也避免用 Hit@3 掩盖排序退化。

## 3. 实测结果

### 3.1 检索层

使用阿里云 `text-embedding-v4` 和重新校准后的相关度阈值 `0.30`：

| 指标 | 结果 |
| --- | ---: |
| 用例通过 | `24/24` |
| Top1 Accuracy | `94.44%` |
| Hit@3 | `100%` |
| 无关问题拒答率 | `100%` |
| 引用结构有效率 | `100%` |
| 相关问题最高分范围 | `0.3446 ~ 0.7195` |
| 相关问题最高分均值 | `0.5627` |
| 无关问题最高分范围 | `0 ~ 0.0540` |
| 无关问题最高分均值 | `0.0092` |

旧阈值 `0.35` 会错误拒绝最高分为 `0.3446` 的口语用例，因此调整为 `0.30`；最高负样本仍只有 `0.0540`。Top1 唯一未命中的是重度错别字问题，正确知识位于 Top3，当前未因此强行引入重排。

### 3.2 Agent 层

首次运行有 `6/7` 通过。失败用例是“任务完成但奖励还没领取是什么意思”：Agent 正确调用了 `search_business_knowledge`，正确的积分规则进入 Top3，回答内容也正确，但最终文字漏写来源。由此可以确定问题不在检索阈值，而在回答阶段对 Prompt 的遵循具有波动。

修复后完整运行结果：

| --- | ---: |
| 用例通过 | `11/11` |
| Tool 选择正确率 | `100%` |
| Tool 执行完成率 | `100%` |
| 期望知识命中率 | `100%` |
| 引用正确率 | `100%` |
| 必需内容满足率 | `100%` |
| 关键结论忠实度 | `100%` |

## 4. 引用遗漏如何治理

引用不能只依赖 Prompt。统一回答出口现在会检查本轮 LangChain 消息：

1. 只读取名为 `search_business_knowledge` 的 Tool 消息。
2. 只提取 Tool 真实返回的 `citation`，不推测或编造来源。
3. 如果模型已经引用其中任一来源，保持原回答不变。
4. 如果模型遗漏全部来源，在回答末尾追加本轮“检索来源”。
5. 未调用 RAG、检索失败或没有匹配内容时不追加来源。

这是一层确定性后处理。它不改变模型答案，不把实时 Tool 结果伪装成知识引用，只解决“证据已经拿到但展示遗漏”的问题。

## 5. 复现方式与产物

```powershell
cd agent-service
.\.venv\Scripts\python.exe -m evals.rag_runner `
  --mode retrieval `
  --split all `
  --output evals\results\rag_retrieval_20260821.json

.\.venv\Scripts\python.exe -m evals.rag_runner `
  --mode agent `
  --output evals\results\rag_agent_20260821.json
```

用例在 `evals/rag_cases.json`，Runner 在 `evals/rag_runner.py`，原始结果保存在 `evals/results/`。Runner 会逐条输出进度，并把问题、回答、Tool 轨迹、检索结果和各项判定写入 JSON，便于复查失败原因。

## 6. 结论与边界

当前 RAG 已具备受控知识、真实向量索引、在线检索、低相关拒答、来源引用和正式评测闭环。现阶段没有证据表明必须为了课程覆盖改写成 LCEL；继续沿用 Agent Tool 编排更简单，也符合“没有实际问题就不增加抽象”的工程原则。

当前还增加了索引新鲜度启动门禁，并使用 `grounding_groups` 检查关键结论是否同时出现在答案和本轮目标知识片段中。该忠实度指标是可复查的业务结论覆盖，不等同于通用语义蕴含模型。

剩余风险是数据集规模仍小，尚未覆盖大量口语、省略表达、错别字、知识冲突和文档扩容后的排序变化。后续每次增加知识文档，都应先扩充冻结评估集，再重新验证阈值、Top1、Hit@3 和拒答率。
