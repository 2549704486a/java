# RAG 知识源治理与 Tool 边界

> RAG 不是把项目文件全部塞给模型，而是先决定哪些事实适合成为知识、谁对这些事实负责，以及内容变化后如何追踪。本阶段只建立可信知识原料，不实现向量检索。

## 1. 为什么先治理知识源

第五讲把 RAG 比作“开卷考试”：离线阶段准备文档、分块并向量化，在线阶段检索相关片段，再让模型依据片段回答。这个流程有一个隐含前提：放进知识库的内容本身是可信且适合被复用的。

积分系统同时存在两种完全不同的事实：

| 类型 | 示例 | 正确载体 |
| --- | --- | --- |
| 稳定规则 | 任务状态含义、兑换需要确认、处理中不等于成功 | RAG 知识文档 |
| 实时业务事实 | 当前积分、库存、价格、活动时间、资格、订单结果 | 业务 Tool |

如果把库存或用户积分写入 RAG，即使检索准确，回答也可能使用已经过期的数据。因此首要边界是：**RAG 负责解释，Tool 负责查询当前事实，写操作继续由受控状态机负责。**

## 2. 首批知识源

知识源位于 `agent-service/knowledge/documents/`：

| 知识 ID | 解决的问题 | 明确不包含 |
| --- | --- | --- |
| `points-and-tasks` | 积分获得方式、三种任务状态、积分规划语义 | 某用户积分、当前任务及奖励值 |
| `exchange-rules-and-status` | 兑换条件、确认机制、异步状态和未知结果 | 当前库存、当前资格、某次订单结果 |
| `agent-service-guide` | Agent 可以做什么、不能做什么、何时必须查 Tool | 当前用户和活动数据 |

每份文档的 `source_refs` 都指向当前项目源码或受控设计文档。文档与源码冲突时，以源码为准，先修正文档并提升版本，再重建索引。

## 3. 元数据与目录清单

每份 Markdown 使用 YAML Front Matter 记录：

- `knowledge_id`：稳定知识标识，不能因改标题而变化。
- `version`：单篇文档语义版本。
- `status`：`active`、`draft` 或 `retired`；只有 `active` 能进入索引。
- `audience`、`topics`：后续过滤和检索使用的元数据。
- `fact_scope`：当前强制为 `stable_rules_only`。
- `source_refs`：可以复查的项目内权威来源。

`manifest.json` 记录目录版本、知识 ID 和文档路径。内容变更时直接提升文档版本和目录版本，由 Git 保存差异和变更历史。

## 4. 确定性校验流程

```text
读取 manifest.json
        ↓
校验清单 Schema 和重复 ID
        ↓
校验文档路径没有越出 knowledge 目录
        ↓
解析 YAML Front Matter
        ↓
检查固定章节和项目内来源文件
        ↓
只输出 status=active 的受控文档
```

执行命令：

```powershell
cd D:\工作\incentive-事务消息\agent-service
.\.venv\Scripts\python.exe -m app.knowledge_catalog
```

当前自动化测试覆盖正常目录、目录穿越、重复 ID、摘要不一致和必需章节缺失。校验通过只证明“知识原料满足治理契约”，不代表检索质量已经合格。

## 5. 课程方法与项目增强

第五讲直接提供的方法包括：文档加载、递归切分、Embedding、向量存储、Top-K 检索、来源元数据，以及进一步使用混合检索、重排和问题改写优化效果。

本项目额外增加了以下工程约束：

- 把实时事实从 RAG 中剥离并强制走 Tool。
- 用项目内源码引用确认知识来源。
- 用目录版本、文档版本和 Git 历史管理变更。
- 在向量化前执行确定性校验，而不是运行时发现脏知识。

这些是基于课程原理做的项目化补充，不应描述成课程示例已经完整实现的能力。

## 6. 下一步

下一阶段在这批受控文档之上实现：

1. 保留标题和段落语义的递归切分，并把知识 ID、版本、来源写入每个 Chunk。
2. 建立可重复构建的本地向量索引，不提交临时索引文件。
3. 实现只读检索 Tool，回答必须给出来源；无可靠结果时拒绝回答。
4. 建立检索命中率、引用正确性、动态事实误答和无答案拒答用例。

在这些验证完成前，当前 Agent 不会自动加载本目录，也不会因为新增了知识文档而改变线上回答。
