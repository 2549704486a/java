# 本地演示数据基线

> 历史数据库主要是压测随机数据，用户积分普遍接近一千万，无法自然演示“当前能兑换什么”和“还差多少积分”。这份基线用少量、有关联的数据构造可解释的业务故事，服务于 Java 接口、Agent Skill 和手工联调，不用于性能压测。

## 1. 数据规模与覆盖场景

| 数据 | 数量 | 覆盖场景 |
| --- | ---: | --- |
| 用户 | 20 | 低积分、刚好可兑换、高积分 |
| 任务 | 6 | 已领取、完成待领取、尚未完成 |
| 奖品 | 6 | 实物、虚拟、可兑换、积分不足 |
| 库存分片 | 38 | 4 个普通实物奖品的分片库存 |
| 兑换记录 | 3 | 成功兑换与失败兑换 |

核心数据由 `sql/seed_demo_budou.sql` 生成。脚本只清理积分激励系统的 10 张核心业务表，不删除表结构，也不处理独立的锁测试表。

## 2. 用户 10 的主验证故事

- 当前积分：1680。
- 任务 1“每日签到”：已完成并领取奖励。
- 任务 2“浏览精选商品”：已完成但尚未领取 30 积分。
- 任务 3 至 6：当前可完成，合计奖励 430 积分。
- 6 号“智能手表”：需要 5000 积分，当前缺口 3320。

因此两个 Skill 应得到稳定结果：

1. `recommend_awards(limit=3)` 依次推荐智能手环、蓝牙耳机、视频会员月卡。
2. `plan_points_for_award(awardId=6)` 优先建议领取任务 2，再列出其余可做任务；总计可增加 460 积分，仍差 2860 积分。

## 3. 数据一致性约束

- 普通实物奖品的分片库存之和必须等于 `award_config.inventory`。
- `user_task.completedTasks` 必须等于该用户的任务完成记录数。
- `finish_task_record.status=1` 的记录必须存在对应积分流水，请求号为 `{userId}:{taskId}`。
- 成功兑换记录必须存在 `userId:{userId}-awardId:{awardId}` 幂等键。
- 用户积分、任务奖励、奖品价格和库存均不得为负数。

脚本执行后已验证上述约束，异常数均为 `0`。

## 4. 安全重置顺序

```text
停止 Java 和 Agent
  -> 备份 MySQL
  -> 清空项目专用 Redis
  -> 执行 seed_demo_budou.sql
  -> 启动 Java 和 Agent
  -> CacheWarmer 重新预热
  -> 验证 MySQL、Redis、Java 接口和 Skill
```

顺序不能颠倒。`DataSyncService` 会把 Redis 库存定期回写 MySQL；应用运行期间先改数据库，可能被旧缓存再次覆盖。

本轮重置前备份保存在 `.local-runtime/backups/budou_before_demo_seed_20260820_1915.sql`。该目录不提交 Git，只用于本机恢复。
