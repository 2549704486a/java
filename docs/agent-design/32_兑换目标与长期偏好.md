# 兑换目标与长期偏好

> 短期记忆解决“这一轮对话刚才说了什么”，长期记忆解决“用户下次回来时，哪些稳定信息仍值得记住”。本项目只保存用户明确确认的兑换目标与偏好，不把实时积分、库存、任务和订单状态当作记忆。

## 1. 用户场景

用户在会话 A 中说：

```text
请记住：我想在 9 月 1 日前兑换 6 号奖品。
```

Agent 查询奖品真实名称后，只生成预览：

```text
将城市随行保温杯（奖品 6）设为兑换目标，计划在 2026-09-01 前完成。
确认无误后请回复“确认保存”。
```

此时长期记忆仍为空。只有用户下一条消息明确回复“确认保存”，Runtime 才绕过模型原子写入。用户之后开启会话 B，询问“我的兑换目标是什么”，Agent 调用 `get_growth_memory` 仍能读到该目标。

## 2. 数据模型

### 2.1 已确认的兑换目标

```python
RedemptionGoalData(
    user_id=10,
    target_award_id=6,
    target_award_name="城市随行保温杯",
    target_date=date(2026, 9, 1),
    status="ACTIVE",
    created_at=datetime(2026, 8, 22, 15, 10),
    updated_at=datetime(2026, 8, 22, 15, 10),
    source_session="user:10:session:web-a",
)
```

`status` 不是永久写死的。每次读取都会用当前业务日期重新计算：目标日期已经过去时返回 `EXPIRED`，但不会擅自删除历史目标。

### 2.2 已确认的稳定偏好

```python
UserPreferenceData(
    user_id=10,
    preferred_categories=["实物", "会员"],
    disliked_categories=["优惠券"],
    task_preferences=["签到", "浏览"],
    created_at=datetime(2026, 8, 22, 15, 20),
    updated_at=datetime(2026, 8, 22, 15, 20),
    source_session="user:10:session:web-a",
)
```

偏好采用“完整替换”语义。修改前先读取旧偏好，将用户没有要求删除的部分合并进预览，避免一次局部修改意外覆盖其他偏好。

### 2.3 待确认草稿

```python
PendingMemoryChange(
    user_id=10,
    session_id="user:10:session:web-a",
    change_type="UPSERT_GOAL",
    payload={
        "target_award_id": 6,
        "target_award_name": "城市随行保温杯",
        "target_date": "2026-09-01",
    },
    summary="将城市随行保温杯（奖品 6）设为兑换目标，计划在 2026-09-01 前完成",
    created_at=datetime(2026, 8, 22, 15, 10),
    expires_at=datetime(2026, 8, 22, 15, 12),
)
```

草稿按“用户 + 会话”隔离且默认两分钟过期。浏览器只能拿到变更类型、摘要和过期时间，不能直接指定服务端要写入的 payload。

## 3. 完整流程

```text
用户明确要求记住目标或偏好
  -> 模型选择 prepare_* Tool
  -> Tool 校验日期、奖品和偏好冲突
  -> Redis 保存短期草稿
  -> 前端展示变更摘要
  -> 用户回复“确认保存/确认遗忘”
  -> Runtime 白名单识别专用口令
  -> 绕过模型，原子消费草稿并写长期记录
  -> 将确定性结果写回会话历史
```

读取、修改与遗忘分别对应：

| 用户意图 | Tool 或路径 | 是否立即改长期记忆 |
| --- | --- | --- |
| 查询目标和偏好 | `get_growth_memory` | 否，只读 |
| 新增或修改目标 | `prepare_redemption_goal` | 否，只生成草稿 |
| 新增或修改偏好 | `prepare_user_preferences` | 否，只生成草稿 |
| 遗忘目标/偏好/全部 | `prepare_forget_growth_memory` | 否，只生成删除草稿 |
| 确认保存或遗忘 | Runtime 确定性路由 | 是，原子执行 |
| 取消保存或遗忘 | Runtime 确定性路由 | 否，只删除草稿 |

## 4. 为什么不能让模型直接写长期记忆

模型适合识别自然语言意图和组织预览，但不适合充当最终授权者：

1. 用户说“我最近比较喜欢实物”可能只是闲聊，不等于要求永久保存。
2. 模型可能把“处理中”“当前积分 900”等动态事实错误沉淀，导致下次会话读取过时数据。
3. 模糊的“好的”“可以”可能同时指兑换、保存记忆或普通对话，不能作为写授权。
4. 多实例并发确认时，需要存储层保证同一草稿最多应用一次，Prompt 无法提供该保证。

因此项目采用与受控兑换相似、但口令和存储完全独立的模式：模型准备，用户确认，Runtime 执行，Store 保证原子性。

## 5. 存储与上下文边界

- 默认使用 Redis，目标和偏好按用户保存，因此可跨会话、跨 Agent 实例读取。
- 待确认草稿按内部 `thread_id` 保存，其他用户或会话不能确认。
- Redis 多实例确认使用事务监视和原子提交；并发请求中只有一个能消费草稿。
- 会话 TTL 或 LRU 淘汰时，只撤销该会话的待确认草稿，不删除已确认长期记忆。
- 上下文裁剪时，仍有效的草稿摘要会临时注入 System Message；草稿 payload 不依赖旧聊天记录。
- 来源会话用于服务端审计，`get_growth_memory` 不把它暴露给模型和用户。

## 6. 动态事实为什么不入记忆

假设用户确认目标时有 900 积分。第二天完成任务后已经有 1200 积分，如果把 900 写入长期记忆，规划会从错误起点计算。

正确分工是：

```text
长期记忆：目标奖品、目标日期、稳定偏好
实时 Tool：积分、库存、活动时间、任务状态、订单状态
RAG：稳定规则和操作说明
```

长期记忆提供“用户想做什么”，实时 Tool 提供“现在实际是什么”。

## 7. 验证证据

定向测试已覆盖：

- 草稿确认前不可见，确认后新会话可读取。
- 用户与会话隔离，其他用户无法确认草稿。
- 草稿过期后不写入。
- 目标日期过去后读取状态变为 `EXPIRED`。
- 遗忘必须二次确认，确认前原记录仍存在。
- 单进程与 Redis 双实例并发确认都只有一个请求成功。
- 记忆确认口令不会误触发兑换确认。
- LangChain Tool Schema 能把日期字符串校验为日期对象。
- HTTP 返回安全摘要，前端能展示保存/遗忘确认卡片。
- 长上下文裁剪后，待确认记忆摘要仍保留。

本阶段没有运行模型全量评测。原因是核心正确性由确定性状态机和存储测试覆盖；模型对自然语言目标、偏好和遗忘意图的稳定路由，将与下一阶段积分规划用例一起建立小型评测集。

## 8. 当前边界

- 每个用户当前只保留一个兑换目标和一份偏好集合。
- 偏好是用户主动维护的数据，不从历史对话自动抽取。
- 已实现目标过期标记，尚未实现到期提醒和自动重新规划。
- 长期记忆已共享，LangGraph 的完整对话检查点仍是进程内存储。
- 下一阶段用目标、实时积分、任务与规则生成可更新的积分计划。
