# 兑换目标与长期偏好

> 短期记忆解决“当前会话刚才说了什么”，长期记忆解决“用户下次回来时，哪些稳定信息仍值得使用”。根据 Agent 课程第七讲，本项目只保存稳定、可复用且由用户直接明确表达的信息；用户不必额外说“请记住”。实时业务事实、敏感信息、临时需求和模型推测不进入长期记忆。

## 1. 用户场景

用户在会话 A 中直接陈述偏好：

```text
我喜欢数码类奖品。
```

这是第一人称、对象明确且没有临时范围的稳定偏好陈述。Agent 先读取已有偏好，合并后直接保存：

```text
已记住：你喜欢数码类奖品。
```

用户不需要特意补充“请记住”，也不需要再回复一次“确认保存”。之后开启会话 B，询问“你记得我喜欢什么奖品吗”，Agent 调用 `get_growth_memory` 仍能读取该偏好。

兑换目标也可以通过明确指令保存：

```text
请记住：我想在 9 月 1 日前兑换 6 号奖品。
```

Agent 查询奖品真实信息并校验目标日期后直接保存：

```text
已记住：你的目标是在 2026-09-01 前兑换城市随行保温杯。
```

之后开启会话 B，询问“我的兑换目标是什么”，Agent 调用 `get_growth_memory` 仍能读取该目标。

以下表达不写入：

- “这次想看数码类奖品”：带有“这次”，只约束本轮推荐。
- “今天不想做浏览任务”：带有“今天”，属于临时状态。
- “这个杯子挺好看”：表达了评价，但没有明确形成奖品类别偏好。
- 用户连续点击或兑换数码奖品：这是行为事实，不能由模型推断成稳定偏好。

## 2. 数据模型

### 2.1 兑换目标

```python
RedemptionGoalData(
    user_id=10,
    target_award_id=6,
    target_award_name="城市随行保温杯",
    target_date=date(2026, 9, 1),
    status="ACTIVE",
    created_at=datetime(2026, 8, 22, 15, 10),
    updated_at=datetime(2026, 8, 22, 15, 10),
    source_session="user:10:session:web-a",
)
```

`status` 不是永久写死的。每次读取都会用当前业务日期重新计算：目标日期已经过去时返回 `EXPIRED`，但不会擅自删除历史目标。

### 2.2 稳定偏好

```python
UserPreferenceData(
    user_id=10,
    preferred_categories=["实物", "会员"],
    disliked_categories=["优惠券"],
    task_preferences=["签到", "浏览"],
    created_at=datetime(2026, 8, 22, 15, 20),
    updated_at=datetime(2026, 8, 22, 15, 20),
    source_session="user:10:session:web-a",
)
```

偏好采用“完整替换”语义。修改前先读取旧偏好，将用户没有要求删除的部分合并进完整列表，避免一次局部修改意外覆盖其他偏好。同一类别同时出现在喜欢与不喜欢列表时拒绝写入，并要求用户澄清。

## 3. 写入、读取与遗忘流程

```text
用户输入
  -> 判断是稳定陈述、临时条件，还是行为推断
  -> 临时条件或行为推断：只服务当前请求，不写长期记忆
  -> 稳定陈述、明确修改或遗忘：模型选择对应的 growth-memory Tool
       -> 更新偏好时先读取旧记忆并合并
       -> 校验奖品、日期、内容类别和偏好冲突
       -> 校验失败：拒绝写入并说明原因
       -> 校验成功：按 user_id 直接写入或删除 Redis
       -> 返回更新后的安全记忆数据
       -> Agent 告知用户处理结果
```

| 用户意图 | Tool | 结果 |
| --- | --- | --- |
| 查询目标和偏好 | `get_growth_memory` | 只读 |
| 新增或修改目标 | `save_redemption_goal` | 校验后立即保存 |
| 新增或修改偏好 | `save_user_preferences` | 校验后立即替换 |
| 遗忘目标、偏好或全部 | `forget_growth_memory` | 按明确范围立即删除 |

## 4. 记忆写入门槛

课程第七讲将适合长期记忆的信息概括为稳定、可复用、用户明确表达。本项目把它落实成以下规则：

| 信息 | 处理方式 | 例子 |
| --- | --- | --- |
| 第一人称、直接且稳定 | 直接保存 | “我喜欢数码类奖品” |
| 明确记忆指令 | 直接保存 | “请记住我更喜欢实物奖品” |
| 明确遗忘 | 直接按范围删除 | “忘掉我的兑换目标” |
| 本轮条件或临时情绪 | 不保存 | “这次想看数码类”“我今天不想做浏览任务” |
| 根据行为推断 | 不保存 | 因为用户兑换过数码奖品就推断其长期偏好 |
| 含糊或互相冲突 | 先澄清，不写入 | 同时说喜欢和讨厌优惠券 |
| 敏感信息 | 拒绝保存 | 密码、访问凭据、身份敏感数据 |
| 动态业务事实 | 每次调用实时 Tool | 当前积分、库存和订单状态 |

这里的“直接保存”并不等于“模型可以任意写”。模型只能调用结构化 Tool；Tool 负责字段校验、业务校验、用户隔离和来源记录。Prompt 要求稳定偏好必须由用户直接陈述，不能从行为、上下文或一次性选择中推断。

## 5. 更新、冲突与遗忘

第七讲强调记忆不是只写不管，还需要更新、冲突处理和遗忘：

- 兑换目标属于当前目标，新目标覆盖旧目标，同时保留最初创建时间并更新来源会话。
- 偏好属于可更新事实，新偏好使用完整列表替换旧偏好。
- 明确冲突不自动选择一方，返回 `CONFLICTING_PREFERENCES` 并要求澄清。
- 目标日期过去后标记为 `EXPIRED`，避免把陈旧目标当成当前计划。
- 用户可以遗忘目标、偏好或全部记忆；重复遗忘按幂等成功处理。

## 6. 存储与上下文边界

- 默认使用 Redis，目标和偏好按 `user_id` 保存，因此可跨会话、跨 Agent 实例读取。
- `source_session` 和更新时间用于服务端追踪，但不会暴露给模型和用户。
- 会话 TTL 或 LRU 淘汰只删除短期对话检查点，不删除长期目标和偏好。
- 长期记忆不会自动塞进每次 Prompt；模型在问题需要时调用 `get_growth_memory`，避免无关上下文膨胀。
- 积分、库存、活动时间、任务与订单继续由实时 Tool 提供，RAG 只提供稳定规则和说明。

## 7. 设计反思

旧方案偏离常规做法的根因不是技术实现错误，而是设计顺序错误：先复用了受控兑换的确认状态机，再反推记忆产品流程，形成了“已有技术方案牵引业务设计”。

正确顺序应当是：

1. 先判断操作后果和信息风险。
2. 再确定用户表达是否已经足够明确。
3. 最后选择直接写入、澄清、拒绝或高风险确认机制。

兑换会扣积分并改变库存，所以需要显式确认；普通目标和偏好在用户已经直接、明确表达时，不需要额外记忆口令或重复确认。两种写操作不能因为都“修改了状态”就使用同一种交互。

第二次纠偏解决的是另一个过度设计：删除二次确认后，系统仍要求用户必须说“请记住”，导致“我喜欢数码类奖品”只作为本轮推荐条件。课程中的“用户明确表达”指信息本身由用户明确陈述，而不等于必须使用固定记忆口令。因此当前实现按表达语义判断稳定性，而不是按关键词判断授权。

## 8. 验证证据与当前边界

定向测试覆盖：

- 明确目标调用后立即可见，并可在新会话读取。
- 不同用户的长期记忆相互隔离。
- 目标日期无效时不写入，日期过去后返回 `EXPIRED`。
- 偏好规范化、完整替换和冲突拒绝。
- 第一人称稳定偏好陈述可以直接写入，不要求“请记住”。
- 带“这次、今天、当前、先”等临时范围的表达不写入。
- 不根据浏览、兑换或推荐选择推断长期偏好。
- 遗忘立即生效，重复遗忘保持幂等。
- 内存与 Redis 两种存储遵循同一接口。
- HTTP 和前端不再暴露记忆确认状态。
- 原有兑换确认流程不受影响。

当前每个用户只保留一个兑换目标和一份偏好集合；尚未实现从历史对话自动抽取候选记忆、记忆重要性评分和审计版本历史。下一阶段先让动态积分计划消费这些已保存目标，再根据真实业务需求决定是否继续扩展。
