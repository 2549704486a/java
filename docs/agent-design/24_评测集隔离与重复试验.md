# 评测集隔离与重复试验

> 这一轮解决两个容易让 Agent 评测“看起来很好、实际上不可信”的问题：用已经参与调优的题目充当考试，以及只跑一次就把随机结果当成稳定能力。核心做法是把公开调优集与冻结盲测集分开，并让同一用例重复运行后报告通过率和波动。

## 1. 为什么要拆成两套用例

| 数据集 | 文件 | 用途 | 是否允许依据结果调 Prompt |
| --- | --- | --- | --- |
| 调优/回归集 | `agent-service/evals/cases.json` | 日常开发、定位失败、离线重评分 | 允许 |
| 冻结盲测集 | `agent-service/evals/blind_cases.json` | 阶段验收、检验未见表达的泛化能力 | 不允许直接针对原题调优 |

原有 `cases.json` 已经参与过 Prompt、Tool 和评分规则调整，因此只能证明“已知行为没有回归”，不能继续被称为独立盲测。新盲测集使用独立编号和不同表达方式，当前首批包含 8 个确定性 Fixture 场景。

这里的“隐藏”是工程流程隔离，不是密码学保密。用例仍在同一代码仓库中，维护者有权限查看；可信度来自以下纪律：

1. 日常开发只运行和查看调优集。
2. 盲测只在阶段验收时运行，默认产物不保存问题、回答、期望短语和完整轨迹。
3. 在看到盲测结果前冻结用例文件，并在评测元数据中记录固定版本标识。
4. 盲测失败时先记录本次结论，再由指定维护者开封定位；被用于修复的题目应转入调优集，并补一条新的未见盲测题。

## 2. 如何运行

公开调优集单次回归保持向后兼容：

```powershell
.\.venv\Scripts\python.exe -m evals.runner --suite fixture
```

关键用例建议重复至少 3 次：

```powershell
.\.venv\Scripts\python.exe -m evals.runner `
  --dataset tuning `
  --suite fixture `
  --repeat 3
```

阶段验收时再运行盲测：

```powershell
.\.venv\Scripts\python.exe -m evals.runner `
  --dataset blind `
  --suite fixture `
  --repeat 3
```

盲测控制台只显示用例 ID、通过状态和耗时；保存的 JSON 也只保留身份无关的聚合证据与各检查项布尔值。盲测结果因缺少原始回答和轨迹，不能直接使用 `rescore.py` 离线重评分。

## 3. 指标如何解释

### 3.1 单次结果与稳定性状态

| 状态 | 含义 |
| --- | --- |
| `single_pass` / `single_fail` | 只运行 1 次，只能描述本次结果，不能声称稳定 |
| `stable_pass` | 重复至少 2 次且全部通过 |
| `flaky` | 同一用例有时通过、有时失败，说明模型行为存在波动 |
| `stable_fail` | 重复至少 2 次且全部失败 |

每个用例同时记录：

- `pass_rate`：通过次数除以运行次数。
- `average_elapsed_ms`：多次调用的平均耗时。
- `p95_elapsed_ms`：使用 nearest-rank 方法得到的 P95。
- `elapsed_stddev_ms`：总体标准差，用于观察耗时波动。

整体汇总还会记录总尝试次数、尝试级通过率、稳定通过用例数、波动用例数和稳定失败用例数。模型能力判断优先看“关键用例是否稳定通过”，不能只看所有尝试混在一起的平均通过率。

### 3.2 为什么重复运行仍有意义

当前模型温度为 0，但这不等于整个 Agent 链路严格确定：模型服务实现、工具时延、上下文和上游依赖仍可能产生变化。重复试验可以发现单次满分掩盖的偶发路由错误或表达失败。

## 4. 本轮边界

本轮完成的是评测基础设施升级，没有调用真实模型生成新的能力结论。已经通过单元测试验证数据集隔离、稳定性聚合、P95/标准差计算和盲测结果脱敏。
