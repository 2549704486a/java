# 单体智能运营 Agent 与工作台

> 本阶段把已有的运营快照、运营知识和活动草案能力组织成一个真正可对话的产品入口。先用单 Agent 建立基线，不提前引入 MCP 或多 Agent；只有后续出现稳定的职责冲突或第二个真实调用方，才验证更复杂的架构。

## 1. 产品边界

运营 Agent 可以完成：

1. 读取服务端计算的客群、任务、奖品库存和历史指标快照。
2. 查询当前有效的运营制度、奖品说明、异常手册和历史案例。
3. 收集活动目标、客群、现金预算、积分发放上限和时间窗口。
4. 生成结构化、可追踪、不可直接发布的活动草案。

运营 Agent 不能完成：

- 直接发布活动。
- 修改线上规则或库存。
- 绕过人工审核触达用户。
- 在实时事实或制度不可用时编造数据。

## 2. 调用链

```text
运营工作台 /operator
  -> POST /v1/operator/chat
  -> 独立运营令牌与服务端权限校验
  -> OperatorAgentRuntime
  -> 运营 Agent 选择 Tool
     -> get_campaign_planning_snapshot
     -> search_operator_knowledge
     -> draft_campaign_plan
  -> 返回带事实依据或知识引用的回答
```

运营 Tool 与普通用户 Tool 分开注册，因此用户端 Agent 不会获得活动草案权限。运营对话按 `operator_id + session_id` 隔离，并对同一会话串行执行，避免并发请求交错写入短期上下文。

## 3. 数据模型实例

### 3.1 运营身份

```json
{
  "operator_id": "local-operator",
  "permissions": ["campaign:read", "campaign:draft"]
}
```

`campaign:read` 允许读取快照和运营知识；`campaign:draft` 允许生成草案。权限由服务端 `.env` 配置，不能由浏览器自行声明。

### 3.2 对话请求

```json
{
  "session_id": "campaign-20260824-01",
  "message": "为积分不少于500的用户策划活动，现金预算1000元，积分上限5000，活动持续7天"
}
```

现金预算在自然语言中可以使用元，但调用草案 Tool 时转换为分；积分发放上限仍是独立字段，不能用积分反推奖品成本。

### 3.3 对话响应

```json
{
  "request_id": "web-2bc...",
  "session_id": "campaign-20260824-01",
  "operator_id": "local-operator",
  "answer": "已生成一份待人工审阅的活动草案……",
  "elapsed_ms": 842.6
}
```

`request_id` 用于关联 HTTP、Agent 和 Tool 轨迹；`session_id` 用于延续同一场活动策划上下文。

## 4. 为什么先用单 Agent

当前三个能力围绕同一个“生成运营草案”目标，职责冲突还不明显。单 Agent 可以提供更低的调用成本、更短的链路和更容易理解的故障现场，也为后续多 Agent A/B 提供必要基线。

当实际用例稳定出现以下问题时，再考虑拆分策划、分析和审核角色：

- 同一上下文中频繁混淆事实分析与规则审核。
- 单 Agent 稳定遗漏某类约束。
- 不同角色需要真正不同的权限或知识范围。

## 5. 验证结果

- Python 定向测试：运营 Agent、运营 API、用户引用兼容性共 `12/12` 通过。
- 前端：`npm run build` 通过，TypeScript 检查和 Vite 生产构建成功。
- 本阶段未执行全量回归；等草案持久化与人工审核模块完成后统一进行里程碑回归。

## 6. 下一步

下一阶段不是让 Agent 直接发布，而是建立草案事实源：持久化草案、版本号、创建人、状态和审计记录，再增加人工审核状态机。发布动作只能由审核通过后的确定性服务执行。
