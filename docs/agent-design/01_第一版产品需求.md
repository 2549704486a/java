# 积分规划与奖品兑换顾问：第一版产品需求

> 第一版不追求让 Agent 代替所有页面操作，而是解决普通接口难以一次完成的多步问题：用户选定奖品后，Agent 查询积分、任务和奖品，计算缺口并给出可执行的积分获取方案。

## 1. 产品定位

Agent 是积分激励系统之上的自然语言业务助手，不是秒杀系统本身，也不是订单查询页面的替代品。

核心问题：

> 我想兑换某个奖品，目前是否满足条件；如果积分不足，应该完成哪些任务？

## 2. 第一版用户流程

```text
用户提出目标奖品
  -> Agent 补齐用户和奖品参数
  -> 查询用户积分
  -> 查询奖品价格、库存和有效期
  -> 检查兑换资格并计算积分缺口
  -> 查询尚可参与或已完成待领奖的任务
  -> 生成积分获取方案
  -> 用户自行前往页面完成任务或兑换
```

## 3. 功能范围

第一版包含：

- 查询用户当前积分。
- 查询有效任务及用户任务状态。
- 查询奖品详情和当前可兑换奖品。
- 检查兑换资格，返回明确的原因码和积分缺口。
- 根据工具返回的数据生成积分获取建议。
- 参数缺失时追问，工具失败时明确告知。

第一版不包含：

- 自动发起兑换或领取任务奖励。
- 用 Agent 代替页面轮询兑换结果。
- 直接访问 MySQL、Redis、RocketMQ。
- 长期记忆、MCP、多 Agent。
- 新兑换链路或历史压测资料。

## 4. 数据与规则边界

- 积分、库存、任务状态和订单状态属于动态事实，必须调用 Java 业务接口。
- 活动说明和积分规则后续可进入 RAG，第一版不建设知识库。
- Agent 只负责理解目标、选择工具和解释结果，不能自行编造任务或修改工具数据。
- 第一版通过请求参数传入 `userId` 便于联调；正式接入时必须由登录态提供用户身份。
- 后续开放兑换时只调用旧链路 `/userAward/exchange`，并增加明确确认、权限、幂等和审计。

## 5. 核心输出

Agent 的积分方案至少包含：

- 当前积分。
- 目标奖品和所需积分。
- 积分缺口。
- 推荐任务、单项奖励和任务状态。
- 完成推荐任务后的预计积分。
- 无法给出方案时的明确原因。

## 6. 第一版验收标准

- 缺少用户或奖品参数时不调用错误工具，而是先追问。
- 积分缺口计算正确，积分充足时不推荐多余任务。
- 只推荐接口返回的有效任务，不虚构奖励积分。
- 已完成待领奖任务与尚未完成任务能被清楚区分。
- 用户已经兑换、活动结束、库存不足时返回准确原因。
- 任一工具异常时不继续编造完整方案。
- 用户要求直接改积分、库存或消息状态时明确拒绝。

## 7. 后续演进

1. 使用 RAG 补充积分规则、任务说明和活动 FAQ。
2. 使用会话记忆保存目标奖品和任务偏好，但不保存动态业务事实。
3. 使用确定性工作流增加“检查条件 -> 用户确认 -> 调用旧链路”的受控兑换。
4. 工具稳定且需要被多个客户端复用时，再封装 MCP Server。
