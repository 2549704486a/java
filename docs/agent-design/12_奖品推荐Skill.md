# 奖品推荐 Skill

> “查看全部奖品”是一次列表查询，“推荐适合我的奖品”则需要结合当前用户积分和每个奖品的实时资格做筛选与排序。第二个 Skill 用来验证 Agent 能否在基础查询、积分规划和奖品推荐之间正确路由。

## 1. 业务目标与边界

支持以下问题：

- 我现在能兑换哪些奖品？
- 推荐一个当前可兑换的奖品。
- 在可兑换范围内，优先推荐能更充分利用积分的奖品。

当前仍然只读，不自动兑换，也不直连数据库和中间件。动态积分与兑换资格全部来自 Java `/agent/query/**` 接口。

## 2. 完整调用流程

```text
用户提出奖品推荐需求
  -> 模型根据 Skill 目录命中 award-recommendation
  -> 调用 load_skill 读取完整 SKILL.md 正文
  -> 模型按照正文调用 recommend_awards
  -> Runtime 注入当前 user_id
  -> 查询实时积分
  -> 查询带资格判断的活动奖品列表
  -> Pydantic 校验嵌套响应
  -> 确定性代码过滤与排序
  -> 模型解释结构化推荐结果
```

确定性业务代码位于 `app/services/award_recommendation.py`。代码中的三个步骤级注释分别标记查询、数据校验和推荐计算，便于沿主流程阅读。

## 3. 为什么规则不写进 Prompt

Prompt 只告诉模型何时使用 Skill，不让模型自行判断库存或计算排序。确定性代码执行以下规则：

1. 只保留 Java 后端已经判定 `redeemable=true` 的奖品。
2. 再检查库存大于零、所需积分为正且不超过当前积分。
3. 按所需积分从高到低排序，使推荐结果更充分利用积分。
4. 所需积分相同时按奖品 ID 排序，保证结果稳定可复现。
5. 用户说“推荐一个”时只返回一个，最大推荐数量限制为五个。

这样做可以独立单测规则，也不会因更换模型而改变业务计算结果。

## 4. Tool、Skill 与数据契约

| 层次 | 载体 | 作用 |
| --- | --- | --- |
| Skill 正文 | `skills/award-recommendation/SKILL.md` | 告诉模型何时推荐、调用哪个 Tool、怎样处理失败 |
| 加载 Tool | `load_skill` | 命中任务后把 Skill 正文送入模型上下文 |
| 业务 Tool | `recommend_awards` | 向模型暴露 `limit` 参数并调用推荐 Service |
| Service | `app/services/award_recommendation.py` | 编排两个查询并执行确定性推荐 |
| 数据契约 | `UserPointsData`、`AwardOptionData`、`AwardRecommendation` | 校验 Java JSON 并稳定输出结构 |

奖品列表真实结构是 `AwardOptionView` 外层包含资格信息、内层包含 `award`。如果缺少嵌套奖品字段，Service 返回 `INVALID_BUSINESS_RESPONSE`，不会把残缺数据交给模型猜测。

## 5. 验证结果

- 当时的单元测试：项目全量 `25/25` 通过，其中推荐 Service 新增 5 个确定性测试。
- 当时的业务验证：用户 10 当前有 1680 积分，按顺序返回智能手环、蓝牙耳机和视频会员月卡。
- 积分规划：兑换 6 号智能手表还差 3320 积分；领取待领取奖励并完成全部可用任务后仍差 2860 积分。
- 完整 Fixture：原 15 例加 3 例多 Skill 路由，共 `18/18` 通过。

定向评测中 E18 首次被判失败，是因为模型调用 `list_awards` 时省略了默认参数 `redeemable_only=false`。Tool 选择和后端路径均正确，因此删除对可选默认参数的显式检查后，使用原始模型输出离线重评分得到 `3/3`，没有重新调用模型碰结果。

## 6. 当前限制

- “充分利用积分”当前定义为优先所需积分更高，不代表用户真实偏好。
- 尚未支持奖品类型、名称、库存阈值等偏好过滤。
- 推荐依据是当前瞬时状态，用户真正兑换时仍需由旧链路重新校验资格。
