# Agent 开发问题与解决方案复盘

> 这份文档总结的不是普通代码缺陷，而是开发 Agent 时更容易反复踩到的工程问题：模型到底该不该做这件事、为什么回答看起来正确但过程仍然错误、问题应该修在 Prompt 还是确定性代码、知识和记忆怎样避免污染，以及什么时候不应该引入一项新技术。

## 1. 范围与证据

本次盘点交叉检查了：

- `docs/agent-design/01~47` 的需求、实现、评测和复盘；
- `docs/agent-journal/任务日记.md` 的开发记录；
- `agent-service/tests` 中已经固化的行为边界；
- 当前代码中的 Agent、Tool、Skill、记忆、RAG、运营工作流和运行时；
- Git 历史以及曾经完成后又整体回滚的 MCP 模块。

本文刻意排除以下内容：

- 编译错误、依赖兼容、字段映射、测试数据字段写错等普通代码缺陷；
- Redis 未预热、服务没有重启、页面路由未挂载等环境或部署问题；
- 单个接口的偶发实现错误。

问题按证据分为三类：

| 标记 | 含义 |
| --- | --- |
| `真实失败` | 已经在评测、日志或手工对话中复现，有直接数据 |
| `设计纠偏` | 在实现或评审阶段发现原方案有系统性风险，先于线上事故修正 |
| `暂缓问题` | 问题存在，但当前业务证据不足，明确不靠堆技术强行解决 |

## 2. 全景结论

项目中遇到的问题可以归纳为九类：

| 类别 | 最核心的问题 | 最终原则 |
| --- | --- | --- |
| Agent 定位 | 把固定流程也交给模型 | 固定流程用页面/API，Agent 只处理理解、选择和组合 |
| Tool 与 Prompt | 回答正确但 Tool 调错、调多或参数没有真正传入 | 模型负责选择，Tool Schema 承接约束，Skill 确定性执行 |
| 评测 | 只看最终文字、关键词误判、反复重跑碰结果 | 同时评答案、轨迹和硬约束，保留原始结果并离线复核 |
| 会话状态 | 用户、会话、请求混用；裁剪破坏 Tool 消息序列 | 身份、会话和请求分离，按完整轮次治理上下文 |
| 高风险写操作 | 让模型承担确认、授权、幂等和未知状态判断 | 模型只参与交互，服务端状态机决定能否执行 |
| RAG | 命中不等于可信，引用不等于有依据 | 治理知识源、时效、受众、忠实度和本轮证据 |
| 长期记忆 | 过度确认、Schema 绑架用户、全量记忆污染上下文 | 忠实保存原意，原子化存储，按任务召回 |
| 智能运营 | 模型把咨询当执行，或凭空编造运营事实 | 意图分流，事实由系统提供，发布由确定性工作流完成 |
| 架构演进 | 为覆盖课程或展示技术而提前增加复杂度 | 先有稳定问题和复用方，再用 A/B 证明新技术价值 |

## 3. Agent 定位、Tool 与 Prompt

### 3.1 固定流程被错误地包装成 Agent

- **证据类型：**设计纠偏。
- **问题：**兑换结果查询、订单列表、页面跳转都有确定输入和确定输出。如果包装成自然语言 Agent，不仅多一次模型调用，还会增加误解和延迟。
- **解决：**订单和异步结果由普通页面及只读 API 展示；Agent 负责“目标不完整、需要组合积分、任务、奖品等事实”的规划问题。
- **状态：**已解决。见 `01_第一版产品需求.md`、`04_最小Agent实现.md`、`43_兑换最终结果查询闭环.md`。

### 3.2 模型过度调用 Tool

- **证据类型：**真实失败。
- **现象：**第一轮 15 个场景的必要回答内容已经 `15/15`，严格轨迹却只有 `5/15`；总 Tool 调用达到 `33` 次。模型会提前查无关信息，也会在已有组合 Skill 时继续调用基础 Tool。
- **根因：**Tool 都“看起来可能有帮助”，Prompt 没有最小调用原则，也没有说明何时应追问、拒绝或立即停止。
- **解决：**加入最小 Tool 决策表：参数缺失先追问，高风险越权请求零 Tool 拒绝，组合 Skill 已覆盖的信息不重复查，失败后停止。
- **结果：**固定集达到 `15/15`，Tool 调用由 `33` 降到 `12`。
- **状态：**已解决。见 `07_第一轮Agent评测报告.md`。

### 3.3 Tool 失败后继续试探并猜测原因

- **证据类型：**真实失败。
- **现象：**用户不存在时，回答擅自推测为登录异常；业务数据格式异常时，模型继续调用多个 Tool，试图用其他结果补齐。
- **根因：**模型把“尽量帮助用户”理解为“必须给出一个解释”，没有把下游错误当成事实边界。
- **解决：**Tool 返回稳定结果码；Prompt 要求不可重试失败立即停止，只复述已知事实，不猜测后台原因，不基于残缺数据继续规划。
- **状态：**已解决。见 `07_第一轮Agent评测报告.md`、`02_工具契约.md`。

### 3.4 最终回答正确，但约束没有进入执行链

- **证据类型：**真实失败。
- **现象：**复杂规划用例 `P08` 最终确实避开了用户不想做的任务，但排除条件没有出现在 Tool 参数中，属于模型碰巧选对。`P01` 为理解“不要分享”，先查一次任务，再由组合 Skill 重复查询。
- **根因：**自然语言里有约束，Tool Schema 却只能接收 ID，模型无法把约束可靠地传给确定性计算。
- **解决：**扩展规划 Tool 的允许/排除任务名称参数；Skill 读取一次实时任务后确定性匹配和过滤，不依赖模型在答案阶段自行删选。
- **结果：**`P01` 从 2 个 Agent Tool、2 次任务查询、3 次模型调用，降为各 1 次 Tool/查询和 2 次模型调用；耗时由 `8320ms` 降至 `5031ms`。
- **状态：**已解决。见 `36_复杂规划评测与任务约束.md`。

### 3.5 Skill 声明、Tool 描述和运行时行为可能漂移

- **证据类型：**设计纠偏。
- **问题：**如果 `SKILL.md`、Tool 描述和真实参数分别维护，模型看到的说明可能已经过期；伪造一个没有真实加载行为的 `load_skill` 也只是在展示概念。
- **解决：**启动时校验 Skill 声明，Tool 描述从声明动态生成；Skill 是业务能力契约，不额外制造虚假的“加载动作”。
- **状态：**已解决。见 `09_Skill运行时标准化.md`。

### 3.6 把每个失败原句都塞进 System Prompt

- **证据类型：**设计纠偏。
- **问题：**针对单个 Case 不断补关键词，短期可能提分，长期会导致 Prompt 膨胀、规则冲突和过拟合。
- **解决：**只把可泛化的决策规则放入 System Prompt；Skill 专属知识放在 Skill；确定性约束放入 Tool Schema 或代码；评分器问题只修评分器。
- **状态：**作为持续规则执行。见 `08_Agent评测体系升级.md`。

## 4. 评测与可观测性

### 4.1 只看最终回答，掩盖错误调用过程

- **证据类型：**真实失败。
- **问题：**模型可能先调错 Tool、重复请求、使用错误参数，最后仍拼出正确答案。只验文字会把高延迟、高成本和潜在副作用判为成功。
- **解决：**同时保存模型声明的 Tool Call、代码真实执行轨迹和 Fixture 后端路径；分别评分答案、参数、调用顺序、调用次数和硬约束。
- **状态：**已解决。见 `14_Tool调用链可观测性.md`。

### 4.2 关键词评分产生假阴性和假阳性

- **证据类型：**真实失败。
- **现象：**回答“业务数据格式异常”在语义上正确，却因规则只匹配另一种说法而失败；可选参数使用默认值时，也曾被评分器误判为模型遗漏。
- **解决：**保留原始模型输出；人工复核失败样本；给评分器增加受控同义表达或契约等价判断，再使用离线工具重评分，不重新调用模型碰满分。
- **状态：**已解决，但仍需持续校准。见 `07_第一轮Agent评测报告.md`、`12_奖品推荐Skill.md`。

### 4.3 用调优集证明泛化能力

- **证据类型：**设计纠偏。
- **问题：**一边看失败样本改 Prompt，一边继续用同一批用例宣称能力稳定，只能证明回归通过，不能证明对新表达有效。
- **解决：**拆分调优集和隔离的保留集；调优集用于快速回归，保留集不向开发过程披露完整内容。
- **状态：**已解决基础设施，Judge 校准仍暂缓。见 `24_评测集隔离与重复试验.md`。

### 4.4 单次通过被误认为稳定

- **证据类型：**设计纠偏。
- **问题：**即使温度较低，模型路由和措辞仍可能波动。一次通过无法区分稳定能力和偶然成功。
- **解决：**关键用例重复运行，记录 `stable_pass`、`flaky`、`stable_fail`；高风险行为使用确定性硬门禁，不被平均分掩盖。
- **状态：**重复试验已实现；完整安全门禁按计划暂缓。

### 4.5 指标为零不一定代表真实消耗为零

- **证据类型：**设计纠偏。
- **问题：**模型网关没有返回 Token 明细时，`0` 可能表示“没有遥测”，而不是“没有消耗”；没有配置单价时也不能把成本写成零。
- **解决：**区分 `0`、`unknown` 和 `not_reported`；拆分总耗时、模型耗时、Tool 耗时和模型调用次数。
- **状态：**已解决基础统计。见 `25_Agent评测耗时Token与成本指标.md`。

### 4.6 每个小改动都执行全量回归，反馈周期过长

- **证据类型：**开发过程纠偏。
- **问题：**频繁全量模型回归耗时、耗费调用额度，也会让开发者把大量时间花在等待上。
- **解决：**小改动执行模块单测和失败用例定向复验；模块完成后执行阶段回归；里程碑或发布前再跑全量。任何未跑的范围必须明确写出，不能默认成“已通过”。
- **状态：**当前采用的测试策略。

## 5. 会话、上下文与运行时

### 5.1 用户 ID、会话 ID、请求 ID 职责混淆

- **证据类型：**设计纠偏。
- **问题：**用户 ID 决定数据权限，会话 ID 决定对话上下文，请求 ID 只关联一次调用的日志。混用会造成串会话、越权或无法排障。
- **解决：**会话键绑定用户与 session；请求 ID 只透传日志和 Tool 轨迹；身份只能来自服务端认证结果。
- **状态：**已解决。

### 5.2 同一用户绑定的 Tool 使 Agent 不能跨用户共享

- **证据类型：**设计纠偏。
- **问题：**Tool 闭包带有用户身份，若全局复用 Agent 实例，可能把一个用户的调用上下文带给另一个用户。
- **解决：**按用户缓存 Agent，使用有界 LRU 和空闲淘汰；共享的是 HTTP 连接池，不是用户绑定的 Tool 实例。
- **状态：**已解决。见 `10_Agent服务化.md`。

### 5.3 同会话并发请求导致消息顺序错乱

- **证据类型：**设计纠偏。
- **问题：**两个请求同时读写同一 checkpoint，后返回的旧请求可能覆盖较新的上下文。
- **解决：**对同一会话串行执行，不同会话仍可并发。
- **状态：**已解决。见 `11_短期记忆与会话隔离.md`。

### 5.4 按消息条数裁剪，切断 Tool 调用序列

- **证据类型：**真实边界测试。
- **问题：**AI 的 Tool Call 和对应 ToolMessage 是一组协议消息。简单截断可能只留下其中一半，形成模型无法理解的上下文。
- **解决：**按完整用户轮次裁剪，同时控制轮数和 Token；当前轮的 Tool 序列不可拆开。
- **状态：**已解决并有定向测试。

### 5.5 重要业务状态只存在聊天历史中

- **证据类型：**设计纠偏。
- **问题：**待确认兑换若只依赖历史消息，历史被裁剪、会话淘汰或进程重启后就无法可靠恢复。
- **解决：**对话历史只帮助表达；待确认状态从确认存储实时注入。短期 checkpoint 与业务状态分离。
- **状态：**确认状态已解决；短期 checkpoint 的多实例共享仍是暂缓问题。

## 6. 高风险写操作

### 6.1 仅靠 Prompt 判断“用户已经确认”

- **证据类型：**设计纠偏。
- **问题：**“好”“就这个”“确认”等表达存在歧义，历史还可能被裁剪；模型重试也可能重复调用写 Tool。
- **解决：**服务端创建绑定用户、会话和奖品的一次性确认状态；用户确认后由运行时确定性路由，原子地从 `PREPARED` 迁移为执行中，模型不做最终授权判断。
- **状态：**已解决。见 `15_受控兑换Skill需求与状态机.md`、`19_受控兑换Skill实现.md`。

### 6.2 把内部确认凭证暴露给模型

- **证据类型：**设计纠偏。
- **问题：**模型无需知道内部凭证；让它复制和选择凭证只增加泄漏、误用和路由不确定性。
- **解决：**前端只展示安全摘要；运行时从当前会话的共享存储查找待确认记录并执行。
- **状态：**已解决。

### 6.3 确认状态只放进程内存

- **证据类型：**设计纠偏。
- **问题：**重启后状态消失，多实例下创建和确认可能落在不同进程，并发确认也难以保证只执行一次。
- **解决：**使用 Redis 共享状态和原子迁移；存储不可用时失败关闭，不静默退回内存。
- **状态：**已解决。见 `22_Redis确认凭证共享存储.md`。

### 6.4 把消费者幂等误当成请求入口幂等

- **证据类型：**设计纠偏。
- **问题：**消费者唯一键只能避免最终业务记录重复，不能阻止入口重复发送事务消息和重复占用资源。
- **解决：**确认 ID 同时作为请求幂等键，在发送消息前持久化请求结果；消费者仍保留业务唯一键，两层分别治理“重复受理”和“重复落库”。
- **状态：**已解决。见 `21_Java兑换请求持久化幂等.md`。

### 6.5 网络超时后自动重试写请求

- **证据类型：**设计纠偏。
- **问题：**客户端超时不代表服务端没有受理。立即重试可能重复写入。
- **解决：**返回 `SUBMISSION_UNKNOWN` 时不自动重试，通过订单事实查询收敛最终状态。
- **状态：**订单查询闭环已完成；固定真实端到端回归按用户决定暂缓。

### 6.6 相信请求体中的用户 ID

- **证据类型：**设计纠偏。
- **问题：**客户端若能自行填写用户 ID，就可以查询或操作别人的数据。
- **解决：**身份从服务端校验过的令牌获得，请求模型禁止出现用户 ID；认证、确认授权和幂等分别解决“是谁”“能否执行”“是否已执行”。
- **状态：**已解决。见 `23_Agent可信用户身份.md`。

## 7. RAG

### 7.1 把所有项目文件都塞进知识库

- **证据类型：**设计纠偏。
- **问题：**源码、日志、内部状态码和过时文档会稀释真正面向用户的规则，还可能暴露内部实现。
- **解决：**只将稳定、可解释、有来源的业务规则纳入知识目录；实时积分、库存和资格由 Tool 查询；写操作仍走状态机。
- **状态：**已解决。见 `26_RAG知识源治理与Tool边界.md`。

### 7.2 只按固定长度切分文档

- **证据类型：**设计纠偏。
- **问题：**标题和正文可能分离，检索命中一段话却不知道它属于哪条规则。
- **解决：**先按 Markdown 标题形成语义章节，再对超长章节递归切分；每个 Chunk 保留文档、章节、版本、受众和来源元数据。
- **状态：**已解决。见 `27_RAG文档切分与本地向量索引.md`。

### 7.3 建索引失败后留下半新半旧数据

- **证据类型：**设计纠偏。
- **问题：**直接覆盖正式集合时，Embedding 或写入中途失败会破坏可用索引。
- **解决：**先构建临时集合，全部成功后再切换；启动时校验目录版本、文档 ID 和版本，索引不完整或过期时拒绝启用 RAG。
- **状态：**已解决。

### 7.4 没有可靠命中时，模型仍用自身记忆补答案

- **证据类型：**设计纠偏。
- **问题：**业务规则看起来常识化，模型很容易在无证据时给出流畅但不可验证的结论。
- **解决：**检索层返回结构化的无相关知识；Agent 明确拒答；关键结论通过 `grounding_groups` 检查“回答中出现的结论是否能在本轮检索证据中找到”。
- **状态：**已解决基础门禁。见 `28_RAG只读检索与来源引用.md`、`31_RAG索引新鲜度与答案忠实度.md`。

### 7.5 模型忘记引用，或引用正确但答案仍无依据

- **证据类型：**真实失败。
- **现象：**首轮 Agent RAG 评测为 `6/7`，知识已正确进入 Top3，答案也正确，但模型漏掉来源。反过来，带着一个真实引用也不代表回答中的每个关键结论都来自该引用。
- **解决：**只从本轮真实知识 Tool 结果确定性补充来源；引用评测与答案忠实度评测分开。
- **状态：**已解决。见 `29_RAG检索与引用评测.md`、`31_RAG索引新鲜度与答案忠实度.md`。

### 7.6 面向用户的回答泄露内部术语

- **证据类型：**真实失败。
- **问题：**模型会照抄服务端状态码、Tool 名称或内部处理语义，用户看不懂，也可能把“处理中”误解为成功。
- **解决：**知识正文首先面向用户写；Prompt 规定表达边界；评测检查内部术语；后处理只做有限清理，不成为第二个答案生成器。
- **状态：**已解决。见 `30_RAG面向用户表达治理.md`。

### 7.7 口语和错别字使相关度下降

- **证据类型：**真实失败。
- **现象：**口语问题最高分只有 `0.3446`，在旧阈值 `0.35` 下被拒答；重度错别字问题的 Top1 也曾错误。
- **解决：**根据正负样本把阈值校准为 `0.30`；保留原始查询，只做受控领域归一化，再将原文与归一化文本双路召回合并，避免模型改写改变原意。
- **结果：**困难集 Top1 从 `3/4` 提升为 `4/4`，口语问题分数提升到 `0.6014`。
- **状态：**已解决当前数据集问题；知识扩容后仍需复验。

### 7.8 为迎合评测，错误地修改 Agent 行为

- **证据类型：**真实失败。
- **现象：**一个所谓“口语规则问题”同时也像是在询问当前积分状态，Agent 调实时 Tool 是合理行为。
- **解决：**保留原始 `10/11` 结果，修正含义不清的评测问题，而不是用 Prompt 强迫模型走 RAG。
- **状态：**已解决。这是“先检查用例是否错，再检查模型是否错”的典型案例。

### 7.9 把受众隔离和无关问题拒答混成一个指标

- **证据类型：**真实失败。
- **现象：**旧版 `15/15` 看似证明拒答稳定；扩大候选池后，`OR13` 被运营奖品文档以 `0.4483` 命中。旧版只是把用户知识过滤后恰好没有剩余候选。
- **根因：**“不能返回用户知识”和“不能返回任何无关知识”是两件事，却由同一用例同时承担。
- **解决：**受众由服务端固定；将受众隔离与无关拒答拆成独立验收条件；运营任务再限定业务知识范围。
- **状态：**当前冻结集已通过。见 `42_运营知识时效与冲突治理.md`。

### 7.10 只按相似度选择知识，忽略新旧制度冲突

- **证据类型：**设计纠偏。
- **问题：**旧制度可能比新通知更像用户问题，纯向量 Top1 不能代表当前有效规则。
- **解决：**知识增加生效区间、权威级别、策略键和显式替代关系；先做有效性过滤，再在候选中按替代关系和权威裁决。
- **状态：**已解决当前明确冲突。见 `42_运营知识时效与冲突治理.md`。

### 7.11 历史引用污染当前回答

- **证据类型：**真实失败。
- **现象：**同一会话上一轮检索了预算通知，下一轮询问“怎么触达用户”没有调用 Tool，回答末尾却仍引用预算通知。
- **根因：**引用补全函数扫描整段会话，而不是当前用户轮次。
- **解决：**从最后一条 HumanMessage 开始收集本轮 Tool 结果；移除模型复用的历史引用；本轮没有检索就不追加来源。
- **状态：**已解决并通过真实两轮对话验证。见 `47_运营意图路由与当前轮引用隔离.md`。

### 7.12 当前仍有的 RAG 边界

- **证据类型：**暂缓问题。
- **问题：**受众隔离能防止普通用户读取运营知识，但“以运营身份提出一个看似用户侧的问题”仍需要任务范围或明确路由，不能只依赖高相关度。
- **当前处理：**运营 Tool 使用服务端受众和 scope；对已经明确的运营任务使用固定知识范围。
- **暂缓原因：**当前没有稳定失败集证明必须引入混合检索、重排或复杂 Query Rewrite。后续先冻结失败样本，再做单变量 A/B。

## 8. 长期记忆

### 8.1 给普通记忆套上二次确认状态机

- **证据类型：**真实设计纠偏。
- **问题：**早期把受控兑换的安全模式复制到所有长期记忆，用户明确说“我喜欢数码类商品”后还要再次确认，交互笨重。
- **根因：**把“写入数据库”一概当成同等级高风险操作，没有按副作用和可逆性分类。
- **解决：**稳定、明确的偏好和目标直接保存；含糊信息才澄清；敏感或不应保存的信息拒绝；不再使用通用记忆确认草案。
- **状态：**已解决。见 `32_兑换目标与长期偏好.md`。

### 8.2 只有出现“请记住”才保存

- **证据类型：**真实失败。
- **现象：**用户在两个会话中明确说“我喜欢数码类商品”，新会话仍读不到。日志显示用户身份正确、读取为空、没有调用保存 Tool。
- **根因：**Prompt 把“明确表达稳定偏好”错误收窄为“明确发出记忆命令”。
- **解决：**识别稳定的第一人称偏好和长期目标；“今天、这次、暂时”等临时条件不保存；不从点击或购买行为擅自推断偏好。
- **状态：**已解决。

### 8.3 为适配固定 Schema 追问用户不必要的信息

- **证据类型：**真实失败。
- **现象：**“我喜欢小鸟”被追问奖品类别和 ID；“明年想换手环”被要求精确日期和具体奖品 ID。
- **根因：**系统优先考虑如何填满数据库字段，而不是忠实记录用户已经表达的内容。
- **解决：**使用原文优先的原子 `MemoryItem`；类型、主题、期限等结构化投影允许为空；真正执行兑换或制定精确计划时再补必要参数。
- **状态：**已解决。见 `33_原文优先的长期记忆内核.md`。

### 8.4 更新整份偏好列表导致误删旧记忆

- **证据类型：**设计纠偏。
- **问题：**模型每次输出一份“完整列表”，遗漏旧项时可能被解释成用户主动删除。
- **解决：**记忆以原子记录执行 `ADD`、`NOOP`、`UPDATE`、`SUPERSEDE`，没有明确冲突就不覆盖其他记忆。
- **状态：**已解决。

### 8.5 每次请求注入全部长期记忆

- **证据类型：**设计纠偏。
- **问题：**记忆越多，Token、噪声和陈旧信息干扰越严重；无关订单问题也可能被偏好带偏。
- **解决：**按当前任务、类型、主题、原文相关性和数量上限召回；只有用户明确要求查看全部记忆时才全量返回。
- **状态：**已解决当前规模问题。见 `34_长期记忆的按需召回.md`。

### 8.6 记忆保存了，却没有参与后续业务

- **证据类型：**产品闭环问题。
- **问题：**只证明“能写、能读”还不算记忆系统。若目标不能驱动积分规划，记忆只是一个独立演示模块。
- **解决：**新增“读取已保存兑换目标 -> 查询实时资格和奖品 -> 生成积分计划”的组合 Skill。
- **状态：**已解决。见 `35_长期目标驱动的积分规划.md`。

## 9. 智能运营与业务闭环

### 9.1 让模型编造客群、库存、成本和历史指标

- **证据类型：**设计纠偏。
- **问题：**运营草案需要事实数据，模型无法可靠估算真实用户数和成本。
- **解决：**通过只读快照提供客群、任务、奖品、库存、单位成本和历史指标；确定性 Skill 校验预算、库存、时间窗和来源，模型只负责理解运营目标与解释结果。
- **状态：**已解决。见 `37_运营活动草案最小闭环.md`、`38_运营身份与真实只读快照.md`。

### 9.2 用户 Agent 和运营 Agent 共用身份与 Tool

- **证据类型：**设计纠偏。
- **问题：**普通用户不应看到运营制度、活动成本和发布能力；把运营 Tool 注册给用户 Agent，再指望模型不调用，并不构成权限隔离。
- **解决：**独立运营令牌、权限、运行时和 Tool Builder；受众和权限由服务端固定，模型不能通过参数扩大范围。
- **状态：**已解决。

### 9.3 把积分当成企业现金预算

- **证据类型：**真实业务建模纠偏。
- **问题：**早期 `budget_points` 同时承担用户激励和企业成本，等于假设积分与人民币存在固定换算。
- **解决：**现金预算使用金额最小单位；积分只作为发放上限；奖品现金成本来自采购或运营事实。积分门槛与单位成本不做虚假换算。
- **状态：**已解决。

### 9.4 “草案生成成功”被误认为活动已经落地

- **证据类型：**产品闭环问题。
- **问题：**只返回一段草案文本，没有持久化版本、审核、发布、审计和效果反馈，无法形成真实运营闭环。
- **解决：**建立草案事实、版本并发检查、人工审核状态机、确定性发布、审计记录和效果回写；下一轮规划读取真实历史指标。
- **状态：**已解决到活动事实发布和人工效果回写。见 `46_运营活动审核发布与效果回流.md`。

### 9.5 “发布活动”被误解为“已经触达用户”

- **证据类型：**真实表达问题。
- **问题：**当前发布只是生成 `SCHEDULED` 或 `ACTIVE` 活动事实；项目尚无活动执行器、用户明细任务和消息渠道。若 Agent 声称已触达，就属于伪造执行结果。
- **解决：**文档和回答明确区分“草案 -> 审核 -> 发布活动事实 -> 执行器 -> 渠道任务 -> 回执 -> 指标”；没有真实渠道时只能解释方法和当前缺口。
- **状态：**边界已澄清，真实自动触达仍未实现。

### 9.6 咨询、规划和执行三种意图被混淆

- **证据类型：**真实失败。
- **现象：**运营人员问“怎么触达用户”，Agent 把它当成立即执行请求，开头大段声明自己不能触达，几乎没有回答“应该怎么做”。
- **根因：**Prompt 只强调能力边界，没有先识别用户是在问方法、要方案，还是要求现在执行。
- **解决：**结构化路由为：
  - `KNOWLEDGE_QUERY`：先回答方法、流程和概念；
  - `PLAN_REQUEST`：读取快照与知识，生成可审核方案；
  - `ACTION_REQUEST`：只调用被允许的写操作，未实现的动作明确不伪造。
- **状态：**已解决当前案例；每轮增加一次分类调用，实测约增加 `1.70~2.06s`，后续可用高置信规则短路优化。见 `47_运营意图路由与当前轮引用隔离.md`。

### 9.7 能力已经演进，旧文档仍描述早期边界

- **证据类型：**真实根因之一。
- **问题：**部分文档还写着“只能生成不可发布草案”，而项目已具备审核和确定性发布。模型检索到旧描述后会错误收缩能力边界。
- **解决：**能力变化时同步更新知识版本、替代关系和边界文档；索引新鲜度门禁阻止旧索引继续服务。
- **状态：**已解决本轮知识，仍需作为持续治理动作。

### 9.8 把内部活动 ID 变成用户的前置知识

- **证据类型：**真实失败。
- **现象：**运营人员问“查看活动历史以及收益”，Agent 要求用户先提供活动 ID；仅补充 Tool 后的第一次复验又退化为欢迎菜单，轨迹为 `events=[]`。
- **根因：**Agent 只有按 ID 查询漏斗的 Tool，没有活动发现 Tool；模型把内部接口必填参数错误地转嫁给用户。首次补 Tool 后，决策规则仍不足以约束模糊短句立即查询。
- **解决：**增加精简的 `list_campaign_activities` 只读 Tool；历史、最近活动、效果和收益查询先自动发现活动，再读取可分析活动的漏斗。只有自然语言目标仍无法消歧时才追问。财务收益与运营 Lift 明确分开。
- **状态：**已解决。真实轨迹为“列活动 -> 并行查询两个活动漏斗”，活动 2 未开始、活动 1 返回演示漏斗；回答不再索要 ID。见 `56_活动历史自动发现与效果解释.md`。

## 10. 架构与技术选型

### 10.1 把课程顺序当成项目实施顺序

- **证据类型：**真实规划纠偏。
- **问题：**课程按知识点由点到面展开，但项目首先需要身份、确认、幂等和结果查询。如果按课时依次“打卡”，会在写操作底座不稳时先堆 RAG、记忆或多 Agent。
- **解决：**课程只做能力索引，实施顺序由业务风险和前置依赖决定；每项技术都要求“失败样本 -> 基线 -> 单变量 A/B -> 收益与复杂度比较”。
- **状态：**已写入最高优先级路线图。

### 10.2 为展示技术提前引入复杂编排

- **证据类型：**多次设计纠偏。
- **问题：**复杂规划失败时，容易直接联想到 Query Rewrite、链式编排或多 Agent；检索失败时，也容易立刻加混合检索和重排。
- **解决：**先判断问题属于 Tool 契约、业务范围、知识治理还是召回能力。当前任务约束问题由 Tool Schema 解决，知识冲突由元数据治理解决，没有证据时不加更重方案。
- **状态：**相关技术保留为触发式选项，不算“遗漏实现”。

### 10.3 MCP 功能完整，但架构方向错误

- **证据类型：**真实架构回滚。
- **现象：**项目曾完整实现统一能力层、MCP Server、Client、双传输、鉴权、审计和 A/B；当时全量 `185` 项测试通过，6 个直连/MCP 场景契约一致。
- **问题：**在没有第二个真实外部调用方之前，为 MCP 新增能力层和多层适配，项目开始从“业务 Agent”偏向“为了展示 MCP 的平台”。技术上能跑，不代表抽象有业务价值。
- **解决：**整体回滚 MCP 代码、测试、配置和对应文档，避免历史设计继续影响后续 Code Agent；先完成兑换助手和运营闭环。只有出现第二个真实调用方，并能量化复用、权限或治理收益时再引入薄协议层。
- **状态：**已彻底回滚。Git 历史保留证据，但当前工作树不保留旧 MCP 设计文档。

### 10.4 为未来多 Agent 提前拆角色

- **证据类型：**设计纠偏。
- **问题：**当前运营快照、知识和草案都服务于一个目标，过早加入 Supervisor、策划 Agent、分析 Agent 会增加调用成本和故障边界，却没有稳定职责冲突证据。
- **解决：**先保留单 Agent 基线；只有上下文互相污染、权限明显冲突或单 Agent 稳定漏步骤时，再设计角色拆分并做 A/B。
- **状态：**暂不引入。见 `45_单体智能运营Agent与工作台.md`。

### 10.5 为了“文档齐全”维护无消费方的上下文目录

- **证据类型：**开发过程纠偏。
- **问题：**文档如果不服务于开发决策、代码理解或面试复盘，只会成为过期信息源，并干扰后续 Agent 判断。
- **解决：**只维护明确有读者和用途的 `agent-design`、`agent-context`、`agent-interview` 与任务日记；无实际消费方的额外学习目录停止维护，错误架构文档随整体回滚删除。
- **状态：**当前执行原则。

## 12. 问题应该修在哪一层

| 观察到的失败 | 优先修复层 | 不应先做的事 |
| --- | --- | --- |
| 模型不知道该查什么 | Prompt 决策规则、Tool 描述 | 立刻增加 Agent 数量 |
| 自然语言约束没进入计算 | Tool Schema、确定性 Skill | 期待模型最后自行过滤 |
| Tool 返回失败后模型猜原因 | Tool 结果码、停止规则 | 补更多猜测案例到 Prompt |
| 缺少业务事实 | Java/API/数据库事实源 | 让模型估算 |
| 缺少稳定规则 | 知识文档和 RAG | 把实时数据写进知识库 |
| 规则过期或冲突 | 元数据、时效、替代关系 | 只提高向量 TopK |
| 无命中仍作答 | 拒答契约、忠实度检查 | 仅要求模型“不要幻觉” |
| 用户问题被误判为执行 | 意图路由、意图专属 Prompt/Tool | 只反复强调能力边界 |
| 高风险写操作 | 服务端身份、状态机、幂等 | 依赖 Prompt 二次确认 |
| 最终答案对但过程不对 | 轨迹和硬约束评测 | 放宽评分只看关键词 |
| 评测规则误判 | 修评分器并离线重评分 | 重跑模型直到通过 |
| 抽象层没有真实复用方 | 删除或回滚抽象 | 用更多适配层证明其必要性 |

## 13. 当前仍未完成，但不应伪装成缺陷

| 项目 | 当前状态 | 何时再做 |
| --- | --- | --- |
| 固定真实兑换端到端回归 | 用户决定暂缓 | 受控兑换核心链路再次变化或发布前 |

## 14. 最终方法论

项目中最有效的开发顺序不是“发现问题 -> 加技术”，而是：

```text
保存失败现场
  -> 判断是答案错、轨迹错、数据错还是评测错
  -> 找到应该负责这一约束的层
  -> 用最小改动修复
  -> 定向复验原失败
  -> 模块完成后阶段回归
  -> 把新边界写回文档和冻结用例
```

最重要的判断标准有三个：

1. **模型擅长理解与生成，不应负责身份、权限、幂等、金额计算和状态迁移。**
2. **最终回答正确只是必要条件，Tool 路径和证据链也必须正确。**
3. **一项技术只有解决了可重复的问题，并且收益高于新增复杂度，才应该进入项目。**
