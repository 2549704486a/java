# 运营意图路由与当前轮引用隔离

> 本阶段修复的不是一句回答，而是一条完整证据链：“怎么触达用户”本应得到方法说明，却被模型当成执行请求；本轮没有检索知识，系统仍追加了上一轮预算文档。解决方案因此同时覆盖意图、Prompt、Tool、知识和引用生命周期。

## 1. 失败现场与直接证据

问题回答以“触达用户不在我的能力范围内”开头，没有解释客群计算、活动执行器、消息渠道和回执等用户真正询问的内容，末尾还引用了“活动预算口径变更通知”。

日志显示：

```text
11:00:10 operator_agent_request_started message_length=6
11:00:15 operator_agent_tool_trace events=[]
```

`events=[]` 证明“怎么触达用户”这一轮没有调用任何 Tool。相同 `session_id` 在更早的轮次曾执行：

```json
{
  "tool_name": "search_operator_knowledge",
  "arguments": {
    "scope": "campaign_policy",
    "query_chars": 18,
    "limit": 3
  },
  "result_code": "KNOWLEDGE_FOUND"
}
```

旧引用补全函数遍历整个会话消息，因此把历史 Tool 的第一条引用当成当前轮证据。代码注释声称是“本轮引用”，实现却没有轮次边界。

## 2. 根因拆分

1. **意图误判**：Prompt 强调“不能触达”，却没有区分咨询方法和立即执行，模型看到“触达”后优先自我澄清。
2. **Prompt 目标偏移**：要求“先给结论”，但没有要求先回答用户真正关心的问题，最终把能力边界放在业务答案之前。
3. **跨轮引用污染**：`InMemorySaver` 保留完整会话，引用函数扫描所有历史 ToolMessage。
4. **知识缺口**：运营知识只有预算、奖品、异常和复盘等内容，没有活动执行与触达说明。
5. **旧边界表述过时**：部分文档仍停留在“只能生成不可发布草案”，没有反映人工审核和确定性发布已经完成。

## 3. 三类意图数据模型

```json
{
  "intent": "KNOWLEDGE_QUERY",
  "confidence": 0.95,
  "requested_action": null,
  "reason": "用户在询问触达方法，没有要求立即发送"
}
```

| 意图 | 例子 | 当前能力 |
| --- | --- | --- |
| `KNOWLEDGE_QUERY` | 怎么触达用户？ | 规划快照、运营知识；先回答方法和流程 |
| `PLAN_REQUEST` | 帮我设计高积分用户触达方案 | 快照、知识、草案 Tool |
| `ACTION_REQUEST` | 现在向这些用户发送通知 | 仅查询相关操作知识；没有触达 Tool 时不得声称执行 |

分类结果只负责选择回答策略和 Tool，不构成授权。真实写操作仍需服务端身份、权限、人工审核和确定性状态机。

## 4. 调用链

```text
运营人员输入
  -> OperatorIntentRouter 结构化分类
  -> 按意图选择同一运营 Agent 的 Prompt 和 Tool
  -> Agent 调用当前意图允许的 Tool
  -> 只从最后一条 HumanMessage 开始收集本轮引用
  -> 返回答案与当前轮真实来源
```

这里没有拆成三个 Agent。运行时只是按 `(operator_id, intent)` 缓存同一套运营 Agent 定义的三个配置，继续共享会话状态和业务实现。

## 5. 引用生命周期修复

引用补全现在先找到最后一条 `HumanMessage`，只在当前轮中收集知识 Tool 返回值。历史引用若再次出现在本轮回答，会被移除；当前轮没有检索时，不再自动追加上一轮来源。

该规则解决的是“证据属于哪一次回答”，不是删除对话记忆。模型仍可看到必要的历史上下文，但引用必须由当前请求重新取得证据。

## 6. 触达知识边界

新增“活动执行与用户触达说明”，明确区分：

```text
草案 -> 人工审核 -> 发布活动事实 -> 活动执行器 -> 渠道任务 -> 渠道回执 -> 行为指标
```

当前项目完成到“发布活动事实”和人工效果回写。活动执行器、用户明细任务、站内信或 Push 等真实渠道以及自动回执仍未实现。因此知识咨询应先解释完整方案，再说明项目现状；执行请求则必须说明当前不能发送。

## 7. 验证口径

本阶段遵循定向优先，没有执行大规模回归：

- 单元测试覆盖结构化结果校验、三类降级规则、意图 Tool 收敛和跨轮引用污染。
- 真实模型分别验证“怎么触达用户”“设计触达方案”“现在发送通知”三条成对表达。
- 知识目录必须通过 Front Matter、来源和切分检查；索引重建后再验证触达问题命中新文档。
- 服务重启后，通过真实 `/v1/operator/chat` 验证最终回答顺序、引用和轨迹。

## 8. 代价与后续观察

- 每次运营对话增加一次短结构化模型调用，会增加少量延迟和 Token 成本；后续应通过轨迹统计真实增量。
- 模型接口不支持结构化模式时使用高精度保守规则；降级结果不会直接授权业务写操作。
- 若固定三类路由仍出现稳定误判，再补少量通用 Few-shot 或验证分类模型，不通过无限增加关键词修补。
