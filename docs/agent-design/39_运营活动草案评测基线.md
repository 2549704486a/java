# 运营活动草案评测基线

> 这组评测回答的不是“模型说得像不像运营人员”，而是“运营身份是否越权、草案是否忠实引用事实、预算和时间约束是否真的满足、输出能否进入人工审核”。当前活动草案由 `CampaignPlanningService` 确定性生成，因此 Service 基线不调用大模型，避免模型偶然答对掩盖工程问题；自然语言入口另行验证 Skill 加载和 Tool 路由。

## 1. 评测对象

评测链路复用正式代码：

```text
冻结 Campaign Fixture
  -> StaticCampaignDataProvider
  -> AuthenticatedOperator
  -> build_operator_tools
  -> CampaignPlanningService
  -> CampaignPlanDraft
  -> 确定性评分器
```

冻结集位于 `agent-service/evals/campaign_cases.json`，运行器位于 `agent-service/evals/campaign_runner.py`。运行方式：

```powershell
cd D:\工作\incentive-事务消息\agent-service
.\.venv\Scripts\python.exe -m evals.campaign_runner
```

冻结集当前包含 8 类边界：完整草案、只读运营、缺少读取权限、未知客群、缺历史指标、过期快照、预算冲突和候选数量上限。

## 3. 四类指标如何计算

每项指标都按“通过检查数 / 适用检查数”计算。不同指标分母不同，不能把没有数据引用的权限用例强行计入数据引用指标。

| 指标 | 核心检查 |
| --- | --- |
| 权限隔离 | 有读取权限才暴露快照 Tool；只有同时具备草案权限才暴露草案 Tool；缺读取权限直接拒绝 |
| 数据引用正确性 | 快照 ID 和时间一致；客群来自同一快照；任务、奖品字段及 `source_ref` 能回查原始事实；未知客群不猜测 |
| 约束满足率 | 状态和原因码、金额预算、积分发放上限、候选数量、完整活动窗口、库存可用性、参与人数和两类结果重算、关键风险均正确 |
| 草案完整性 | 固定为可编辑、不可发布、必须人工审核；阻断风险与状态一致；核心字段完整；不同状态携带正确的数据形态 |

评分器不只比较最终状态。例如草案即使返回 `DRAFT_READY`，只要任务来源被篡改、成本计算错误或奖品在活动中途过期，对应指标仍会失败。

## 4. 首轮基线

| 项目 | 结果 |
| --- | ---: |
| 用例通过率 | `8/8` |
| 权限隔离 | `16/16` |
| 数据引用正确性 | `21/21` |
| 约束满足率 | `35/35` |
| 草案完整性 | `20/20` |
| 模型调用 | `0` |

原始逐项结果保存在 `agent-service/evals/results/campaign_planning_baseline_20260822.json`。测试还主动篡改过任务来源和计划奖品金额，评分器均能将其识别为失败，说明当前满分不是因为评分规则恒真。

## 5. 结果边界

1. 当前结论只证明冻结业务规则和权限边界正确，不代表运营自然语言 Agent 已经完成。
2. Fixture 使用本地演示数据，不包含真实用户数据，也不衡量活动上线后的业务收益。
3. 当前没有模型调用，因此没有 Token、模型延迟、措辞质量和多轮稳定性指标。
4. 后续引入运营对话 Agent、MCP 或多 Agent 时，应复用同一冻结集作为业务正确性基线，再新增各自的路由、成本和稳定性指标。
