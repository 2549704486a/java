# 长期记忆的按需召回

> 本阶段解决“记忆已经存下来了，应该给模型看多少”的问题。用户的全部记忆不是每次对话的固定背景；系统只在当前任务确实需要时，取回少量相关内容。

## 1. 为什么不能每次读取全部记忆

全量注入会带来三个问题：无关信息占用上下文、旧信息干扰当前判断、记忆规模增长后调用成本持续上升。例如用户询问订单状态时，“喜欢小鸟”和“明年换手环”都不应进入模型上下文。

本阶段把读取分成三种模式：

| 模式 | 触发条件 | 返回内容 |
| --- | --- | --- |
| `FILTERED` | 提供当前问题或记忆类型 | 最多返回 `limit` 条相关记忆 |
| `RECENT` | 没有检索语义，也没有要求全部 | 返回最近更新的少量记忆 |
| `ALL` | 用户明确要求查看全部记忆 | 返回全部生效记忆和旧聚合视图 |

## 2. 检索请求模型

```json
{
  "query": "帮我看看手环计划",
  "memory_types": ["goal"],
  "limit": 3,
  "include_all": false
}
```

- `query` 保留当前问题的检索语义。
- `memory_types` 先缩小到目标、偏好、个人信息或经历。
- `limit` 默认是 5，避免一次注入过多内容。
- `include_all` 只有用户明确要求查看全部记忆时才能开启。

返回结果会携带召回元数据：

```json
{
  "memories": [
    {
      "memoryType": "goal",
      "rawText": "我打算明年换一个手环",
      "normalizedData": {
        "subject": "手环",
        "timeExpression": "明年",
        "targetYear": 2027
      }
    }
  ],
  "retrieval": {
    "mode": "FILTERED",
    "queryApplied": true,
    "memoryTypes": ["goal"],
    "totalActive": 2,
    "returned": 1,
    "limit": 3
  }
}
```

来源会话和来源消息仍只留在服务端，不注入模型。

## 3. 当前排序规则

当前单个用户的记忆量很小，因此先采用可解释的确定性排序：

1. 按 `memory_types` 过滤不需要的类型。
2. 主题直接出现在问题中时优先，例如“手环”。
3. 比较用户原文、结构化辅助字段和问题中的中英文词组重合度。
4. 相关度相同时，优先返回最近更新的记忆。
5. 没有类型约束且没有文本相关证据时，不返回记忆。

这套规则不需要额外的向量服务，也不会把记忆检索和业务知识 RAG 混在一起。只有记忆规模增长、同义表达召回持续失败并有评测证据时，再比较语义检索方案。

## 4. 旧聚合视图的边界

`goal` 和 `preferences` 是为旧接口保留的聚合视图，可能一次包含多个偏好。按需检索时返回它们会绕过筛选，因此 `FILTERED` 和 `RECENT` 模式将其置空，只返回命中的原子 `MemoryItem`；`ALL` 模式才返回聚合视图。

## 5. 验证结果

关键测试验证了：

- 手环问题只返回手环目标，不返回小鸟偏好。
- “你记得我喜欢什么”可以按偏好类型返回偏好。
- 订单问题不会注入无关记忆。
- 显式查看全部时不受 `limit` 限制，并兼容返回旧目标视图。

本阶段执行记忆 Store 与 Skill 定向测试，共 `15/15` 通过。按照阶段约定，完整回归留到长期记忆模块全部完成后统一执行。
