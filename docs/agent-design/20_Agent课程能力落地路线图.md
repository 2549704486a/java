# Agent 课程能力落地路线图

> 这份文档回答的是“接下来优先做什么，以及为什么”。课程按照知识讲解顺序组织，但项目必须按照风险、依赖和业务价值推进，因此不能机械地从第一讲依次实现到第十二讲。后续开发以本路线图为最高优先级导向，并允许根据实际进度、验证结果和新发现的问题动态调整。

## 1. 文档定位与优先级

四类文档各自解决不同问题，不能相互替代：

| 文档 | 回答的问题 |
| --- | --- |
| 本路线图 | 下一步优先做什么，为什么这样排序 |
| `agent-context/` | 当前项目和代码的事实是什么 |
| `agent-learning/` | 历史学习资料；仅在明确学习或复习时按需使用 |
| `agent-journal/任务日记.md` | 实际完成了什么，何时完成，如何验证 |

执行时遵守以下优先级：

1. 当前源码和可重复验证结果决定“事实”。
2. 本路线图决定“开发顺序”。
3. 设计文档决定“具体方案”。
4. 课程提供方法和候选技术，不因为课程讲过就强行落地。
5. `agent-learning/` 不参与优先级判断，也不作为日常任务的必填维护项。

## 2. 课程覆盖情况

### 2.1 状态口径

| 状态 | 判定标准 |
| --- | --- |
| 已落地 | 已有运行代码，并有自动化测试、回归结果或真实链路验证 |
| 部分落地 | 核心能力已有实现，但仍存在重要工程缺口 |
| 未落地 | 当前代码和验证材料中没有该能力 |
| 暂缓 | 技术可用，但当前收益不足或前置条件尚未满足 |
| 不适用 | 与当前业务目标没有合理结合点 |

只有完成代码或文档、获得验证证据后，才能修改覆盖状态；“计划实现”不能写成“已落地”。

## 3. 分阶段开发路线

### P0：先补齐受控写操作的工程底座

这是当前最高优先级。受控兑换已经能运行，但确认凭证仍是单进程内存状态，Java 接口的 `Idempotency-Key` 还没有形成持久化幂等闭环。此时继续增加 RAG 或 MCP，只会在不稳固的写操作底座上扩大系统复杂度。

按以下顺序实施：

1. 在 Java 旧兑换入口实现持久化的请求级幂等，明确请求指纹、幂等键、处理中、成功、失败和未知状态。
2. 将 Python `ConfirmationStore` 从单进程内存迁移为 Redis 共享存储，使用原子状态迁移保证多实例下最多执行一次。
3. 明确可信用户身份来源，逐步替代当前由请求参数直接传入 `user_id` 的演示边界。
4. 建立“准备兑换 -> 用户确认 -> Java 受理 -> 查询最终结果”的固定端到端回归。

完成门槛：单元测试、并发测试和本地真实链路验证全部通过；失败与未知结果语义清楚；覆盖表和任务日记已更新。

### P1：把评测从“能跑”升级为“结果可信”

1. 分离调优集和隐藏盲测集，防止针对公开用例背答案。
2. 对非确定性模型用例重复运行，记录成功率和波动，而不是只看单次结果。
3. 组合代码规则、执行轨迹、LLM Judge 和人工抽检，并校准各层误判。
4. 增加 Tool 调用次数、模型耗时、token 和成本指标。
5. 扩充越权、提示注入、重复确认、并发确认和未知结果等对抗用例。

完成门槛：固定回归与盲测分离；评分规则有误判样例和校准记录；关键写操作安全用例必须全通过。

### P2：用 RAG 回答规则，不替代实时 Tool

RAG 的第一个合理场景是积分规则、兑换规则、活动说明和常见问题等静态或低频变化知识。

1. 建立受控知识源和文档版本。
2. 实现切分、元数据、向量化、检索和来源引用。
3. 使用 LCEL 串联检索、上下文构造、回答和结构化输出。
4. 建立检索命中率、引用正确性和无答案拒答评测。

边界必须保持：

- 规则和说明走 RAG。
- 当前积分、库存、任务、奖品和订单状态走 Tool。
- 兑换写操作继续走受控状态机，不交给 RAG。

### P3：治理记忆，而不是无限保存对话

1. 增加 token 预算和上下文裁剪。
2. 对长会话生成可校验摘要，并保留关键业务标识。
3. 增加会话 TTL 和共享 checkpointer，支持多实例。
4. 只有在用户知情且业务确有价值时，才保存长期偏好；动态业务事实不得写入长期记忆。

### P4：用 MCP 标准化只读能力

1. 优先将奖品、任务、积分规则等只读能力封装为 MCP Tool 或 Resource。
2. 对比直接 LangChain Tool 与 MCP 在契约、复用、鉴权、审计和错误处理上的差异。
3. 在身份、幂等和审计尚未成熟前，不把兑换写操作作为通用 MCP 能力暴露。

### P5：完善交互、部署和可运维性

1. 使用 SSE 提供流式回答和步骤状态，而不是让用户长时间等待空白页面。
2. 使用 Docker Compose 固化 Java、Python、前端与中间件的本地开发环境。
3. 补齐优雅停机、健康检查、超时、并发限制和配置校验。
4. 建立指标、日志、轨迹关联和基础 CI 门禁。

### P6：只有证明确有必要时才引入多 Agent

多 Agent 不是课程覆盖任务，而是复杂度治理手段。只有在单 Agent 同时处理知识问答、积分规划和受控兑换时出现稳定且可复现的路由、上下文污染或权限隔离问题，才进行 A/B 评测。

候选结构可以是“协调 Agent + 知识问答 Agent + 规划 Agent + 确定性兑换工作流”，但在证据出现前保持单 Agent 架构。

## 4. 动态调整规则

1. 每项新任务先映射到本路线图的阶段，再决定需要加载哪一节课程和哪些源码。
2. 不随意跳过更高优先级阶段；只有前置阻塞、用户明确改变目标或新证据证明收益更高时才调整。
3. 数据一致性、越权、重复写入和结果未知等问题一旦出现，优先级高于新增功能。
4. 大任务可以拆成可独立验证的小任务，但不能降低原完成门槛。
5. 调整必须在本文“调整记录”中写明触发原因、证据、影响和新顺序。
6. 路线图可以变化，已经发生的代码和验证事实不能为了配合路线图而改写。

## 5. 每次任务完成后的维护动作

每完成一项独立任务，必须同时完成以下动作：

1. 完成实现或文档，并获得可复查的验证证据。
2. 更新本文件“课程覆盖情况”中对应课程的状态、证据和缺口。
3. 更新“当前里程碑”；若优先级发生变化，再更新“调整记录”。
4. 在 `agent-journal/任务日记.md` 记录完成时间、任务概述和验证结果。
5. 使用中文提交信息完成一次 Git 提交。
6. 向用户汇报已完成内容、验证结果和剩余风险。

`agent-learning/` 只有在用户明确要求学习、复习或整理技术专题时才更新，不属于上述必做流程。

推荐使用以下进度记录格式：

```markdown
### YYYY-MM-DD｜任务名称

- 所属阶段：P0/P1/...
- 完成内容：
- 验证证据：
- 课程覆盖变化：
- 剩余问题：
- 下一步：
```
