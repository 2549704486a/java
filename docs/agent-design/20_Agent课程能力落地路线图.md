# Agent 课程能力落地路线图

> 这份文档回答的是“接下来优先做什么，以及为什么”。课程按照知识讲解顺序组织，但项目必须按照风险、依赖和业务价值推进，因此不能机械地从第一讲依次实现到第十二讲。后续开发以本路线图为最高优先级导向，并允许根据实际进度、验证结果和新发现的问题动态调整。

## 1. 文档定位与优先级

四类文档各自解决不同问题，不能相互替代：

| 文档 | 回答的问题 |
| --- | --- |
| 本路线图 | 下一步优先做什么，为什么这样排序 |
| `agent-context/` | 当前项目和代码的事实是什么 |
| `agent-learning/` | 历史学习资料；仅在明确学习或复习时按需使用 |
| `agent-journal/任务日记.md` | 实际完成了什么，何时完成，如何验证 |

执行时遵守以下优先级：

1. 当前源码和可重复验证结果决定“事实”。
2. 本路线图决定“开发顺序”。
3. 设计文档决定“具体方案”。
4. 课程提供方法和候选技术，不因为课程讲过就强行落地。
5. `agent-learning/` 不参与优先级判断，也不作为日常任务的必填维护项。

## 2. 课程覆盖情况

### 2.1 状态口径

| 状态 | 判定标准 |
| --- | --- |
| 已落地 | 已有运行代码，并有自动化测试、回归结果或真实链路验证 |
| 部分落地 | 核心能力已有实现，但仍存在重要工程缺口 |
| 未落地 | 当前代码和验证材料中没有该能力 |
| 暂缓 | 技术可用，但当前收益不足或前置条件尚未满足 |
| 不适用 | 与当前业务目标没有合理结合点 |

只有完成代码或文档、获得验证证据后，才能修改覆盖状态；“计划实现”不能写成“已落地”。

## 3. 最高优先级导向与分阶段开发路线

### 3.1 产品北极星：积分激励智能增长平台

项目不再局限于“兑换聊天入口”，而是扩展为同时服务用户和运营人员的积分激励智能增长平台。扩充业务时必须满足三个条件：业务在积分激励体系中真实存在、能够复用当前数据和链路、引入 Agent 后确实比固定页面或普通接口更有价值。

| 产品区域 | 服务对象 | 核心能力 | Agent 的合理价值 |
| --- | --- | --- | --- |
| 用户增长顾问 | 积分用户 | 查询积分与奖品、建立兑换目标、制定积分计划、解释规则、受控兑换 | 理解自然语言目标，组合实时数据和规则，跨会话持续跟进 |
| 运营智能工作台 | 活动运营人员 | 创建活动草案、检查规则冲突、估算积分成本与库存风险、分析活动效果 | 面对多约束目标组织方案，调用多种数据能力，并给出可审阅的推理依据 |
| 增长知识中心 | 用户、运营和 Agent | 兑换规则、活动制度、奖品说明、历史活动案例、异常处理手册 | 将分散知识统一检索，处理版本、新鲜度、引用和冲突 |
| 业务能力中心 | 前端、Agent、评测工具和未来应用 | 积分、任务、奖品、目标、活动、分析报告等标准能力 | 通过稳定契约复用 Tool 和 Resource，为 MCP 提供真实落点 |
| 评测与治理中心 | 开发和运营人员 | 用例、轨迹、成本、忠实度、权限和发布门禁 | 用证据决定 Prompt、RAG、记忆、MCP 和多 Agent 是否真正改善产品 |

产品边界保持不变：旧事务消息兑换链路继续作为唯一兑换写链路；Agent 可以生成建议或草案，但兑换、活动发布和规则变更等高风险操作必须经过显式确认或人工审核，再由确定性服务执行。

### 3.4 技术准入门槛

我们会主动扩展业务，为课程技术创造合理条件，但每项技术仍须通过证据决定最终形态：

| 候选技术 | 业务前置条件 | 允许保留实现的直接证据 |
| --- | --- | --- |
| 长期记忆 | 已有兑换目标和偏好管理 | 新会话能正确恢复已保存信息；直接稳定陈述无需固定口令即可写入，临时条件不写入，冲突、过期和遗忘可控；不污染实时业务事实 |
| 复杂问题改写 | 已有多约束用户规划或运营策划用例 | 相比原始问题，子任务覆盖率和 Tool 路由稳定提升，延迟与成本可接受 |
| 混合检索或重排 | 知识中心包含精确标识、长文本和历史案例 | 在冻结困难集上提升 Top1、Hit@K 或冲突识别，且不会破坏无答案拒答 |
| MCP | 已有用户端、运营端或评测端中的至少两个真实调用方 | 契约复用、鉴权和审计收益明确，额外延迟和部署复杂度可接受 |
| 多 Agent | 已有活动策划、分析和审核等职责不同的运营任务 | 相比单 Agent，约束满足率、错误隔离或可解释性稳定提升，协作成本可控 |

统一采用以下证据闭环：

1. 先写真实业务场景和验收指标。
2. 使用当前实现建立单 Agent 或现有检索基线。
3. 保存失败样本，区分能力不足、数据不足和评测误判。
4. 只针对失败原因引入候选技术，并做定向 A/B 对照。
5. 同时评估准确率、稳定性、延迟、成本和维护复杂度。
6. 只有收益稳定且大于复杂度时才保留，否则回退到简单方案。

回归频率遵循“定向优先、里程碑全量”：单个小改动只跑相关单元测试和困难用例；完成一个阶段、修改核心路由或准备发布时，再执行完整评测与回归。

### P0：先补齐受控写操作的工程底座

该阶段的身份、幂等、共享确认和结果查询已经完成，固定真实端到端回归按用户决定暂缓。兑换受理后的状态由真实订单记录提供，页面只对处理中订单轮询，不再依赖模型解释最终结果。

按以下顺序实施：

- [x] 在 Java 旧兑换入口实现持久化的请求级幂等，明确请求指纹、幂等键、执行中、完成和未知状态。
- [x] 将 Python `ConfirmationStore` 从单进程内存迁移为 Redis 共享存储，使用原子状态迁移保证多实例下最多执行一次。
- [x] 使用签名 JWT 建立可信用户身份来源，移除请求体和路径中的 `user_id` 演示边界。
- [x] 增加真实兑换记录查询 Tool 和身份绑定订单页面，明确处理中、成功和失败三种状态。
- [ ] 建立“准备兑换 -> 用户确认 -> Java 受理 -> 查询最终结果”的固定端到端回归。（用户决定暂缓，不阻塞 P1）

完成门槛：单元测试、并发测试和本地真实链路验证全部通过；失败与未知结果语义清楚；覆盖表和任务日记已更新。

### P1：把评测从“能跑”升级为“结果可信”

- [x] 分离调优集和冻结盲测集，防止针对公开用例背答案；盲测结果默认脱敏并记录用例集哈希。
- [x] 对非确定性模型用例支持重复运行，记录逐用例成功率、稳定/波动状态、耗时 P95 和标准差。
- [ ] 组合代码规则、执行轨迹、LLM Judge 和人工抽检，并校准各层误判。（后续补充）
- [x] 增加 Tool 调用次数、模型耗时、Token 和可配置成本指标，并区分端到端、模型与 Tool 耗时。
- [ ] 扩充越权、提示注入、重复确认、并发确认和未知结果等对抗用例。（与安全硬门禁一并后续补充）

完成门槛：固定回归与盲测分离；评分规则有误判样例和校准记录；关键写操作安全用例必须全通过。

### P2：用 RAG 回答规则，不替代实时 Tool

RAG 的第一个合理场景是积分规则、兑换规则、活动说明和常见问题等静态或低频变化知识。

1. [x] 建立受控知识源和文档版本。
2. [x] 实现切分、Chunk 元数据、向量化接口和可重复构建的本地索引。
