# 长期目标驱动的积分规划

> 本阶段把“记住用户目标”和“根据实时情况制定计划”连成闭环。长期记忆只负责回答用户想要什么，积分、库存、资格和任务仍在每次规划时重新查询。

## 1. 用户场景

用户先说：

> 我打算明年换一个手环。

几天后在新会话中说：

> 帮我规划之前的手环目标。

Agent 不需要用户重复描述目标，也不能直接拿旧积分生成答案。它调用 `plan_points_for_saved_goal`，由确定性代码完成目标读取、奖品解析和实时积分规划。

## 2. 完整流程

```text
用户要求规划已保存目标
  -> 读取当前用户生效的 goal 记忆
  -> 根据 goal_query 定位目标
  -> 检查目标时间是否过期
  -> 读取已绑定 awardId，或按 subject 匹配当前奖品
  -> 唯一奖品：复用 PointsPlanningSkill
  -> 查询实时资格、积分缺口和可用任务
  -> 返回目标上下文与实时 PointsPlan
```

无法唯一确定时不会猜测：多个长期目标要求用户先选择目标；“手环”同时匹配多个奖品时返回候选奖品。

## 3. 输入与输出模型

Tool 输入只保留定位目标和任务排除条件：

```json
{
  "goal_query": "手环目标",
  "excluded_task_ids": []
}
```

唯一解析成功后的输出示例：

```json
{
  "status": "TARGET_RESOLVED",
  "goal_raw_text": "我打算明年换一个手环",
  "goal_time_expression": "明年",
  "target_year": 2027,
  "candidates": [],
  "plan": {
    "status": "PLAN_READY",
    "award_id": 8,
    "award_name": "智能手环",
    "current_points": 300,
    "required_points": 500,
    "points_gap": 200,
    "recommended_points": 200,
    "remaining_gap": 0
  }
}
```

如果“手环”对应多个当前奖品，只返回候选：

```json
{
  "status": "AWARD_NEEDS_SELECTION",
  "goal_raw_text": "我打算明年换一个手环",
  "candidates": [
    {"award_id": 8, "name": "智能手环", "required_points": 500, "inventory": 20},
    {"award_id": 9, "name": "运动手环", "required_points": 800, "inventory": 10}
  ],
  "plan": null
}
```

## 4. 目标解析规则

| 目标状态 | 系统动作 |
| --- | --- |
| 没有保存目标 | 不查询业务服务，提示用户先建立目标 |
| 只有一个目标 | 直接尝试解析 |
| 有多个目标且问题包含主题 | 按主题定位，例如“手环目标” |
| 有多个目标但无法唯一定位 | 返回需要选择，不使用最近一条替用户决定 |
| 目标已绑定 `awardId` | 跳过奖品列表，直接规划 |
| 宽泛目标唯一匹配当前奖品 | 使用匹配奖品进行规划 |
| 宽泛目标匹配多个奖品 | 返回候选让用户选择 |
| 目标期限已过 | 停止业务查询，要求先更新目标 |

## 5. 事实边界

- 目标原文和时间属于长期记忆，可以跨会话复用。
- 奖品列表、库存、兑换资格、积分和任务属于动态事实，每次规划实时查询。
- 现有任务接口没有任务耗时和周期信息，因此系统只能判断当前任务奖励能否覆盖缺口，不能虚构精确完成日期。
- `plan_points_for_saved_goal` 已经包含目标召回和 `PointsPlanningSkill`，模型不得在前后重复调用相关基础 Tool。

## 6. 验证

关键测试覆盖：无目标时零业务查询、绑定奖品跳过列表、宽泛目标唯一匹配、多个奖品要求选择、过期目标停止查询，以及写入 Tool 与规划 Tool 共享同一 Store。

新增组合 Skill 与原积分规划定向测试共 `14/14` 通过；连同长期记忆、Prompt 和 Skill 注册的本轮定向验证共 `34/34` 通过。完整回归仍按约定留到当前模块阶段完成后执行。
