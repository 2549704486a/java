# 运营 RAG 纯向量检索基线

> 本轮先回答一个问题：运营知识扩充后，当前纯向量检索到底能做到什么程度。只有先保留基线，后续才能判断关键词检索、混合召回、重排或 Query Rewrite 是真实优化，还是无效复杂度。

## 1. 测试范围

冻结 `15` 条运营检索用例，不调用对话模型：

| 类型 | 代表问题 | 目的 |
| --- | --- | --- |
| 精确编号 | 查询 `OPS-RUNBOOK-CAMPAIGN-001` | 验证编号能否找到对应手册 |
| 精确条款 | 快照超过 24 小时能否继续规划 | 验证具体制度条款 |
| 语义案例 | 查找类似的高积分用户召回案例 | 验证非关键词式案例召回 |
| 字段语义 | 兑换门槛是否等于采购成本 | 验证相近业务概念区分 |
| 口语表达 | “快照放两天了还能用不” | 验证非正式表达 |
| 知识冲突 | 旧预算说法与新通知冲突 | 验证能否召回纠正依据 |
| 受众隔离 | 运营入口询问用户兑换状态 | 验证用户知识不会越界返回 |
| 无关问题 | 询问圆面积 | 验证拒答 |

用例保存在 `agent-service/evals/operator_rag_cases.json`，原始结果保存在 `agent-service/evals/results/operator_rag_vector_baseline_20260822.json`。

## 2. 执行方式

```powershell
cd D:\工作\incentive-事务消息\agent-service
.\.venv\Scripts\python.exe -m evals.rag_runner `
  --mode retrieval `
  --case-file evals\operator_rag_cases.json `
  --audience operator `
  --split all `
  --output evals\results\operator_rag_vector_baseline_20260822.json
```

Runner 的 `audience` 由调用端固定为 `operator`，不是模型生成的参数。

## 3. 结果

| 指标 | 结果 |
| --- | ---: |
| 用例通过 | `15/15` |
| Top1 | `100%` |
| Hit@3 | `100%` |
| 负样本拒答率 | `100%` |
| 引用结构有效率 | `100%` |
| 正样本 Top1 最低分 | `0.4214` |
| 正样本 Top1 平均分 | `0.6034` |
| 正样本 Top1 最高分 | `0.7686` |

最低分来自口语问题“快照都放两天了，还能接着拿来出方案不？”。它虽然正确命中异常手册，但与阈值 `0.30` 的余量只有约 `0.12`。知识继续扩容后，这类问题最可能先出现排序下降。

受众隔离用例的原始候选最高分为 `0.6413`，但候选属于 `end_user` 知识，因此运营检索最终返回 `NO_RELEVANT_KNOWLEDGE`。这说明拒答来自服务端受众过滤，而不是相似度不足。

## 4. 能得出什么结论

当前知识规模只有 8 篇、33 个 Chunk，纯向量检索已经覆盖本轮精确编号、条款、案例和口语问题。现在直接加入混合检索或重排，没有基线失败作为收益证据。

因此下一步不直接堆检索算法，而是先完成运营检索 Tool、生效时间过滤和真正的多文档冲突治理。等知识规模扩大或冻结集出现稳定失败，再使用同一批用例做消融对比。

## 5. 不能得出什么结论

- 两条“知识冲突”用例是用户陈述与受控知识冲突，不是两个有效知识文档互相冲突。
- 本轮没有调用 Agent，不衡量 Tool 路由、答案生成、引用表达和忠实度。
- 用例基于当前知识设计，不是独立盲测集，不能描述成生产准确率。
- `15/15` 不能证明知识扩容后仍无需关键词检索或重排。

后续完整模块测试需要补充同权威级别冲突、不同生效时间冲突和旧制度与新通知冲突，并保留纯向量模式作为 A/B 基线。

> 后续复验说明：治理层为了过滤更多候选，将召回池从 `2 × limit` 扩到 `4 × limit` 后，`OR13` 暴露出运营文档误召回。旧基线的拒答部分依赖候选池较小，不能单独证明语义拒答稳定。修正过程与最终证据见 `42_运营知识时效与冲突治理.md`。
